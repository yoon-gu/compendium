## 한눈에 보기

은행이 코딩 에이전트를 쓰려면 무엇이 걸릴까? 돈과 규제다. Revolut은 프런티어 모델 API 대신 오픈 웨이트 모델을 전용 GPU에 올려 둘을 한꺼번에 풀었다.

| 항목 | 내용 |
|---|---|
| 규모 | 엔지니어 2,031명, B200 GPU 56장 |
| 모델 | GLM[^glm]. 4월 GLM 5.1로 시작, 지금은 GLM 5.3. Together AI[^together] 전용 추론 위에서 돈다 |
| 효과 | 슬라이드 기준 리드 타임 60% 개선. 말로는 코딩 시간 60%, 리드 타임 70% |
| 비용 | 토큰 백만 개에 0.30달러, 캐시는 무료. Anthropic·OpenAI에 쓰던 돈의 10분의 1, 매달 같은 금액 |
| 튜닝 | GPU는 그대로 두고 설정만 바꿔 처리량 76% 증가, 첫 토큰 시간 88% 감소 |
| 규제 | 코딩 에이전트는 자율 에이전트가 아니라 사람이 낀 생산성 도구. 샌드박스·데이터 위치·로그로 증명 |

## 먼저, 오픈 웨이트 모델을 직접 띄운다는 것

참고: [vLLM 문서](https://docs.vllm.ai/), [llm-d, prefill/decode 분리](https://llm-d.ai/docs/well-lit-paths/pd-disaggregation)

보통 회사는 Claude Code[^claudecode]나 Codex[^codex]를 쓸 때 모델 회사의 API를 부르고 쓴 토큰만큼 돈을 낸다. 편하다. 대신 많이 쓰면 청구서가 튄다.

다른 길도 있다. 가중치가 공개된 모델, 곧 오픈 웨이트(open-weight) 모델을 받아 내가 빌린 GPU에 올린다. 그러면 돈은 GPU 시간으로 나간다. 많이 쓰든 적게 쓰든 같은 금액이다. 데이터도 내가 고른 나라의 서버를 벗어나지 않는다.

공짜 점심은 없다. 서빙을 내가 책임져야 한다. 발표에 나오는 용어를 먼저 정리해 둔다.

| 용어 | 뜻 | 이 발표에서 |
|---|---|---|
| 첫 토큰 시간(time to first token, TTFT) | 요청을 보내고 첫 글자가 올 때까지 | 3초 아래가 목표. 5초를 넘으면 슬랙 항의가 쏟아진다 |
| 초당 토큰(tokens per second, TPS) | 답을 뽑아내는 속도 | 200이면 충분. 저녁 5시 이후엔 800 |
| 초당 요청(requests per second, RPS) | 서버가 받는 요청의 양 | 수요. 튜닝 뒤 76% 더 받았다 |
| KV 캐시(KV cache) | 앞 문맥을 다시 계산하지 않도록 GPU 메모리에 둔 중간값 | 긴 문맥과 동시 사용자가 이 메모리를 먹는다 |
| 양자화(quantization) | 숫자를 더 적은 비트로 저장 | Blackwell[^b200]에선 FP4 |
| 텐서 병렬(tensor parallelism, TP) | 모델 하나를 GPU 여러 장에 쪼개 싣기 | TP4에 들어가도 TP8이 나을 수 있다 |
| 캐시 적중(cache hit) | 같은 앞부분을 다시 계산하지 않고 재사용 | 코딩 작업은 90% 넘어야 한다 |
| prefill/decode 분리(PD disaggregation) | 입력 읽기와 답 쓰기를 다른 GPU에 맡기기 | 새로 켠 설정 |

클라이언트 코드로 보면 차이는 작다. 원문에는 코드가 없으니 아래 예는 차이를 보이려고 파이썬으로 새로 적은 것이다. 엔드포인트 주소와 모델 이름은 자리만 잡아 두었다.

```python
# 보통 방식: 프런티어 모델 API를 토큰 단위로 산다
from anthropic import Anthropic

client = Anthropic()                     # 요청마다 입력·출력 토큰 값을 낸다
reply = client.messages.create(          # 월말 청구서가 사용량을 따라 흔들린다
    model="claude-opus-5-5",
    max_tokens=2048,
    messages=[{"role": "user", "content": "이 테스트가 왜 깨지는지 찾아 줘"}],
)
print(reply.content[0].text)
```

```python
# Revolut 방식: 오픈 웨이트 모델을 전용 GPU에 올리고 OpenAI 호환 API로 부른다
import os
from openai import OpenAI

client = OpenAI(
    base_url="https://<전용 엔드포인트>/v1",   # 회사가 빌린 GPU 56장. 값은 GPU 시간으로 고정
    api_key=os.environ["ENDPOINT_KEY"],
)
reply = client.responses.create(              # Responses API를 지원하니 Codex·OpenCode에 그대로 꽂힌다
    model="<GLM 모델 이름>",
    input="이 테스트가 왜 깨지는지 찾아 줘",
)
print(reply.output_text)
```

바뀌는 것은 주소와 모델 이름 두 줄이다. 진짜 차이는 코드 밖에 있다. 청구서가 고정되고 데이터가 어디서 처리되는지 내가 정한다. 느려지면 그것도 내 책임이 된다.

## Revolut은 어떤 회사인가

발표자는 미국 청중을 위해 짧게 소개하고 시작한다. 유럽의 디지털 은행이다. 슬라이드에 적힌 숫자는 이렇다.

- 고객 8천만 명 이상, 45개 이상 시장
- 유럽에서 가장 많이 내려받은 금융 앱
- 기업 가치 1,150억 달러 이상, 유럽에서 가장 비싼 비상장 회사
- 2025년 매출 60억 달러 이상, 전년보다 46% 성장

이 회사는 제품을 많이 내는 것을 중요하게 여겨서 엔지니어링 속도에 관심이 많다.

## 코딩이 병목이 아니었다

발표자는 엔지니어 2,031명의 1년 반 기록을 담은 그래프 하나를 보여 준다. 선은 둘이다. 하나는 리드 타임(lead time)으로, 엔지니어가 기능을 집어 든 때부터 병합되어 배포할 준비가 될 때까지를 일 단위로 잰다. 다른 하나는 시간 단위로 잰 코딩 시간이다.

그래프에는 세 시점이 찍혀 있다.

1. 2025년 1월: 사내에 Gemini[^gemini]를 열어 처음으로 사내 데이터를 AI에 넣을 수 있게 됐다. 스택 오버플로와 문서를 뒤지지 않아도 되니 리드 타임이 10%, 코딩 시간이 20% 줄었다.
2. 2026년 1월: Claude Code를 전사에 깔았지만 효과는 크지 않았다. 엔지니어 한 명이 한 달에 1천 달러, 1만 달러를 쓰는데 그만큼 돌아오지 않았다. 그래서 예산 상한을 엄격하게 걸고 풀었다.
3. 2026년 4월: GLM 5.1을 직접 띄웠다. 선이 크게 꺾였다.

왜 이때 꺾였을까? 발표자는 토큰을 아낄 필요가 없어져서라고 답한다. 상한이 있으면 엔지니어는 토큰을 분기 말이나 가장 어려운 일을 위해 남겨 둔다. 상한이 없으면 메일함을 뒤지거나 Jira·Confluence를 만지는 잡일에도 마음 편히 쓴다.

줄어든 폭은 오히려 코딩 시간보다 리드 타임 쪽이 컸다. 발표자는 여기서 엔지니어링의 병목이 꼭 코딩은 아니라고 결론짓는다. 코드를 쓰는 시간보다 그 주변에서 새는 시간이 더 길다.

> 해설 — 이 비교는 깔끔한 실험이 아니다. 2026년 4월 전후로는 모델 자체도 좋아졌고 사람들이 에이전트를 쓰는 방식도 바뀌었다. 그러니 리드 타임 개선을 모델 교체 하나의 효과로 볼 수는 없다. 숫자도 슬라이드(리드 타임 60%)와 말(리드 타임 70%)이 조금 다르다. 다만 "토큰 걱정이 사라지자 잡일에 AI를 쓰기 시작했다"는 관찰은 사용 방식에 대한 이야기라 숫자보다 오래 갈 만하다.

## 오픈 웨이트가 기본, 프런티어는 예외

그래서 지금은 어떤가? 오픈 웨이트 모델이 Revolut의 기본값이 됐다. 이유는 두 가지다.

- 청구서가 예측된다. 매달 같은 금액이라 월말에 놀랄 일이 없다.
- 리드 타임이 줄었다.

그렇다고 프런티어 모델을 버리지는 않았다. Codex, Claude Code, Gemini는 지금도 쓴다. 최신 모델이 훌륭하다는 것은 발표자도 인정한다. 다만 예외로 두고 GPT나 Claude가 가장 잘하는 몇몇 일에만 쓴다.

## 엔지니어를 행복하게 하는 숫자

모델을 직접 돌릴 때 잴 숫자는 "행복한 엔지니어를 위한 지표"라는 제목의 슬라이드에 모여 있다.

| 숫자 | 뜻 |
|---|---|
| 2,000 | GLM 5.3을 B200 56장으로 2,000명에게 대 준다. 토큰을 쓰면서 눈치 볼 필요가 없다 |
| 3초 미만 | 첫 토큰 시간. 경험상 5초를 넘으면 발표자의 슬랙이 터진다 |
| 200 이상 | 초당 토큰 목표. 이 정도면 사람들이 불만이 없다 |
| 0.30달러 | 입력·출력 토큰 백만 개당, 캐시는 무료. 비용은 예전의 10분의 1 |

초당 토큰은 왜 200이면 될까? 일하는 방식이 바뀌었기 때문이다. 사람들은 이제 모델이 생각하는 글자가 흘러가는 것을 지켜보지 않고 작업을 여러 개 동시에 걸어 두었다가 끝나면 들여다본다. 그래서 첫 토큰이 빨리 오는 것이 중요하고 뒤의 속도는 덜 중요하다. 발표자는 농담도 한다. 저녁 5시가 지나 GPU가 한가해지면 초당 800 토큰이 나오는데 그때 접속하면 꿈 같다고.

GLM은 큰 모델이다. GLM-5.1만 해도 파라미터가 7,540억 개인 전문가 혼합(mixture of experts, MoE) 모델이다. 이걸 2,000명이 함께 쓰게 하려면 B200 56장이 든다.

## GPU를 늘리지 말고 먼저 설정을 고쳐라

이 발표의 가장 기술적인 대목이다. 가중치를 GPU에 올리고 추론을 돌리기만 하면 성능이 형편없으니 작업 종류에 맞게 설정을 고쳐야 한다.

슬라이드의 그래프는 4월부터 8월까지의 기록이다. 파란 선이 수요(RPS), 빨간 선이 최적화 대상인 첫 토큰 시간이다. 첫 토큰은 처음에 10초를 넘었고 이전하던 도중에는 14.26초까지 갔다가 8월에 1.68초가 됐다. 그동안 GPU는 56장 그대로였다.

```
처리량(RPS)      76% 증가
첫 토큰 시간      14.26초 → 1.68초 (88% 감소)
GPU             56장 그대로
```

슬라이드 부제를 보면 개선의 80%는 GPU를 더 사지 않고 하이퍼파라미터를 고친 데서 나왔다. 그래서 제목이 "확장을 참고, 먼저 튜닝하라"다.

무엇을 고쳤을까? 발표자는 비법은 없다며 살펴볼 것을 늘어놓는다.

1. 긴 문맥은 속임수다. 백만 토큰을 받을 수 있어도 실제로 필요한 건 25만 6천 토큰이다. 긴 문맥은 KV 캐시를 많이 먹고 얻는 것은 적다.
2. 양자화. Blackwell 세대 GPU라면 FP4보다 높은 정밀도로 돌릴 이유가 없다. 발표자 말로는 FP8에서 FP4로 내리면 GPU 사용량이 40% 줄고 정확도 손실은 없다.
3. 텐서 병렬. GLM은 GPU 4장(TP4)에 들어가지만 그러면 KV 캐시 자리가 모자란다. 작업량에 따라 8장(TP8)이 더 나을 수 있다.
4. 캐시 적중률. 코딩 작업이면 90%를 넘어야 한다. 같은 사용자의 요청을 같은 서버로 보내는 고정 세션(sticky session)이 여기에 도움이 된다.
5. 그 밖에 추측 디코딩(speculative decoding)과 prefill/decode 분리. 분리는 Together AI 전용 추론에서 새로 켠 기능이다.

> 해설 — "FP4로 내려도 손실이 없다"는 말은 발표자의 경험이다. 근거가 되는 평가는 발표에 나오지 않는다. 코딩 작업의 품질은 벤치마크 점수보다 미묘하게 떨어지기도 하니, 따라 하려면 자기 작업으로 직접 재 봐야 한다. 반대로 "GPU를 사기 전에 설정부터"라는 교훈은 거의 모든 자체 서빙에 통한다. 같은 하드웨어에서 첫 토큰 시간이 8분의 1이 됐다는 숫자가 그걸 보여 준다.

## 실제 운영 구성

슬라이드에는 세 칸이 있다.

| 텍스트 모델 | 비전 모델 | 하니스·앱 |
|---|---|---|
| 글로 쓴 설명을 넣으면 돌아가는 코드가 나온다 | 목업을 넣으면 돌아가는 화면이 나온다 | CLI냐 앱이냐 |

GLM은 텍스트만 다루는 모델이라 그림을 못 읽는 게 흠이다. 그래도 발표자는 매번 더 똑똑한 모델을 고르겠다고 한다. 그림은 다른 방법으로 풀면 된다. 로컬 라우터를 두고 이미지 인식만 Gemini 같은 비전 모델로 보내고 본 작업은 GLM이 맡는다. 꼭 비전 모델이 필요하면 GLM의 작은 비전 모델도 잘 돈다. UI 디자이너가 이걸로 화면 시안 만드는 시간을 크게 줄였다고 한다.

마지막은 하니스다. 이 엔드포인트는 모두 OpenAI 호환 API이고 Responses API를 지원한다. 그래서 OpenCode[^opencode], Codex CLI, Codex 앱에 그대로 꽂아 쓸 수 있다.

## 규제받는 은행이 통과한 방법

마지막 슬라이드 제목은 "이 방에 계신 CIO께"다.

먼저 중국산 모델에 대한 거부감 이야기다. GLM은 중국 회사 Z.ai[^glm]가 만들었다. 발표자의 반론은 간단하다. 가중치만 받아 미국이나 유럽 서버에 올려 쓴다. 중국으로 가는 추론 서버를 쓰지 않으니 데이터도 중국으로 가지 않는다.

Revolut은 유럽연합의 규제를 받는 은행이라 가장 엄격한 규제를 받는다. 코드베이스가 감사 대상이니 AI도 꼼꼼히 들여다본다. 여기서 Revolut은 코딩 에이전트를 자율 에이전트가 아니라 "사람이 낀 생산성 도구"로 분류하는 길을 찾았다. 그러면 자율 에이전트만큼 무거운 규제 감사를 받지 않는다.

물론 말로만 하면 안 된다. 증명할 장치가 셋 필요하다.

| 샌드박스 | 데이터 보호 | 분석·로그 |
|---|---|---|
| 사람이 반드시 끼게 한다 | 데이터를 남기지 않는다(zero data retention) | 사고 조사와 감사에 쓴다 |
| 내부의 나쁜 사용을 막는다 | 미국·유럽연합·영국·이스라엘 안에서만 처리 | 사용 분석도 덤으로 얻는다 |
| 프롬프트 주입을 막는다 | | |

샌드박스는 어렵지 않다. Codex나 Claude Code에는 이미 승인 기능이 있으니 허용하지 않을 명령만 규칙으로 정하면 된다. 예를 들어 grep은 허용하고 gradle은 막는다. Claude Code라면 설정 파일에 이렇게 적는다.

```json
{
  "permissions": {
    "allow": ["Bash(grep:*)"],
    "deny": ["Bash(gradle:*)"]
  }
}
```

이런 규칙이 있으면 이것이 따로 감독해야 할 자율 에이전트가 아님을 규제 당국에 보여 줄 수 있다. 샌드박스는 회사 안의 나쁜 사용자도 막는다. 발표자는 큰 회사에서 무슨 일이 벌어지는지 알면 놀랄 거라고 말한다. 프롬프트 주입은 모델이 똑똑해져서 예전만큼 걱정거리는 아니지만 늘 대비해야 한다.

데이터는 데이터 동등성 체계(data equivalency framework)에 든 나라에 두면 된다. 미국, 유럽연합, 영국, 이스라엘이다. 추론 회사나 GPU 회사는 기본으로 데이터를 남기지 않는다. 마지막으로 사고가 나면 로그를 깊이 파고들 수 있어야 하니 OpenTelemetry[^otel] 같은 탄탄한 관측 장치가 있어야 한다.

## 정리

이 발표는 두 가지 통념을 건드린다. 하나는 코딩 에이전트의 효과가 더 좋은 모델에서 나온다는 생각이다. Revolut의 경험은 다르다. 조금 덜 똑똑해도 토큰을 마음껏 쓸 수 있는 모델이 리드 타임을 더 줄였다. 엔지니어가 시간을 잃는 곳이 코딩 바깥에 있었기 때문이다.

자체 서빙은 GPU를 많이 사야 하는 일이라는 통념도 있다. 발표자는 반대로 GPU를 늘리기 전에 문맥 길이, 양자화, 병렬화, 캐시를 먼저 고치라고 말한다. 같은 56장으로 첫 토큰 시간이 8분의 1이 됐다.

나는 규제 대목이 가장 실용적이라고 본다. 은행은 대개 "통제할 수 없는 자율 시스템"이라는 걱정 때문에 코딩 에이전트를 막는다. Revolut은 그 걱정을 기술 장치로 바꿔 답했다. 승인 규칙, 데이터 위치, 로그. 셋 다 이미 있는 도구로 만들 수 있다.

> 해설 — 걸러 볼 점이 몇 가지 있다. 발표가 12분짜리라 수치의 근거가 다 나오지 않는다. 리드 타임 개선이 모델 교체 때문인지 다른 변화 때문인지도 가려지지 않았다. 청구서가 10분의 1이 됐다는 비교에도 GPU 계약 조건이 들어 있지 않다. 2,000명이 꾸준히 쓰는 규모라서 고정 비용이 남는 장사가 됐을 수 있다. 작은 팀이면 계산이 다를 것이다. 마지막으로 "사람이 낀 생산성 도구"라는 분류가 다른 나라 규제 당국에서도 통할지는 알 수 없다. 이건 Revolut이 자기 감독 당국과 맞춘 해석이다.

[^revolut]: Revolut — 2015년 영국에서 시작한 디지털 은행. 이 글에서는 엔지니어 2,000명에게 코딩 모델을 직접 띄워 대 주는 회사로 나온다.
[^glm]: GLM — 중국 AI 회사 Z.ai(옛 Zhipu AI)의 언어 모델 계열. GLM-5.1은 2026년 4월 MIT 라이선스로 공개된 7,540억 파라미터 MoE 모델이다. 이 글에서는 Revolut이 직접 띄운 주력 코딩 모델로 나온다.
[^together]: Together AI — 오픈 모델 추론과 GPU를 빌려주는 미국 회사. 이 글에서는 Revolut의 GLM이 올라간 전용 추론 서비스로 나온다.
[^claudecode]: Claude Code — Anthropic의 터미널 코딩 에이전트. 이 글에서는 2026년 1월 전사에 깔았지만 예산 상한 탓에 효과가 작았던 도구로 나온다.
[^codex]: Codex — OpenAI의 코딩 에이전트(CLI와 앱). 이 글에서는 프런티어 예외로 남겨 둔 도구이자, 자체 GLM 엔드포인트를 꽂아 쓰는 하니스로 나온다.
[^gemini]: Gemini — Google의 AI 모델. 이 글에서는 2025년 1월 사내에 처음 연 AI이자, 이미지 인식을 넘겨받는 비전 모델로 나온다.
[^b200]: B200 — NVIDIA의 Blackwell 세대 데이터센터 GPU. FP4 연산을 하드웨어로 지원한다. 이 글에서는 GLM을 올린 56장으로 나온다.
[^opencode]: OpenCode — 여러 모델 회사의 API를 골라 쓸 수 있는 오픈소스 터미널 코딩 에이전트. 이 글에서는 GLM 엔드포인트를 꽂아 쓰는 하니스로 나온다.
[^otel]: OpenTelemetry — 로그·지표·추적 데이터를 모으는 오픈 표준. 이 글에서는 사고 조사와 감사를 위한 관측 장치로 나온다.
