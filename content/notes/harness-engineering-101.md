## 한눈에 보기

에이전트란 무엇인가? 저자는 채팅 API 호출을 while 루프로 감싼 것이라고 답한다. 거기에 붙는 나머지는 다 뭔가가 고장 나서 덧댄 땜질이다. 책 16장은 모두 같은 틀로 짜였다. 무엇이 고장 났나, 가장 작은 땜질은 무엇인가, 그 땜질의 값은 얼마인가. 본문과 함께 의존성 없는 파이썬 장난감 하니스도 자라서 마지막에는 300줄쯤 되는 코딩 에이전트가 된다.

| 부 | 장 | 고장 | 땜질 |
|---|---|---|---|
| 1부 통신선 | 1-5 | 모델과 말하는 법, 모델이 아무것도 못 만짐, 한 번의 도구 호출로는 부족함, 비용 폭증 | JSON 배열, 도구, 에이전트 루프, 프롬프트 캐싱 |
| 2부 오래 달리기 | 6-9 | 배열이 컨텍스트 창을 다 채움, 작업이 배열 하나에 안 들어감, 모델이 길을 잃음, 세상은 비동기 | 예산 관리, 서브에이전트, 리마인더, 백그라운드 작업 |
| 3부 생태계 | 10-12 | 프레임워크가 막연히 두려움, 능력이 배열에 다 안 들어감, 모델이 본 것을 모름 | 해독표, MCP·스킬·지연 로딩·훅, 요청 캡처 |
| 4부 신뢰·도메인·데이터 | 13-15 | 루프가 언젠가 사고를 침, 몸을 얼마나 특화할지, RAG라는 이름의 홍수 | 다섯 겹 방어, 코딩 에이전트 사례, 밀어 넣기와 끌어오기 |
| 에필로그·부록 | E, A-D | 실제로 만들어 보기, 고급 주제 | 300줄 하니스, 모델 라우팅·워크트리·플랜 모드·재시도 |

## 먼저, 하니스란 무엇인가

참고: [원문 서문](https://isuruwijesiri.com/harness-engineering-101/), [Anthropic Messages API 문서](https://docs.anthropic.com/en/api/messages)

하니스(harness)는 원래 말에 채우는 마구(馬具)를 뜻한다. AI 쪽에서는 모델을 둘러싼 프로그램을 가리킨다. 사용자 입력을 받고, 모델에 보낼 요청을 짜고, 모델이 부탁한 도구를 실제로 실행하고, 결과를 다시 넣어 준다. Claude Code[^claude-code]나 Cursor 같은 코딩 에이전트에서 모델 말고 나머지가 다 하니스다.

저자의 비유는 단순하다. 모델은 뇌, 하니스는 몸이다. 뇌는 글자를 받아 글자를 낼 뿐이다. 파일을 읽거나 명령을 돌리는 것은 언제나 몸이다. 그리고 뇌와 몸 사이로는 JSON 배열 하나만 오간다.

| | 채팅 한 번 | 에이전트 |
|---|---|---|
| 모델 호출 | 질문 하나에 한 번 | 일이 끝날 때까지 수십 번 |
| 배열에 들어가는 것 | 사용자 말, 모델 답 | 거기에 도구 호출과 도구 결과 |
| 멈추는 조건 | 답이 오면 | 모델이 더는 도구를 부르지 않을 때(`end_turn`) |
| 누가 실행하나 | 실행할 것 없음 | 하니스가 실행하고 결과를 배열에 붙임 |

코드로 보면 차이가 몇 줄이다. 아래는 원문 장난감 하니스(v1, v3)를 참고해 옮긴 이가 줄여 쓴 것이다.

```python
# 보통 채팅: 한 번 보내고 끝. 배열에는 사람 말과 모델 답만 쌓인다.
messages.append({"role": "user", "content": question})
reply = call_llm(messages)                      # 왕복 1번. 서버는 아무것도 기억하지 않는다
messages.append({"role": "assistant", "content": reply["content"]})

# 에이전트: 모델이 도구를 그만 부를 때까지 돈다.
for _ in range(MAX_ROUNDS):                     # 상한이 없으면 같은 실패를 계속 반복할 수 있다
    reply = call_llm(messages, tools=TOOLS)     # 매 왕복마다 지금까지의 배열 전체를 다시 보낸다
    messages.append({"role": "assistant", "content": reply["content"]})
    if reply["stop_reason"] != "tool_use":      # 끝났다고 하면 사용자에게 돌려준다
        break
    results = [{"type": "tool_result", "tool_use_id": b["id"],
                "content": execute_tool(b["name"], b["input"])}   # 실행은 하니스가 한다
               for b in reply["content"] if b["type"] == "tool_use"]
    messages.append({"role": "user", "content": results})        # 결과는 사용자 자리로 돌아간다
```

"고쳐 줘" 한마디가 이 루프를 40번 돌 수도 있다. 사용자에게는 답 하나지만 배열은 40번 왕복했다. 책의 나머지는 이 루프가 길어지고 비싸지고 엉뚱한 짓을 할 때 붙이는 땜질 이야기다.

## 1부 통신선: 마법은 없다

### 1장 그냥 JSON 배열이다

가장 중요한 문장부터 보자. API는 상태가 없다(stateless). 서버는 호출과 호출 사이에 아무것도 기억하지 않는다. 대화가 이어지는 듯 보여도 실은 내 프로그램이 배열을 들고 있다가 매번 통째로 다시 보낼 뿐이다.

이것을 알고 나면 여러 말이 쉬워진다. 대화 기억은 리스트 하나다. 모델이 잊었다는 것은 배열에서 빠졌다는 뜻이다. 컨텍스트 창(context window)은 배열의 최대 크기다. `/clear`는 `messages = []`이고 세션 재개는 파일을 읽는 일이다.

배열 안에는 화자가 있다. `system`은 개발자가 모델에 주는 지시, `user`는 사람, `assistant`는 모델의 지난 답이다. 내용은 문자열이 아니라 타입이 붙은 블록 목록이다. 글, 이미지, 도구 호출, 생각이 다 블록이다. Anthropic과 OpenAI의 형식은 대체로 표기만 다르다. 시스템 프롬프트를 어디에 두느냐, 도구 결과를 어떤 역할로 보내느냐 정도다. 그래서 저자는 어느 회사 모델을 쓸지는 하니스에서 얕은 결정이라고 본다.

### 2장 뇌: 다음 토큰을 내는 블랙박스

모델은 무엇을 하나? 토큰 열을 받아 다음 토큰 하나하나의 확률을 낸다. 그게 전부다. 고르고 붙이고 다시 돌리는 일은 서빙 쪽 코드가 한다. 온도(temperature)를 요청마다 바꿀 수 있는 것이 그 증거다.

저자는 학습 세 단계로 모델의 버릇을 설명한다.

| 단계 | 얻은 것 | 하니스 쪽에서 알아 둘 점 |
|---|---|---|
| 사전학습(pre-training) | 지식, 패턴 완성 | 환각(hallucination)은 그럴듯한 글을 내도록 배운 결과다. 프롬프트로 없앨 수 없고 사실을 넣어 줘서 피해 간다 |
| 사후학습(post-training) | 지시 따르기, 역할 존중 | 시스템 프롬프트가 힘을 갖는 것은 그렇게 학습됐기 때문이다. API가 강제하는 것이 아니다 |
| 과제 강화학습(RL) | 도구 호출, 생각, 스스로 고치기 | 도구 호출 JSON이 깔끔한 것도, 오류를 보면 다른 길을 찾는 것도 학습된 기술이다 |

이미지도 결국 토큰이 된다. PDF를 읽는다는 것도 대개 하니스나 API 계층이 글자를 뽑고 쪽을 그림으로 바꿔 넣는 일이다. 저자는 인상적인 기능을 볼 때마다 그중 뇌가 한 몫과 몸이 한 몫을 나눠 보라고 권한다. 대개 몸 쪽이 생각보다 크다.

### 3장 도구: 함수에 이어 붙인 JSON

모델은 아무것도 실행하지 않는다. 부탁할 뿐이다. 도구는 요청에 넣는 스키마, 모델 답에 오는 `tool_use` 블록, 다음 메시지에 붙이는 `tool_result` 블록, 이 JSON 세 조각으로 이뤄진다. 하니스 쪽에서 보면 이름을 함수에 잇는 딕셔너리 조회다.

작지만 중요한 규칙도 있다. 도구가 실패하면 예외를 던지지 말고 오류 문자열을 결과로 돌려준다. 모델이 길을 바꾸려면 그 오류만큼 좋은 신호가 없다.

사람도 도구가 될 수 있다. 막혔을 때 사용자에게 묻는 `ask_user_question` 도구를 두면 된다. 구조화된 출력(structured output)도 같은 기술이다. 원하는 결과 형식을 스키마로 가진 도구를 하나 만들고 그걸 부르게 하면 인자가 곧 답이 된다. 웹 검색처럼 공급자 서버에서 도는 서버 쪽 도구는 편하다. 다만 거기에는 내 권한 검사가 끼어들 수 없다는 걸 기억해 두라고 한다.

### 4장 에이전트 루프

위 코드가 이 장의 전부다. 모델이 도구를 부르면 실행해서 붙이고 다시 부른다. 그만 부르면 멈춘다. `stop_reason` 값 하나로 갈라진다.

저자는 실패를 연료로 쓰는 버릇을 강조한다. 흔한 실수로는 도구 오류에 루프가 죽는 것, 오류를 "실패했음"처럼 뭉개는 것, 하니스가 몰래 고쳐서 다시 해 보는 것이 있다. 마지막이 가장 나쁘다. 몰래 고치면 모델이 아는 세상과 실제 세상이 어긋난다. 저자는 MI Copilot에서 파일 쓰기가 실패했는데 모델이 그 사실을 모른 채 계속 편집해서 파일이 망가진 경험을 든다. 대신 돌 수 있는 횟수에는 상한(예: 50회)을 둔다.

ReAct[^react]는 이 루프의 조상이다. 도구 호출을 학습하지 못한 모델에게 "생각, 행동, 관찰" 형식으로 답하게 하고 정규식으로 잘라 썼다. 지금의 도구 호출에서는 그 순환이 프롬프트에서 가중치 안으로 옮겨 갔다.

### 5장 캐싱: 순서가 돈이다

루프의 값을 계산해 보자. 배열이 1만 토큰에서 시작해 한 바퀴에 2천 토큰씩 늘고 40바퀴를 돈다. 그러면 입력 토큰 합계가 약 196만이다. 요청 하나에 그렇다. 매번 전체를 다시 보내니 비용이 대화 길이의 제곱으로 는다.

땜질은 프롬프트 캐싱(prompt caching)이다. 공급자는 이미 처리한 앞부분을 저장해 두었다가 다음 요청에서 바이트 단위로 앞에서부터 같은 데까지는 다시 계산하지 않는다. 그 부분은 값의 10% 정도만 받는다. 에이전트 루프는 뒤에 덧붙이기만 하니 원래 캐시에 잘 맞는다.

규칙은 간단하다. 덧붙이기는 싸고 위쪽을 고치면 그 아래 전부를 다시 낸다. 캐시를 깨는 흔한 실수는 이렇다.

- 시스템 프롬프트에 초 단위 현재 시각을 넣는다
- 도구 목록 순서가 실행마다 바뀐다
- 세션 중간에 MCP 서버를 켜고 끄며 도구 목록을 바꾼다(저자가 WSO2 BI Copilot에서 실제로 겪었다)
- 위쪽의 '현재 상태' 칸을 매 바퀴 고쳐 쓴다
- 공간을 아끼려고 중간 메시지를 자꾸 지운다. 줄였는데 더 비싸진다

Anthropic은 `cache_control` 표시를 최대 네 군데까지 직접 다는 방식이고 OpenAI는 자동이다. 어느 쪽이든 응답의 `cache_read_input_tokens`가 두 번째 바퀴부터 입력 대부분을 차지해야 정상이다. 캐시가 깨져도 오류는 나지 않고 청구서에만 찍히니 저자는 이 숫자를 생체 신호처럼 본다. 그래서 릴리스 전마다 실제 API로 캐시 검사를 돌린다고 한다.

## 2부 오래 달리기: 압박받는 배열

### 6장 컨텍스트는 자루가 아니라 예산이다

배열이 컨텍스트 창을 꽉 채우면 요청이 거절된다. 더 큰 문제는 그 전에 온다. 배열이 길어지면 모델이 중간 내용을 놓치고 앞쪽 지시를 덜 따른다. 이른바 컨텍스트 부패(context rot)다. 20만 토큰 창이라도 믿고 쓸 수 있는 주의력은 그보다 훨씬 적다.

예산을 가장 많이 먹는 것은 대화보다 도구 결과다. 그래서 싸고 확실한 처방도 거기 있다.

- 도구 출력을 처음부터 자른다. 잘랐다는 사실은 꼭 알린다
- 파일 전체 대신 줄 범위를 읽게 한다
- 필요할지 모르는 것을 미리 밀어 넣지 말고 필요할 때 모델이 가져가게 한다

저자는 MI Copilot에서 긴 결과를 말없이 잘랐다가 모델이 크게 헷갈린 경험을 든다. 지금은 자르고, 전체를 파일로 남기고, 그 경로를 알려 준다.

그래도 차면 압축(compaction)을 한다. 오래된 부분을 요약으로 바꾸고 최근 몇 메시지만 원문 그대로 남긴다. 요약은 결론만 남기고 왜 다른 길을 버렸는지는 잃는다. 그래서 무엇을 남길지(현재 상태, 결정, 건드린 파일, 다음 단계)를 요약 프롬프트에 분명히 적어야 한다. 압축은 캐시를 한 번 깨지만 드물게 크게 하는 편이 자주 조금씩 자르는 것보다 싸다.

세션을 넘는 기억은 파일에 둔다. `CLAUDE.md` 같은 기억 파일(memory file)이다. 배열은 램, 파일은 디스크다. 기억 파일도 예산이니 짧은 목차만 넣고 자세한 문서는 필요할 때 읽게 한다.

### 7장 서브에이전트: 컨텍스트를 갈라 쓴다

"재시도 로직이 어디 있지?"에 답하려면 파일 열다섯 개를 읽어야 할 수 있다. 답은 한 문장이다. 그 탐색 기록 5만 토큰이 주 루프 배열에 남으면 아깝다.

서브에이전트(subagent)는 빈 배열로 같은 루프를 한 번 더 돌린다. 마지막 답만 도구 결과로 돌아오고 배열은 버려진다. 저자는 서브에이전트를 조직도가 아니라 컨텍스트 도구로 보라고 한다. 토큰 비용은 그대로다. 대신 주 루프의 주의력을 아낀다.

정의에서 세 가지가 나온다. 자식은 아무것도 모르니 과제를 혼자 읽어도 알 수 있게 써야 한다. 부모는 보고서만 보니 근거(파일 경로, 줄 번호)를 요구해야 한다. 결과는 도구 결과로 돌아오니 실패도 크게 알려야 한다.

중간 분량은 많고 결론은 짧은 일을 맡긴다. 탐색, 테스트 돌려 실패 요약하기, 문서 조사, 서로 독립인 병렬 작업이 그렇다. 세션의 판단이 쌓여야 하는 일이나 grep 한 번이면 끝나는 일은 맡기지 않는다. 저자는 탐색만 하라고 보낸 서브에이전트가 파일을 고친 일을 겪었다. 과제에 "읽기만"이라고 쓰지도 않고 쓰기 도구까지 쥐여 준 탓이다. 과제는 슬랙 접근권이 없는 외주 작업자에게 쓰는 티켓처럼 쓰라고 한다.

### 8장 달리는 루프 조종하기

사람이 작업 중에 파일을 고친다. 8만 토큰 전에 말한 규칙이 흐려진다. 열두 단계 중 일곱째에서 할 일을 잊는다. 사람이 매 턴 바로잡는 채팅에서는 문제가 안 된다. 혼자 40바퀴를 도는 에이전트에서는 이런 일이 쌓인다.

땜질로는 하니스가 직접 배열에 글을 넣는다. 사용자 자리 맨 아래에 `<system-reminder>` 같은 표시를 붙여 사람 말과 하니스 말을 가른다. 왜 시스템 프롬프트가 아니라 아래쪽일까? 위를 고치면 캐시가 깨진다. 모델은 최근 토큰을 더 잘 본다. 그리고 끼어들 순간이 마침 다음 메시지를 만들 때다.

저자는 큐를 권한다. 파일 감시기, 권한 시스템, 기억 모듈이 할 말을 큐에 넣으면 큐는 정해진 순서로 다음 메시지에 비워진다. 그래야 모델이 무엇을 왜 봤는지 추적할 수 있다. 몸에서 일어난 사건이 배열 속 문장이 된다. 사건 중심의 하니스와 글자만 아는 뇌의 접점이 바로 여기다.

가장 인상적인 예는 할 일 목록이다. 모델이 `todo_write`로 목록을 고치면 하니스가 그 목록을 다시 리마인더로 넣어 준다. 계획이 바래 가는 기억에서 늘 눈앞에 있는 입력이 된다. 다만 너무 자주 넣으면 소음이 된다. 넣는 시점은 시간표보다 사건에 맞추고 매번 넣어야 하는 말이라면 시스템 프롬프트로 옮긴다.

### 9장 백그라운드 작업과 시간

20분짜리 빌드를 돌리면 어떻게 하나? 루프를 막아 두거나, 시간 초과로 끊거나, 모델이 `sleep 30`을 반복하며 확인하게 된다. 마지막이 가장 흔하고 가장 비싸다. 비싼 뇌가 주방 타이머 일을 하는 셈이다.

땜질은 일을 턴 밖으로 내보내는 데서 시작한다. 명령을 백그라운드로 띄우면 작업 ID부터 바로 돌려준다. 작업이 끝나면 8장의 큐로 "b1 끝남"을 알린다. 반대로 사건이 턴을 시작하게도 만든다. 조건 감시, 정해진 시각, 모델이 스스로 거는 알람이 모두 같은 '뇌 깨우기'에 방아쇠만 다르다. 이제 사용자 입력은 여러 사건 중 하나가 된다.

규칙도 따른다. 깨울 때마다 돈이 드니 빈도를 대상이 바뀌는 속도에 맞춘다. 알림은 사실이어야 한다. 사용자는 돌고 있는 모든 일을 보고 끌 수 있어야 한다. 몇 시간 뒤 깨어날 약속은 디스크에 있어야 프로세스가 재시작돼도 살아남는다.

## 3부 생태계: 이미 아는 것에 이름 붙이기

### 10장 모든 프레임워크는 1장을 감싼 포장지다

LangChain[^langchain], LangGraph, CrewAI, 각종 에이전트 SDK의 낯선 낱말들은 앞의 아홉 장에서 이미 만든 것들이다. 저자의 해독표를 줄이면 이렇다.

| 프레임워크 말 | 실체 |
|---|---|
| 메모리, 스레드 | 배열, 그리고 디스크에 저장한 배열 |
| 도구, 출력 파서 | 스키마와 디스패치 표, 강제된 도구 호출 |
| 에이전트, 실행기 | `stop_reason`을 보는 while 루프 |
| 멀티 에이전트, 핸드오프 | 빈 배열로 부른 같은 루프 |
| 미들웨어, 콜백 | 배열에 덧붙이는 지점의 코드 |
| 체인, 그래프 | 함수 호출과 if 같은 평범한 제어 흐름 |

프레임워크가 커 보이는 것은 역사 때문이다. GPT-3.5 시절에는 모델이 약해서 하니스가 정규식 파싱, 퓨샷 템플릿, 작은 호출 사슬을 다 해야 했다. 그 뒤 강화학습이 어려운 부분을 모델 안으로 옮겼다. 그런데 어휘는 남았다.

쓸 만한 값도 있다. 여러 공급자 형식 맞추기, 재시도 같은 배관, 추적 도구 연동, 팀원이 아는 공통어다. 대가는 배열과의 거리다. 저자의 기준으로는 작고 투명한 층은 쓰고 배열을 차지하려는 층은 의심해야 한다. 낯선 프레임워크를 10분 만에 읽는 질문 네 개도 준다. 루프는 어디 있나? 배열은 누가 만들고 나는 그걸 보고 고칠 수 있나? 조립 단위는 무엇인가? 이 책에 없는 무엇을 해 주나?

### 11장 몸 넓히기: MCP, 스킬, 지연 로딩, 훅

능력을 하니스 코드에 하나하나 박으면 하니스 작성자가 병목이 된다. 반대로 도구 백 개를 꽂으면 스키마만으로 예산이 바닥난다. 생태계가 내놓은 답은 넷이다.

| 더하고 싶은 것 | 수단 | 핵심 |
|---|---|---|
| 다른 시스템과 말하는 능력 | MCP[^mcp] 서버 | 3장의 디스패치 표에 네트워크가 한 번 끼었을 뿐이다 |
| 일하는 절차 | 스킬(skill) | 이름과 한 줄 설명만 넣고 본문은 필요할 때 넣는다 |
| 많은 도구를 작은 배열로 | 지연 로딩(deferred loading) | 이름만 두고 `tool_search`로 찾을 때 스키마를 붙인다 |
| 반드시 지켜질 보장 | 훅(hook) | 루프 사건에 묶인 스크립트. 관찰, 보탬, 거부 |

가운데 둘은 점진적 공개(progressive disclosure)라는 원리를 함께 쓴다. 짧은 목차는 배열에 두고 자세한 것은 밖에 두었다가 필요할 때 가져온다. 한 번 붙인 스키마는 빼면 캐시가 깨지니 세션 끝까지 그대로 둔다.

훅은 성격이 다르다. 다른 셋은 뇌가 고를 수 있는 일을 늘린다. 훅은 뇌가 무엇을 고르든 몸이 하는 일을 늘린다. "편집 뒤 늘 포매터를 돌려라"를 프롬프트에 쓰면 저자 표현으로 97%쯤 지켜진다. 훅으로 걸면 100%다. MCP 서버는 남이 짠 손을 내 몸에 다는 일이니 보안 결정이라고도 짚는다.

### 12장 배열 디버깅하기

에이전트가 이상하게 굴면 코드를 읽고 싶어진다. 그런데 모델이 본 것은 마지막에 조립된 요청뿐이다. 시스템 프롬프트, 기억 파일, 스킬 목록, MCP 스키마, 리마인더, 압축 요약이 다 그 요청을 만든다. 내가 머릿속에 그린 배열과 실제로 나간 바이트가 다를 수 있다.

볼 수 없는 프롬프트는 고칠 수 없다. 저자가 세운 규칙이다. 그러니 실제 요청부터 본다. 방법은 셋이다.

- 캡처: HTTP 호출 직전에 요청 본문 전체와 응답(`usage` 포함)을 파일로 남긴다. 그 뒤에 요청을 바꾸는 층이 있으면 캡처가 틀린다
- 재생: API에 상태가 없으니 캡처한 요청이 곧 완전한 재현 사례다. 한 곳만 고쳐 다시 보내며 가설을 시험한다
- 고정 테스트: API만 가짜로 두고 조립된 배열의 존재, 위치, 바이트를 단언한다. 캐시가 조용히 깨지는 것을 테스트가 먼저 잡는다

저자 경험으로는 모델 탓을 하고 들여다보면 원인이 배열에 있을 때가 많다. 넣은 적이 없거나, 망가졌거나, 엉뚱한 자리에 있었다. 서브에이전트 기록과 리마인더 큐 기록도 따로 남겨야 한다. LangSmith 같은 추적 화면은 이 캡처를 보기 좋게 그려 주는 도구다.

## 4부 신뢰, 도메인, 데이터

### 13장 반사 신경과 안전장치

루프는 언젠가 사고를 친다. 모델은 확률 기계라 가끔 틀린다. 게다가 배열에는 사용자가 쓰지 않은 글이 가득하다. 웹 페이지, 파일 내용, MCP 도구 설명 어디에든 "이전 지시를 무시하고…" 같은 문장이 숨어 있을 수 있다. 프롬프트 주입(prompt injection)이다. 뇌가 바로 틀리는 쪽이니 안전은 몸에 있어야 한다.

저자는 방어를 싸고 확실한 것부터 다섯 겹으로 쌓는다.

| 층 | 내용 | 확실성 |
|---|---|---|
| 0 | 손을 주지 않는다. 필요 없는 도구는 아예 없다 | 확률 1 |
| 1 | 규칙 코드. 보호 경로, 허용·금지 목록, 읽지 않은 파일 편집 거부 | 확률 1, 비용 거의 0 |
| 2 | 사람에게 묻는다. 권한 모드, 기억되는 허락, 계획 단위 승인 | 사람의 주의력에 달림 |
| 3 | 작은 모델이 큰 모델을 심사한다 | 증거일 뿐 권위가 아니다 |
| 4 | 피해 반경을 줄인다. git으로 되돌리기, 샌드박스, 비밀값 최소화 | 다른 방어가 다 뚫려도 버팀 |

규칙이 거절할 때는 이유를 담아 오류로 돌려준다. 그러면 거절이 조종도 겸한다. 2층의 적은 승인 피로다. 한 시간에 마흔 번 물으면 사람은 읽지 않고 예를 누른다. 3층 분류기도 언어 모델이라 환각도 하고 주입도 당한다. 그래서 차단하려면 실제로 있는 규칙을 대게 하고 허락하려면 사용자가 실제로 한 말을 인용하게 한다. 애매하면 사람에게 넘긴다.

시스템 프롬프트는 접근 제어가 아니다. "절대 지우지 마라"는 확률 기계 속 선호일 뿐이다. 확률 1로 지켜져야 하는 것은 프롬프트에 둘 수 없다.

### 14장 사례: 코딩 에이전트

에이전트는 왜 코딩에서 먼저 잘됐을까? 코딩에서는 세상이 전부 글자다. 컴파일러와 테스트가 공짜로 정직하게 되받아친다. git으로 실수를 되돌릴 수도 있다. 다른 분야에 에이전트를 들일 때도 이 세 질문으로 남은 하니스 작업량을 가늠할 수 있다.

코딩 하니스는 기관 넷을 덧붙인다. 편집 도구는 정확히 일치하는 원문 조각이 있어야만 바꿔 준다. 빠른 검색은 파일을 통째로 쏟지 않는다. LSP[^lsp] 진단은 편집 직후 새로 생긴 오류만 알려 준다. 되돌리기와 격리는 git이 맡는다.

반론도 공정하게 다룬다. "bash 하나면 된다"는 쪽이다. 모델은 유닉스 도구 사용 기록을 산더미처럼 보고 배웠다. 셸은 어떤 도구 목록도 예상 못 한 일을 받아 준다. 하니스 장치가 모델 능력 안으로 녹아든 일도 이미 두 번 있었다. 저자는 이 말이 반은 맞다고 본다. 그래도 지금은 몸이 사는 것이 있다. `sed -i`가 든 문자열 명령은 권한 검사가 들여다볼 수 없다. 셸은 편집 뒤 진단을 먼저 알려 주지 않는다. 약한 모델일수록 구조가 더 필요하다. 저자는 One Code[^one-code]에서 일부러 함정을 심은 프로젝트로 싼 모델들을 시험한다. 그러면 읽지 않은 파일을 고치고, 검색이 비면 원인을 지어내고, 서브에이전트가 과제를 벗어난다. 그래서 저자는 둘 다 싣는다. 흔한 길에는 구조화된 도구, 나머지에는 터미널, 그리고 둘 다에 안전장치를 둔다. 고르는 일은 모델에게 맡긴다.

### 15장 RAG는 처음부터 하니스 패턴이었다

검색 증강 생성(retrieval-augmented generation, RAG)의 갈래는 많다. 단순 RAG, 하이브리드, 재순위화, 그래프, 교정형, 에이전트형. 저자 눈에 RAG는 배열에 무엇을 넣을지 정하는 일이다. 갈래마다 어떤 글을 어떻게 고르느냐만 다르다.

고전 RAG는 하니스가 먼저 찾아서 붙이는 밀어 넣기(push)다. GPT-3.5 시절 챗봇에 맞춘 방식으로, 그때 모델은 한 번밖에 답할 수 없었다. 임베딩, 청킹, 벡터 DB는 진짜 공학이지만 검색 색인 공학이다. 모델이나 루프는 건드리지 않는다. 임베딩 검색은 의미로 하는 grep이라고 기억하면 된다.

진짜 갈림길은 밀어 넣기와 끌어오기(pull)다. 끌어오기에서는 검색을 도구로 준다. 모델이 생각하면서 찾고 빗나가면 다시 찾는다. 여러 단계를 거쳐야 하는 질문은 미리 찾아 줄 수 없으니 끌어오기가 자연스럽다. 밀어 넣기는 싸고 빠르다. 한 단계 질문이 쏟아지는 고객 지원 챗봇이라면 여전히 맞는 답이다. 둘은 섞인다. 코딩 에이전트에서 기억 파일은 밀어 넣기이고 grep은 끌어오기다. 찾는 일이 길어지면 서브에이전트에 맡긴다. '딥 리서치' 제품들이 대략 이 모양이다.

## 에필로그와 부록

에필로그는 `harness.py` 298줄을 한 덩어리씩 짚는다. 배열, 루프, 디스패치 표, 리마인더 큐, 권한 게이트다. 저자는 이 뼈대가 자신이 만든 세 제품 밑에 다 깔려 있다고 말한다. 할 일 목록은 리마인더 큐를 부르는 네 줄이고 사용자에게 묻기는 `input()` 한 줄이다. 권한 게이트는 디스패치보다 먼저, 모델이 손댈 수 없는 코드에서 돈다. 그 두 호출의 순서가 곧 안전 설계다. 연습 문제로는 캐시를 일부러 깨 보기, 압축 구현, 요청 재생기, 두 번째 API 형식, 병렬 서브에이전트, 진짜 샌드박스에서 자기 에이전트 공격해 보기를 낸다.

부록 넷은 필요할 때 읽는 고급 주제다.

- A. 하니스 하나, 뇌 여럿: 일마다 감당할 수 있는 가장 싼 모델을 배정한다. 기준은 난이도보다 틀렸을 때의 결과다. 서브에이전트가 쓴 보고서를 부모가 그대로 믿는다면 그 서브에이전트는 싼 모델에 맡기지 않는다. 약한 모델에는 더 친절한 프롬프트와 더 좁은 도구를 준다.
- B. 워크트리와 격리: 서브에이전트는 주의력을 격리할 뿐 파일은 공유한다. 쓰는 에이전트를 나란히 돌리려면 git 워크트리로 디렉터리와 브랜치를 따로 준다. 다만 `node_modules`, DB, 포트 같은 실행 환경은 여전히 공유된다.
- C. 모드와 플랜 모드: 모드는 뇌의 상태가 아니라 몸, 곧 게이트의 상태다. 플랜 모드에서는 읽기만 허락하고 계획을 한 번 승인받은 뒤 실행한다. 사람은 키 입력 마흔 개보다 계획 하나를 더 잘 판단한다.
- D. 재시도·속도 제한·스트리밍: API에 상태가 없으니 재시도는 안전하다. 속도 제한은 요청 수 대신 토큰으로 잰다. 스트리밍 실패는 답 중간에 끊기는 실패다.

## 정리

저자는 에이전트를 둘러싼 용어 홍수를 두 질문으로 줄인다. 무엇이 배열에 들어가는가? 모델의 손을 무엇이 지키는가? 프레임워크, MCP, 스킬, RAG, 멀티 에이전트 모두 이 둘 중 하나로 들어간다.

나는 이 책의 가장 쓸모 있는 대목이 5장과 12장이라고 본다. 둘 다 '보이지 않는 실패'를 다룬다. 캐시가 깨져도 오류는 나지 않는다. 모델이 지시를 무시하는 것처럼 보여도 실은 지시가 배열에 없었을 수 있다. 둘 다 실제로 나간 요청을 보기 전에는 알 수 없다. 에이전트를 만들거나 쓰는 사람이 오늘 당장 할 수 있는 일은 요청 캡처 세 줄과 `cache_read_input_tokens` 출력 한 줄이다.

> 해설 — 걸러 볼 점이 몇 가지 있다. 첫째, Claude Code의 내부 동작(리마인더, 파일 추적, 압축 프롬프트 등)에 관한 설명은 저자가 관찰하고 One Code에서 재현한 것이다. 공식 문서로 다 확인된 사양은 아니다. 둘째, "프롬프트로는 97%, 훅으로는 100%" 같은 수치는 설명용 예시로 보이고 측정값은 아니다. 또 예제 코드는 Anthropic API를 기본으로 하고 모델 이름(claude-sonnet-5, gpt-5.2 등)은 집필 시점 기준이다. 끝으로 저자도 밝히듯 장마다 결론을 먼저 두도록 고치고 영어를 다듬는 데 Claude Code와 One Code를 썼다. 초고는 저자가 직접 썼다.

[^claude-code]: Claude Code — Anthropic이 만든 터미널 기반 코딩 에이전트. 이 책에서는 리마인더·압축·권한 모드 같은 하니스 기법의 주된 참조 사례로 자주 나온다.
[^react]: ReAct — 2022년 논문 "Reasoning + Acting"에서 나온 프롬프트 방식. 이 책에서는 도구 호출 학습 이전에 같은 루프를 글 형식과 정규식으로 흉내 내던 조상으로 소개된다.
[^langchain]: LangChain — 2022년에 나온 LLM 앱 프레임워크. 이 책에서는 모델이 약하던 시절의 꼭 필요했던 요령을 호환성 때문에 지금도 품고 있는 예로 나온다.
[^mcp]: MCP(Model Context Protocol) — Anthropic이 2024년에 공개한 개방 규격. 에이전트가 다른 프로세스나 원격 서비스의 도구를 같은 방식으로 찾고 부르게 해 준다. 이 책에서는 3장의 디스패치 표가 네트워크로 늘어난 것으로 설명된다.
[^lsp]: LSP(Language Server Protocol) — 편집기가 언어별 분석기에서 진단·정의로 이동·참조 찾기를 받아 오는 규격. 이 책에서는 편집 직후 새 오류를 모델에게 알려 주는 코딩 하니스의 신경계로 나온다.
[^one-code]: One Code — 저자가 Pi(아르민 로나허 등이 만든 오픈소스 에이전트 하니스, pi.dev) 위에 Claude Code의 동작을 처음부터 다시 만든 오픈소스 코딩 에이전트. 이 책에서는 각 기법이 실제 규모에서 어떻게 생기는지 보여 주는 사례로 나온다.
