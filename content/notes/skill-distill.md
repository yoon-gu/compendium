## 한눈에 보기

Claude Code로 어떤 작업을 깔끔하게 끝냈다고 하자. 같은 일을 내 GPU에서 도는 오픈 웨이트 모델에게도 시킬 수 있을까? 보통은 요령을 사람이 정리해 프롬프트로 넘긴다. 그런데 그 글이 약한 모델에게도 통할지는 돌려 보기 전엔 모른다. skill-distill은 실제로 돌려 보며 그 글을 고치는 루프다.

| 항목 | 내용 |
|---|---|
| 무엇인가 | 선생 에이전트(Claude Code·Codex)가 따르는 스킬 한 장과 기록 관리 스크립트 |
| 입력 | 잘 끝난 기준 세션 하나, 학생 하네스 + 모델(예: omp + DeepSeek-V4.1-Flash) |
| 루프 | 스킬을 쓰고 → 학생을 3번 돌리고 → 기준과 비교하고 → 처음 어긋난 곳을 고친다 |
| 멈춤 | 3번 모두 일치하면 끝. 최대 8회, 3회 연속 나아지지 않으면 중단 |
| 최종 판정 | 사용자가 기준과 학생 결과를 나란히 보고 pass/fail |
| 결과물 | 작업 1개·모델 1개·하네스 1개에 맞춘 SKILL.md |
| 아닌 것 | 범용 스킬 작성기도, 파인튜닝 도구도 아니다 |
| 조심할 점 | 학생이 승인 없이 셸 명령을 돌린다. 격리된 환경에서 쓰는 게 안전하다 |

## 먼저, 스킬과 '증류'란 무엇인가

참고: [Agent Skills 명세](https://agentskills.io/), [skill-distill SKILL.md](https://github.com/sybil-solutions/skill-distill/blob/main/skills/skill-distill/SKILL.md)

에이전트 스킬(agent skill)은 `SKILL.md` 한 장과 거기 딸린 스크립트·참고 문서를 묶은 폴더다. 에이전트는 평소엔 스킬의 이름과 한 줄 설명만 본다. 관련 있는 일이 오면 그때 본문을 읽고 따른다. Claude Code와 Codex가 같은 형식을 쓴다.

증류(distillation)는 원래 모델 학습에서 쓰는 말이다. 큰 선생 모델의 출력을 정답 삼아 작은 학생 모델의 가중치를 학습시킨다. skill-distill은 가중치를 건드리지 않는다. 선생이 아는 것을 학생이 읽을 문서인 `SKILL.md`로 옮긴다.

보통 하는 방식과 skill-distill의 방식을 파이썬 의사 코드로 비교해 보자. 실제 도구는 선생 에이전트가 따르는 SKILL.md와 `distill.py` 하위 명령으로 이루어져 있다. 아래는 그 흐름만 옮긴 것이다.

```python
# 보통 방식: 사람이 요령을 정리해 한 번 넘긴다
notes = summarize_by_hand(reference_session)   # 강한 모델에겐 당연한 단계가 빠지기 쉽다
skill = write_prompt(notes)
result = run(student, prompt, skill)           # 한 번 돌리고
print("되는 것 같다")                           # 학생의 "완료" 보고를 그대로 믿는다
# 학생이 서버를 포그라운드로 띄워 멈췄는지, 검증 없이 끝냈는지 모른다
```

```python
# skill-distill: 학생을 실제로 돌려 보며 스킬을 고친다
acceptance = observable_items(reference_result)   # 4-10개, 기준 결과로 먼저 통과 확인
skill = first_draft(reference_session)
for it in range(1, 9):                            # 최대 8회
    trials = [run(student, prompt, skill, fresh_copy(base)) for _ in range(3)]
    verdicts = [judge(t, reference_result, acceptance) for t in trials]
    if all(v.verdict == "match" for v in verdicts):
        break
    skill = fix_at(first_divergence(verdicts), skill)  # 뒤쪽 증상이 아니라 첫 분기점
    # 3회 연속 최고 점수가 안 오르면 중단
decision = ask_user(reference_result, best(trials))   # pass / fail은 사람이
```

보통 방식과 달리 skill-distill은 학생을 실제로 여러 번 돌려 본다. 그리고 "잘했다"의 기준을 학생의 말 대신 기준 결과에서 끌어낸다.

## 기존 스킬 개선 도구와 무엇이 다른가

스킬을 평가하고 고치는 루프 자체는 새롭지 않다. Anthropic의 skill-creator[^skillcreator]도, darwin-skill도 있다. 원문에 따르면 이 도구들은 같은 모델이 스킬을 쓰고 같은 모델이 그 스킬을 시험한다. skill-distill에서는 다른 하네스에서 도는 다른 모델이 시험대에 오른다. 정답으로 삼는 것도 이미 잘 끝난 세션 하나다. 테스트 세트를 따로 만들지 않는다.

| 항목 | skill-distill | skill-creator | darwin-skill | D-Skill (논문) |
|---|---|---|---|---|
| 스킬을 실행하는 쪽 | 사용자가 고른 학생 하네스·모델 | 같은 세션의 서브에이전트 | 같은 에이전트의 서브에이전트 | 학생 모델 |
| 비교 기준 | 기준 세션의 결과물 | 스킬 없이 돌린 결과나 이전 버전 | 9차원 루브릭 점수 | 선생·학생의 짝지은 실행 기록 |
| 최종 판정 | 사용자의 pass/fail | 사용자가 뷰어로 검토 | 사이클마다 사용자 확인 | 벤치마크 점수 |

선생과 학생을 나눈다는 점에서는 D-Skill 논문[^dskill]이 가장 가깝다. D-Skill은 고정된 실행 기록에서 오프라인으로 스킬을 뽑아 선생과 학생의 격차를 75-95% 줄였다고 보고한다. 다만 깊은 계산이나 인식처럼 학생에게 없는 기본 능력은 스킬로 채울 수 없다고도 밝힌다. skill-distill은 여러 과제의 기록 대신 사용자의 세션 하나를 기준으로 삼고 학생을 다시 돌려 가며 고친다. 대신 성능 수치는 아직 공개하지 않았다.

## 어떻게 돌아가나

선생이 따르는 SKILL.md는 0-9단계로 되어 있다. 크게 묶으면 다섯 덩어리다.

### 1. 기준을 먼저 못 박는다

학생은 기준 세션의 첫 사용자 메시지를 손대지 않은 채 그대로 받는다. 선생이 더 잘 다듬어 주면 안 된다. 같은 프롬프트로 같은 결과를 내야 비교가 된다. 시작 상태는 세션이 시작된 시점의 git 커밋이다. 빈 폴더에서 시작했다면 `empty`다. 커밋하지 않은 변경에서 시작했다면 버릴 브랜치에 먼저 커밋해 둔다. GPU 서버나 외부 API가 필요하면 시행마다 깨끗한 사본을 만드는 명령을 `--setup`으로 넘긴다.

본격적으로 들어가기 전에 학생이 살아 있는지부터 본다. "hello.txt를 만들고 DONE이라 답하라" 같은 1분짜리 일을 시킨다. 모델 ID가 틀렸거나 서버가 꺼져 있으면 스킬이 나빠서 실패한 것처럼 보이기 때문이다.

### 2. "기준만큼 좋다"를 글로 적는다

선생은 기준 결과가 왜 좋았는지를 `acceptance.md`에 4-10개 항목으로 적는다. 하나하나가 시행에서 확인할 수 있는 관찰이어야 한다. 예를 들면 "게임이 콘솔 오류 없이 시작한다", "README에 실행법이 있다" 같은 것이다. 그중 스크립트로 확인할 수 있는 것은 `checks.sh`로 만든다. 웹 앱이면 Playwright로 헤드리스 크로미움을 띄워 키를 누르고 클릭하고 스크린샷을 남긴다.

여기에 중요한 규칙이 하나 있다. 이 체크를 학생보다 기준 결과에 먼저 돌려야 한다. 기준 결과에서 실패하는 체크는 체크가 틀린 것이다.

### 3. 학생용 스킬을 쓴다

선생은 학생이 자기보다 약하다고 가정한다. 쓸 수 있는 컨텍스트가 짧고 글을 글자 그대로 따른다고 본다. 스킬은 그런 독자에 맞춰 아래 규칙대로 쓴다.

- 기준 세션이 실제로 일한 순서대로 단계에 번호를 매긴다. 막다른 길은 뺀다. 단계마다 성공하면 무엇이 보여야 하는지 적는다.
- 기준 세션이 내린 결정(구조, 라이브러리와 버전, 파일 배치)을 이유 한 마디와 함께 넘긴다. 상황이 조금 달라도 학생이 맞춰 갈 수 있게.
- 기준 세션과 학생이 빠졌던 함정을 "X 하지 마라, 왜냐하면 Y" 꼴로 모은다.
- 끝내기 전에 반드시 돌릴 검증 명령과 통과했을 때의 모습을 적는다. 오픈 모델은 확인 없이 성공을 보고하는 일이 잦다.
- 하네스 쪽 함정도 적는다. 오래 도는 서버를 포그라운드로 띄우면 도구 호출이 멈춘다. 백그라운드로 띄우고 끝나면 끈다.
- 학생이 같은 기계적 단계에서 계속 실수하면 문장을 늘리지 말고 `skill/scripts/`에 스크립트를 넣는다.
- 본문은 250줄 안팎으로 줄이고 긴 참고 자료는 `references/`로 뺀다.

스킬로 답을 넘겨주지 않는다. 이게 가장 중요한 제약이다. 스킬에 기준 세션의 완성 결과물이나 그걸 그대로 찍어 내는 스크립트를 넣으면 안 된다. 학생이 끝내 못 하는 부분에만 40줄 안팎의 짧은 코드 조각을 허용한다. 왜 필요했는지는 기록에 남긴다. 저자의 표현으로는 설치 프로그램이 아니라 학생이 일을 해낼 수 있게 하는 문서여야 한다.

### 4. 학생을 세 번 돌리고 판정한다

`distill.py trial`은 지금 스킬을 그 반복 번호로 얼려 둔다. 그리고 시작 상태를 새로 복제해 작업 폴더 셋을 만들고 tmux 창 셋에서 학생을 돌린다. 학생이 받는 것은 원래 프롬프트, 작업 폴더 안 `.skill/<이름>/`에 복사한 스킬, 그 스킬을 읽으라는 한 줄뿐이다. 시행 하나의 기본 제한 시간은 90분이다.

왜 세 번일까? 오픈 모델은 결과가 들쭉날쭉하다. 저자는 "One lucky run proves nothing."이라고 적었다. 한 번 운 좋게 된 것은 아무것도 증명하지 못한다는 말이다.

선생은 시행마다 실행 기록, 체크 로그, 스크린샷을 보고 `acceptance.md` 항목과 하나씩 맞춰 본다. 판정은 match·close·miss·broken 넷 중 하나와 0-10점이다. 기준은 엄격하다. 사용자에게 기준과 같다고 내밀 자신이 없으면 match가 아니라 close다. 그리고 학생이 처음 잘못된 길로 들어선 지점, 곧 첫 분기점(first divergence)을 기록한다. 뒤쪽 증상을 고치는 수정은 대개 실패해서다.

### 5. 실패 유형에 맞춰 고친다

| 무슨 일이 있었나 | 고치는 법 |
|---|---|
| 단계를 건너뛰거나 안 읽었다 | 그 단계를 앞으로 옮기고 짧게 줄이고, "멈추고 확인" 관문을 단다 |
| 단계를 잘못 읽었다 | 구체적으로 다시 쓰고 기대 결과 예시를 붙인다 |
| 하네스·도구를 잘못 썼다 | 스킬 맨 위에 정확한 명령을 적는다 |
| 알려 줘도 어려운 부분을 못 했다 | 짧은 코드 조각이나 스크립트를 준다 |
| 확인 없이 끝냈다 | 검증 단계를 필수로 하고 명령과 기대 출력을 적는다 |
| 긴 실행에서 맥락을 잃었다 | 문장을 줄이고 해당 단계에서만 읽을 `references/`로 나눈다 |
| 시행 환경이 깨졌다 | 스킬이 아니라 `--setup`이나 `checks.sh`를 고치고, 그 시행은 세지 않는다 |

다음 반복에서 점수가 떨어지면 수정을 더 얹지 말고 원인이 된 변경을 되돌린다. 3번 모두 match면 끝이다. 8회를 채우거나 3회 연속 최고 점수가 오르지 않아도 멈추고 학생이 아직 못 하는 것을 사용자에게 알린다. 원문은 이것도 쓸모 있는 결과라고 본다.

마지막으로 `distill.py report`가 기준과 학생 결과를 나란히 놓은 `report.html`을 만든다. 사용자가 pass를 주면 스킬이 `final/`로 복사된다. 끝에는 하네스·모델·반복 횟수·일치 수를 적은 "Tested with" 줄이 붙는다. fail이면 사용자가 한 말을 `acceptance.md`에 더하고 다시 고친다.

## 시범 실행에서 배운 것

판정 규칙에는 저자가 시범 실행에서 겪은 실패가 녹아 있다. 이 대목이 이 글에서 가장 흥미롭다.

시범 작업에서 학생 시행 셋은 기능을 다 갖췄다. 선생은 8.5-9점을 줬다. 그런데 사용자는 보자마자 품질이 근처에도 못 간다며 거절했다. 가까이서 보니 학생이 만든 월드는 기준보다 비어 있고 단조로웠다. 축소판으로 보면 같아 보였을 뿐이다. 원문은 SKILL.md의 다른 예시(텐트까지 걸어가 E 키를 누르는 동작)로 보아 게임 형태의 웹 결과물이었을 것으로 짐작한다.

그 뒤로 SKILL.md에 아래 내용이 들어갔다.

- 기준과 학생 화면을 2배 배율로, 같은 영역끼리 맞대어 본다. 기능이 같다고 품질이 같은 게 아니다.
- 학생은 화면을 잘 못 본다. 그래서 확인할 수 있는 숫자를 준다. "화면 칸 중 눈에 보이는 디테일이 있는 비율"을 출력하는 스크립트다. 이 지표는 기준 56%, 거절된 시행 33-40%로 둘을 갈랐다.

같은 시범에서 체크 실패 4건 중 3건은 체크 쪽 버그였다. 저장 데이터의 키를 짐작으로 적었거나 Escape 키가 일시정지 메뉴를 열어 버리는 식이었다. 그래서 "체크가 실패하면 체크부터 의심하라"는 규칙이 생겼다. 학생의 마지막 메시지도 증거가 아니다. 학생들은 "검증 완료, 테스트 모두 통과"라고 곧잘 말한다. 선생이 직접 돌려 보고 사용자처럼 걸어가서 키를 눌러 봐야 한다.

다만 원문이 짚듯 이 수치들은 SKILL.md 본문에만 있다. README는 완료 실행 기록이 `examples/`에 있다고 소개한다. 그런데 그 기록은 아직 저장소에 없다.

## 학생 하네스와 격리 범위

학생은 하네스별 셸 어댑터로 돈다. 하네스마다 상태가 다르다.

| 하네스 | 상태 | 전역 설정·스킬 끄기 |
|---|---|---|
| omp (oh-my-pi)[^omp] | 시험됨 | 끌 수 있음 |
| Codex CLI | 선생으로만 시험됨. 학생으로 쓰려면 제공자 설정 필요 | 끌 수 있음 |
| Claude Code | 작성됨. 오픈 모델은 Anthropic 호환 서버를 `ANTHROPIC_BASE_URL`로 지정 | 옵션 없음 |
| pi | 작성됨, 미시험 | 스킬만 끌 수 있음 |
| opencode | 작성됨, 미시험. 세션 로그 파서 없음 | 옵션 없음 |

원문은 먼저 Claude Code와 opencode 어댑터에 전역 설정을 끄는 옵션이 없다고 경고한다. 이 둘을 학생으로 쓰면 사용자의 전역 지침 파일이 학생에게 같이 들어간다. 그러면 스킬의 효과와 기존 설정의 효과가 섞인 채 판정된다.

실행 권한은 그보다 더 중요한 문제다. 어댑터는 학생을 무인으로 돌리려고 승인 절차를 끈다. Claude Code에는 `--dangerously-skip-permissions`, Codex에는 `--dangerously-bypass-approvals-and-sandbox`를 넘긴다. pi는 처음부터 권한 시스템이 없다. 시행마다 작업 폴더를 새로 복제하기는 한다. 하지만 그건 git 복제일 뿐 샌드박스가 아니다. 약한 모델이 승인 없이 내 계정 권한으로 셸 명령을 돌리는 구조다. 컨테이너나 가상 머신에서 돌리는 편이 안전하다.

개인정보는 설계에 반영돼 있다. 원본 세션 로그와 시행 기록이 쌓이는 `runs/`는 `.gitignore`에 들어 있다. 기준 요약을 만들 때 시스템 메시지, `AGENTS.md`·`CLAUDE.md` 지침, 환경 정보는 걷어 낸다. 마지막 전달 전에도 선생은 스킬에 비밀 값이나 사설 호스트 이름이 복사되지 않았는지 확인한다.

## 누구에게 맞나

프런티어 모델로 한 번 성공한 작업을 로컬 오픈 웨이트 모델에게 되풀이해 맡기려는 개발자에게 맞다. 반복 작업이 대표적이다. 비용이나 데이터 반출 문제로 로컬 모델을 써야 하는데 그 모델이 혼자서는 같은 품질을 못 낼 때다. 결과가 저장소 안 파일로 남고 스크립트로 검사할 수 있는 작업일수록 잘 맞는다.

여러 작업에 두루 쓸 범용 스킬이 필요하다면 맞지 않는다. 결과 스킬은 작업 1개·모델 1개·하네스 1개에 맞춰져 있다. 기준 세션이 없으면 시작도 못 한다. 버전마다 학생을 3번, 최대 8회까지 돌리니 선생 토큰과 학생 실행 시간도 꽤 든다. 2026년 11월 22일 기준 저장소의 커밋은 2개, 시험된 학생 하네스는 omp 하나다. 지금은 직접 써 보며 다듬을 사람에게 맞는 단계다.

설치는 저장소를 복제해 선생 에이전트의 스킬 폴더에 심볼릭 링크로 거는 것으로 끝난다. tmux, git, Python 3.10 이상, 그리고 모델에 연결된 학생 하네스가 있어야 한다. 잘 끝난 세션의 마지막에 "이 세션을 내 로컬 서버의 deepseek-v4.1-flash와 omp용 스킬로 증류해 줘"라고 영어로 요청하면 루프가 시작된다.

## 맺으며

읽고 나서 남는 것은 두 가지다.

하나는 "정답을 어디서 가져오나"에 대한 답이다. 에이전트 평가는 정답 세트 만들기가 늘 어렵다. skill-distill은 그걸 따로 만들지 않는다. 사용자가 이미 만족한 세션 하나가 정답이다. 선생은 그 결과에서 "왜 좋았나"를 관찰 가능한 항목으로 뽑는다. 그리고 그 체크가 기준 결과에서 먼저 통과하는지 확인한다. 정답을 만드는 대신 읽어 내는 셈이다.

다른 하나는 시범 실행의 실패담이다. 기능 목록이 다 맞았는데 사람은 한눈에 아니라고 했다. 선생 모델의 9점과 사람의 "근처에도 못 간다" 사이에는 간극이 있다. 결국 사람이 마지막 판정을 쥐어야 하는 이유도 이 간극이다. 저자는 그 간극을 숫자 하나(디테일 있는 칸의 비율)로 학생에게 보여 줬다. 약한 모델에게는 말보다 측정할 수 있는 신호가 낫다. 사람에게 일을 가르칠 때와 크게 다르지 않다.

[^skillcreator]: skill-creator — Anthropic이 공개한 스킬 작성·개선용 스킬. 같은 테스트 프롬프트를 스킬을 넣은 서브에이전트와 넣지 않은 서브에이전트로 함께 돌려 비교한다. 이 글에서는 같은 모델 안에서 스킬의 효과를 재는 도구로 skill-distill과 대비된다.
[^dskill]: D-Skill — 선생 에이전트의 실행 기록에서 학생이 쓸 스킬을 오프라인으로 뽑아내는 방법을 다룬 논문(arXiv 2610.28914). SpreadsheetBench-Verified, ALFWorld, 체스 퍼즐에서 선생·학생 격차를 줄였다고 보고한다. 이 글에서는 선생과 학생을 나눈다는 점에서 가장 가까운 선행 작업이다.
[^omp]: omp (oh-my-pi) — 터미널에서 도는 코딩 에이전트 하네스. 승인 없이 돌리는 `--auto-approve` 옵션에서도 사용자가 정한 deny 규칙과 보호 폴더는 지킨다. 이 글에서는 skill-distill이 실제로 시험한 유일한 학생 하네스다. README 예시에서는 로컬 서버의 DeepSeek-V4.1-Flash를 학생 모델로 붙였다.
