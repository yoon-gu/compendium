## 한눈에 보기

README 첫 줄의 물음은 이렇다. 프런티어 모델이 어떤 일을 잘 해냈다. 오픈 웨이트 모델도 같은 일을 해낼 수 있을까? 알맞은 지시만 받는다면.

skill-distill은 그 '알맞은 지시'를 돌려 보며 찾는 도구다. 사람이 요령을 정리해 넘기고 끝내지 않는다. 학생 모델을 실제로 돌리고, 결과를 기준과 맞대고, 틀린 데를 고친다.

| 항목 | 내용 |
|---|---|
| 무엇인가 | 선생 에이전트(Claude Code[^claudecode]·Codex[^codex])가 따르는 스킬 한 장과 기록 관리 스크립트 |
| 입력 | 잘 끝난 기준 세션 하나, 학생 = 하네스 + 모델(예: omp[^omp] + DeepSeek[^deepseek]-V4.1-Flash) |
| 루프 | 스킬을 쓰고 → 학생을 세 번 돌리고 → 기준과 비교하고 → 처음 어긋난 곳을 고친다 |
| 멈춤 | 세 번 모두 일치하면 끝. 최대 8회, 3회 연속 최고 점수가 그대로면 중단 |
| 최종 판정 | 사용자가 기준과 학생 결과를 나란히 보고 pass/fail |
| 결과물 | 저장소의 재사용 가능한 '운영 스킬'과, 작업 1개·모델 1개·하네스 1개에 맞춘 '생산된 스킬' |
| 아닌 것 | 기준 세션 없이 범용 스킬을 새로 쓰는 도구도, 파인튜닝 도구도 아니다 |

## 먼저, 스킬과 '증류'란 무엇인가

참고: [Agent Skills 명세](https://agentskills.io/), [skill-distill SKILL.md](https://github.com/sybil-solutions/skill-distill/blob/main/skills/skill-distill/SKILL.md)

에이전트 스킬(agent skill)이란 `SKILL.md` 한 장에 스크립트와 참고 문서를 곁들여 묶은 폴더다. 에이전트는 평소에 스킬의 이름과 한 줄 설명만 본다. 관련된 일이 들어오면 그제야 본문을 읽고 따른다. Claude Code와 Codex가 이 형식을 함께 쓴다.

증류(distillation)는 원래 모델 학습 용어다. 큰 선생 모델의 출력을 정답 삼아 작은 학생 모델의 가중치를 학습시킨다. skill-distill은 가중치에 손대는 대신 선생이 아는 것을 학생이 읽을 문서, 곧 `SKILL.md`로 옮겨 적는다.

흔히 하는 방식과 skill-distill의 방식을 파이썬 의사 코드로 나란히 놓아 보자. 실제 도구는 선생이 따르는 SKILL.md와 `distill.py` 하위 명령으로 되어 있다. 아래는 그 흐름만 파이썬으로 옮긴 것이다.

```python
# 흔한 방식: 사람이 요령을 정리해 한 번 넘긴다
notes = summarize_by_hand(reference_session)   # 강한 모델에겐 당연한 단계가 빠지기 쉽다
skill = write_prompt(notes)
result = run(student, prompt, skill)           # 한 번 돌리고
print("되는 것 같다")                           # 학생의 "다 됐습니다"를 그대로 믿는다
# 학생이 서버를 포그라운드로 띄워 멈췄는지, 검증 없이 끝냈는지 모른다
```

```python
# skill-distill: 학생을 실제로 돌려 보며 스킬을 고친다
acceptance = observable_items(reference_result)   # 4-10개, 기준 결과로 먼저 통과 확인
skill = first_draft(reference_session)
for it in range(1, 9):                            # 최대 8회
    trials = [run(student, prompt, skill, fresh_copy(base)) for _ in range(3)]
    verdicts = [judge(t, reference_result, acceptance) for t in trials]
    if all(v.verdict == "match" for v in verdicts):
        break
    skill = fix_at(first_divergence(verdicts), skill)  # 뒤쪽 증상이 아니라 첫 분기점
    # 3회 연속 최고 점수가 그대로면 중단
decision = ask_user(reference_result, best(trials))   # pass / fail은 사람이
```

skill-distill은 학생을 여러 번 실제로 돌린다. 잘했는지를 재는 잣대도 학생의 보고가 아니라 기준 결과에서 가져온다.

## README가 말하는 루프

잘 끝난 세션의 마지막에 선생에게 이 세션을 증류하라고 하면서 학생을 지목한다. 그러면 선생은 다섯 단계를 되풀이한다.

1. 세션을 읽고 학생용 스킬을 쓴다.
2. 시작 상태를 새로 복제한 폴더에서, 원래 프롬프트와 스킬만 주고 tmux[^tmux] 안에서 학생을 돌린다.
3. 학생이 만든 결과를 기준 세션이 만든 결과와 비교한다.
4. 학생이 처음 길을 잘못 든 곳을 찾아 스킬의 그 대목을 고친다.
5. 다시 돌린다. 버전마다 세 번씩, 학생이 기준과 맞을 때까지.

선생이 지키는 규칙도 README에 다섯 줄로 있다.

- 학생은 기준의 프롬프트를 글자 그대로, 깨끗한 시작 상태와 스킬만 받는다. 하네스가 허용하면 학생 쪽 전역 지침 파일과 스킬도 끈다.
- 스킬에 기준의 완성 결과물이나 그걸 써 주는 스크립트를 넣지 않는다. 단계·결정·함정·검증을 가르친다. 학생이 달리는 못 해내는 부분에만 짧은 코드 조각을 준다.
- 스킬 한 버전에 시행 세 번. 저자의 말로 "One lucky run proves nothing." 한 번 운 좋게 된 것은 아무것도 증명하지 못한다.
- 체크는 기준 결과에 먼저 돌린다. 기준에서 실패하는 체크는 고장 난 체크다.
- 원본 세션 로그는 git이 무시하는 `runs/`에만 둔다. 내 컴퓨터의 경로와 맥락이 들어 있어서다.

## 선생이 따르는 SKILL.md, 0-9단계

README가 지도라면 SKILL.md는 길 안내다. 선생에게 "너는 선생이다"라고 못 박고 초안에서 멈추지 말라고 한다. 학생에게 시켜 보고, 실제로 한 일을 보고, 틀린 데를 고치고, 또 시켜 보라는 것이다. 정해진 기계적 작업은 `distill.py`가 맡는다. 선생은 판단이 필요한 두 가지만 한다. 스킬에 무엇을 적을지, 그리고 시행 결과가 기준과 맞는지.

### 0-1. 입력을 정하고, 학생이 살아 있는지 본다

| 입력 | 기본값 |
|---|---|
| 학생 하네스 + 모델 | 사용자가 반드시 지목한다 |
| 기준 세션 | 지금 이 세션. `extract_session.py`로 읽기 좋은 요약을 만든다 |
| 작업 프롬프트 | 기준 세션의 첫 사용자 메시지 그대로. 다듬지 않는다 |
| 시작 상태 | 세션이 시작된 시점의 git 커밋, 빈 폴더였다면 `empty` |
| 기준 결과 위치 | 기준 세션의 작업 폴더 |

커밋하지 않은 변경에서 시작했다면 버릴 브랜치에 먼저 커밋해 둔다. GPU 서버나 외부 API처럼 저장소 밖 자원이 필요하면 시행마다 깨끗한 사본을 얻는 방법을 `--setup`으로 넘긴다. 지저분한 상태에서 시작한 시행은 판정할 수 없어서다.

본론에 앞서 1분짜리 일을 시켜 본다. "hello.txt를 만들고 DONE이라 답하라" 같은 것이다. 모델 ID가 틀렸거나 키가 없거나 서버가 꺼져 있으면 스킬이 나빠서 실패한 것처럼 보이기 때문이다.

### 2-3. 실행을 만들고, "기준만큼 좋다"를 글로 적는다

`distill.py init`이 실행 폴더를 만든다. 선생은 기준 요약(`reference.md`)을 끝까지 읽는다. 기준 결과도 직접 열어 보고 돌려 보고 중요한 파일을 읽는다. SKILL.md의 표현으로는 요약은 지도일 뿐 결과가 아니다.

그다음 기준 결과를 좋게 만든 것을 `acceptance.md`에 4-10개 적는다. 모두 시행에서 확인할 수 있는 관찰이어야 한다. "게임이 콘솔 오류 없이 시작한다", "텐트까지 걸어가 E를 누르면 사람이 밥을 먹고 거리 인원 수가 준다", "README에 실행법이 있다", "동시 1요청의 초당 토큰 수가 기준의 5% 안이다" 같은 것들이다. 방법보다 결과를 적고 각 항목을 어떻게 확인할지도 적는다.

스크립트로 확인할 수 있는 항목은 `checks.sh`로 만든다. 웹 앱이면 `capture_web.py`가 Playwright[^playwright]로 헤드리스 크로미움을 띄워 조작하고 스크린샷을 남긴다. 그리고 이 체크를 기준 결과에 먼저 돌린다. 통과하지 못하면 체크가 틀린 것이니 시행을 판정하기 전에 체크부터 고친다.

### 4. 학생용 스킬의 첫 버전을 쓴다

학생은 선생보다 약하다. 쓸 수 있는 컨텍스트도 대개 짧고 글을 글자 그대로 따른다. 그런 독자에게 맞춰 쓰라는 지침이 일곱 가지다.

- 순서가 중요하다. 기준이 실제로 중요한 일을 한 순서대로 단계 번호를 매긴다. 막다른 길은 뺀다. 단계마다 할 일, 정확한 명령이나 파일, 성공했을 때 보여야 할 것을 적는다. 기준이 헤맨 곳에는 "X가 보이면 Y를 하라"를 단다.
- 결정을 이유와 함께 넘긴다. 구조, 라이브러리와 버전, 파일 배치, 결과를 좌우한 수치 같은 것들이다. 이유를 한 마디 붙이면 상황이 조금 달라도 학생이 맞춰 간다.
- 함정을 모은다. 기준과 학생이 빠졌던 막다른 길마다 "X 하지 마라, 왜냐하면 Y"를 한 줄씩.
- 검증을 스킬에 넣는다. 끝났다고 말하기 전에 돌릴 검증 명령과 통과했을 때의 모습을 맨 끝에 적는다. 오픈 모델은 일찍 멈추거나 확인 없이 성공을 보고하는 일이 잦다.
- 하네스 쪽 함정을 적는다. 오래 도는 서버가 도구 호출을 막아 버린다면 백그라운드로 띄우고 끝나면 끄라고 적는 식이다.
- 문장보다 스크립트. 학생이 빌드 명령이나 데이터 변환 같은 기계적 단계에서 계속 헛디디면 `skill/scripts/`에 스크립트를 넣고 그걸 돌리라고 한다.
- 답을 넘겨주지 않는다. 기준의 완성 결과물이나 그걸 써 주는 스크립트는 안 된다. 40줄 안팎의 코드 조각은 학생이 달리 해낼 수 없는 몇 군데에만 허용하고 왜 필요했는지 기록에 남긴다. 목표는 학생이 일을 해낼 수 있게 하는 스킬이지 설치 프로그램이 아니다.

본문은 250줄 아래로 유지하고 긴 참고 자료는 `references/`로 빼서 필요한 단계에서만 읽게 한다. 저장소에는 학생 스킬의 틀도 있다. 목표, 완료 조건 체크리스트, 시작 전 하네스 주의, 단계, 결정과 이유, 하지 말 것, 끝내기 전 검증 순서다.

### 5. 학생을 돌린다

`distill.py trial -k 3`이 지금의 스킬을 그 반복 번호로 얼려 둔다. 시작 상태를 새로 복제한 작업 폴더 셋을 만들고 tmux 창 셋에서 학생을 띄운다. 학생이 받는 것은 원래 프롬프트, 작업 폴더 안 `.skill/<이름>/`에 복사된 스킬, 그리고 "이 폴더에 스킬이 있으니 처음부터 끝까지 읽고 따르라"는 한 줄뿐이다. 시행 하나의 기본 제한 시간은 90분이다. 사용자는 `tmux attach`로 학생이 일하는 모습을 지켜볼 수 있다.

시행이 도는 동안 선생은 놀지 않는다. 다음 체크를 준비하고 기준을 다시 읽으며 몇 분마다 들여다본다. 같은 오류가 10분 넘게 되풀이되는 식으로 확실히 막힌 게 아니면 시행을 일찍 끊지 않는다. 끊었다면 판정에 그 사실을 적는다.

### 6. 시행마다 판정한다

선생은 시행마다 학생이 한 일의 기록, 체크 로그, 스크린샷을 읽는다. 체크가 못 잡는 부분은 결과를 직접 연다. 그리고 `acceptance.md`와 기준에 항목별로 맞춰 본다. 판정은 match·close·miss·broken 넷 중 하나에 0-10점이다. match는 사용자에게 기준과 같다며 내밀 수 있다는 뜻이다. 조금이라도 망설여지면 close다.

가장 중요한 기록은 첫 분기점(first divergence)이다. 학생이 처음으로 잘못 든 길, 그 뒤의 격차를 설명하는 지점이다. 예시로 "4단계: vite를 포그라운드로 띄워 도구 호출이 20분 동안 멈춤"이 적혀 있다. 뒤쪽 증상을 고치는 수정은 대개 실패한다.

### 7. 실패 유형에 맞춰 고친다

| 무슨 일이 있었나 | 고치는 법 |
|---|---|
| 단계를 건너뛰거나 안 읽었다 | 앞으로 옮기고 짧게 줄이고, "멈추고 확인" 관문을 단다 |
| 단계를 잘못 읽었다 | 구체적으로 다시 쓰고 기대 결과 예시를 붙인다 |
| 하네스·도구를 잘못 썼다 | 맨 위에 하네스 주의와 정확한 명령을 적는다 |
| 알려 줘도 어려운 부분을 못 했다 | 짧은 코드 조각이나 `skill/scripts/`의 스크립트를 준다 |
| 확인 없이 끝냈거나 일찍 멈췄다 | 검증 단계를 필수로 하고 명령과 기대 출력을 적는다 |
| 긴 실행에서 맥락을 잃었다 | 문장을 줄이고, 그 단계에서만 읽을 `references/` 파일로 나눈다 |
| 시행 환경이 깨졌다 | 스킬이 아니라 `--setup`이나 `checks.sh`를 고치고, 그 시행은 세지 않는다 |

본 실패들을 한 번에 고치고 각 수정이 무엇을 겨냥했는지 판정 기록에 남긴다. 다음 반복에서 점수가 떨어지면 수정을 더 얹지 말고 원인이 된 변경을 되돌린다.

언제 멈추나? 한 반복의 세 시행이 모두 match면 다음 단계로 간다. 8회를 채우거나 3회 연속 최고 점수가 오르지 않아도 멈춘다. 그때는 학생이 아직 못 하는 것과 해 본 시도를 사용자에게 알린다. SKILL.md는 그것도 쓸모 있는 결과라고 적었다.

### 8-9. 사용자가 정하고, 전달한다

`distill.py report`가 `report.html`을 만든다. 기준과 시행들, 판정 기록, 스킬을 나란히 놓은 보고서다. 선생은 이 보고서를 보여 주고 가장 좋은 시행의 작업 폴더를 알려 줘서 사용자가 직접 돌려 볼 수 있게 한다. 그리고 묻는다. 이게 기준만큼 좋은가?

fail이면 사용자의 말이 가장 중요한 증거가 된다. 그 말을 `acceptance.md`에 더하고 7단계로 돌아간다. pass면 스킬이 `final/`로 복사된다. 넘기기 전에 SKILL.md 끝에 "Tested with" 줄을 붙인다. 하네스·모델·반복 횟수·마지막 시행 일치 수를 적는 줄이다. 기준에서 비밀 값이나 사설 호스트 이름, 개인 정보가 묻어오지 않았는지도 확인한다. 원하면 학생 하네스의 스킬 폴더에 설치한다.

## 시범 실행에서 배운 판정 요령

SKILL.md의 판정 절에는 "실제 실행에서 배웠다"는 요령이 붙어 있다. 읽으면서 가장 흥미로웠던 대목이다.

시범 작업에서 학생 시행 셋은 기능을 모두 갖췄다. 축소판으로는 기준과 똑같아 보였다. 선생은 8.5-9점을 줬다. 그런데 사용자는 보자마자 품질이 근처에도 못 간다며 거절했다. 가까이서 보니 학생이 만든 월드는 듬성듬성하고 밋밋했다. 기능이 같다고 기준만큼 좋은 건 아니었다. 이 일로 생긴 요령이 여섯 가지다.

- 완성도는 원래 해상도로, 나란히 놓고 본다. 둘 다 2배 배율로 캡처해 같은 영역끼리 맞댄다. 물체당 디테일, 밀도, 글꼴, 움직임 같은 구체적인 격차를 먼저 적고 나서 점수를 매긴다.
- 학생은 대개 화면을 못 본다. 그러니 신경 쓰는 시각 속성마다 학생이 확인할 수 있는 숫자를 준다. 시범에서는 '눈에 보이는 디테일이 있는 화면 칸의 비율'이 기준(56%)과 거절된 시행(33-40%)을 갈랐다. 학생 스킬에는 이 비율과 빈 영역 지도를 출력하는 스크립트가 들어갔다.
- 학생의 마지막 메시지는 증거가 아니다. 학생들은 "검증 완료, 테스트 모두 통과"라고 곧잘 말한다. 선생이 체크를 직접 돌리고, 사용자처럼 걸어가 키를 누르고 버튼을 눌러 화면을 본다.
- 첫 화면만 보지 말고 상태를 찔러 본다. 핵심 루프가 있는 작업이면 처음·중간·끝 세 지점에서 확인한다. 저장 상태가 있는 앱이면 학생의 코드로 중간 상태와 완료 상태를 만들어 페이지 스크립트가 돌기 전에 주입한다(Playwright의 `add_init_script`). 값을 넣고 새로고침하는 방식은 실패한다. 많은 페이지가 닫힐 때 상태를 덮어 저장하기 때문이다.
- 체크가 실패하면 체크부터 의심한다. 기준에 다시 돌려 본다. 시범에서 실패로 나온 4건 중 3건은 체크 쪽 버그였다. 짐작으로 적은 저장 키, 일시정지 메뉴를 열어 버린 Escape 키, 빗나간 닫기 클릭이었다.
- 같은 것끼리 비교한다. 시행에 한 조작(직접 조작, 상태 주입)은 기준에도 똑같이 하고 둘 다 보고서에 넣는다.

## 학생 하네스와 실행 권한

학생은 하네스별 셸 어댑터로 돈다. 어댑터는 헤드리스 세션 하나를 돌리고 끝난다. 세션 로그를 `$TRACE_DIR/session.jsonl`에 남기고 하네스의 종료 코드를 그대로 돌려준다. 새 하네스를 붙이려면 `omp.sh`를 복사해 명령만 바꾸면 된다.

| 하네스 | README의 상태 | 학생의 전역 지침·스킬 끄기 | 승인 절차 |
|---|---|---|---|
| omp (oh-my-pi) | 시험됨 | 지침 파일·규칙·스킬 모두 끔 | `--auto-approve` |
| Codex CLI | 선생으로 시험됨. 학생으로 쓰려면 `STUDENT_ARGS`에 제공자 설정 필요 | 사용자 설정·규칙 끔 | 승인과 샌드박스를 모두 우회 |
| Claude Code | 작성됨. 오픈 모델은 Anthropic 호환 서버를 `ANTHROPIC_BASE_URL`로 지정 | 끄는 옵션 없음 | `--dangerously-skip-permissions` |
| pi[^pi] | 작성됨, 미시험 | 스킬만 끔 | — |
| opencode[^opencode] | 작성됨, 미시험. 세션 로그 파서가 아직 없음 | 끄는 옵션 없음 | `--auto` |

표에서 오른쪽 두 열이 눈에 걸린다.

하나는 격리의 빈틈이다. Claude Code와 opencode 어댑터에는 전역 지침을 끄는 옵션이 붙어 있지 않다. 이 둘을 학생으로 쓰면 사용자의 전역 지침 파일이 학생에게도 들어간다. 그러면 스킬의 효과와 기존 설정의 효과가 섞인 채 판정된다.

다른 하나는 실행 권한이다. 어댑터는 학생을 무인으로 돌리려고 승인 절차를 끈다. 시행마다 작업 폴더를 새로 복제하긴 하지만 그건 git 복제일 뿐 샌드박스가 아니다. 약한 모델이 내 계정 권한으로 승인 없이 셸 명령을 돌리는 구조다. 저장소가 따로 경고하지는 않는다. 그래도 컨테이너나 가상 머신에서 돌리는 편이 안전하다.

## 설치와 사용

저장소를 복제해 선생 에이전트의 스킬 폴더에 심볼릭 링크로 걸면 끝이다. Claude Code는 `~/.claude/skills/`, Codex는 `~/.agents/skills/`다. tmux, git, Python 3.10 이상, 그리고 모델에 연결된 학생 하네스가 있어야 한다. 웹 결과물을 다루려면 Playwright와 Pillow, 크로미움도 설치한다.

잘 끝난 세션의 마지막에 이렇게 말하면 된다. "이 세션을 내 로컬 서버의 deepseek-v4.1-flash와 omp용 스킬로 증류해 줘." README의 예시는 영어다.

저장소 구성은 단출하다. 선생이 따르는 `SKILL.md`, 기록 관리 스크립트 `distill.py`(init·trial·status·wait·evidence·verdict·ledger·report·accept), 세션 로그를 읽기 좋은 요약으로 바꾸는 `extract_session.py`, 웹 앱을 캡처하는 `capture_web.py`, 하네스 어댑터 다섯 개, 학생 스킬 틀이다. README는 완료된 실행 예시를 `examples/`에 둔다고 소개하지만 2026-11-24 기준으로는 아직 그 폴더가 없다.

## 누구에게 맞나

프런티어 모델로 한 번 성공한 작업이 있다. 그 작업을 로컬 오픈 웨이트 모델에게 되풀이해 맡기려는 사람에게 맞다. 비용이나 데이터 반출 문제로 로컬 모델을 써야 하는데 그 모델이 혼자서는 같은 품질을 내지 못할 때다. 결과가 저장소 안 파일로 남고 스크립트로 검사할 수 있는 작업일수록 잘 맞는다.

이런 경우엔 맞지 않는다. 결과 스킬은 작업 1개·모델 1개·하네스 1개에 맞춰져 있다. 여러 작업에 두루 쓸 스킬을 원한다면 다른 도구를 찾아야 한다. 기준 세션이 없으면 시작할 수 없다. 버전마다 세 번, 최대 8회를 돌리니 선생의 토큰과 학생의 실행 시간도 꽤 든다. 공개된 지 며칠 안 됐고 시험된 학생 하네스도 omp 하나다. 지금은 직접 써 보며 다듬을 사람에게 맞는 단계다.

## 맺으며

읽고 나서 정답을 구하는 방식과 시범 실행의 실패담이 오래 남았다.

에이전트 평가에서는 늘 정답 세트 만들기가 어렵다. skill-distill에서는 사용자가 이미 만족한 세션 하나가 정답이다. 선생은 그 결과에서 "왜 좋았나"를 관찰 가능한 항목으로 뽑고 그 체크가 기준에서 먼저 통과하는지 확인한다. 정답을 새로 만들지 않고 이미 있는 결과에서 읽어 낸다.

시범 실행에서 기능 목록은 다 맞았는데 사람은 한눈에 아니라고 했다. 선생 모델의 9점과 사람의 "근처에도 못 간다" 사이에는 간극이 있다. 이 간극 때문에 마지막 판정은 사람이 쥐어야 한다. 저장소는 그 간극을 숫자 하나, 디테일 있는 칸의 비율로 학생에게 보여 줬다. 약한 모델에게는 말보다 잴 수 있는 신호가 낫다. 사람에게 일을 가르칠 때도 대체로 그렇다.

[^claudecode]: Claude Code — Anthropic이 만든 터미널 코딩 에이전트. 이 글에서는 선생 역할을 하는 하네스이자, Anthropic 호환 서버를 붙이면 학생으로도 쓸 수 있는 하네스다.
[^codex]: Codex — OpenAI의 코딩 에이전트 CLI. 이 글에서는 선생으로 시험된 하네스이며, 로컬 OpenAI 호환 서버를 제공자로 지정하면 학생으로도 쓸 수 있다.
[^omp]: omp (oh-my-pi) — 터미널에서 도는 코딩 에이전트 하네스. 이 글에서는 skill-distill이 실제로 시험한 유일한 학생 하네스다.
[^deepseek]: DeepSeek — 오픈 웨이트 대형 언어 모델을 내는 중국 AI 회사. 이 글에서는 README 예시의 학생 모델(DeepSeek-V4.1-Flash)을 만든 곳이다.
[^tmux]: tmux — 터미널 하나에서 여러 세션과 창을 띄우고 나중에 다시 붙을 수 있게 해 주는 터미널 멀티플렉서. 이 글에서는 학생 시행 셋이 각자의 창에서 돌고, 사용자가 붙어서 지켜보는 무대다.
[^playwright]: Playwright — 브라우저를 코드로 조작하는 마이크로소프트의 자동화 라이브러리. 이 글에서는 웹 결과물을 헤드리스 크로미움으로 띄워 조작하고 스크린샷을 남기는 데 쓴다.
[^pi]: pi — 터미널 코딩 에이전트 하네스. 이 글에서는 어댑터만 작성되고 아직 시험되지 않은 학생 하네스다.
[^opencode]: opencode — 오픈소스 터미널 코딩 에이전트. 이 글에서는 어댑터가 작성됐지만 시험되지 않았고, 세션 로그를 읽는 파서도 아직 없는 학생 하네스다.
