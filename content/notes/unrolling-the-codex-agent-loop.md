## 한눈에 보기

코딩 에이전트는 모델에게 정확히 무엇을 보낼까? Codex[^codex]가 보내는 실제 요청을 보면 답이 나온다.

| 항목 | 내용 |
|---|---|
| 루프 | 프롬프트를 보내고, 모델이 도구를 부르면 실행해 결과를 덧붙이고, 다시 보낸다. 모델이 사용자에게 말을 걸면 한 턴이 끝난다 |
| 요청 | Responses API[^responses]에 `instructions`·`tools`·`input` 세 칸을 채워 보낸다 |
| 순서 | 권한 안내 → 개발자 지침 → AGENTS.md[^agents] 등 사용자 지침 → 환경 정보 → 사용자 메시지 |
| 무상태 | 이전 응답 ID를 쓰지 않고 매번 대화 전체를 보낸다. 데이터 비보존(ZDR)[^zdr] 고객을 지원하기 위해서다 |
| 캐시 | 새 프롬프트가 늘 이전 프롬프트를 앞부분으로 그대로 품게 짠다. 그래야 캐시가 맞고 비용이 선형으로 는다 |
| 조심할 것 | 도구 목록·모델·샌드박스·작업 폴더를 대화 중에 바꾸면 캐시가 깨진다. 바뀐 것은 고치지 않고 새 메시지로 덧붙인다 |
| 압축 | 토큰이 한도를 넘으면 `/responses/compact` 엔드포인트로 대화를 짧은 항목 목록으로 바꾼다 |

## 먼저, Responses API란 무엇인가

참고: [Responses API 문서](https://platform.openai.com/docs/api-reference/responses), [프롬프트 캐싱 문서](https://platform.openai.com/docs/guides/prompt-caching)

원문은 Responses API를 안다고 보고 바로 JSON으로 들어간다. 모르는 분을 위해 먼저 짚는다.

Responses API는 OpenAI가 Chat Completions 다음으로 내놓은 모델 호출 API다. 무엇이 다른가? 대화를 "메시지 목록"이 아니라 "항목(item) 목록"으로 다룬다. 사용자 메시지, 모델의 추론 요약, 도구 호출, 도구 결과가 모두 같은 줄에 선 항목이다. 응답도 항목 목록으로 돌아온다. 그러니 받은 항목을 그대로 다음 요청의 `input` 뒤에 붙이면 대화가 이어진다.

대화를 잇는 방법은 둘이다. 하나는 서버에 맡기는 것이다. 지난 응답의 ID를 `previous_response_id`로 넘기면 서버가 저장해 둔 앞 대화를 이어 붙인다. 다른 하나는 클라이언트가 매번 대화 전체를 보내는 것이다. Codex는 뒤쪽을 고른다.

| | 서버가 기억(`previous_response_id`) | 클라이언트가 전부 보냄(Codex) |
|---|---|---|
| 요청 크기 | 새 항목만 | 대화 전체, 턴마다 커진다 |
| 서버 저장 | 대화를 저장해야 한다 | 저장할 것이 없다 |
| 데이터 비보존(ZDR) | 맞지 않는다 | 그대로 지원된다 |
| 연산 비용 | 캐시가 맞으면 비슷하다 | 캐시가 맞으면 비슷하다 |

두 방식을 파이썬으로 적어 보면 이렇다. 원문의 예시는 JSON뿐이라 차이를 보기 쉽게 옮긴 이가 파이썬으로 다시 썼다. `post()`는 Responses API에 요청 한 번을 보내는 함수다.

```python
# 방식 1: 서버가 대화를 기억한다. 보내는 양은 작지만 서버에 대화가 남는다
resp = post(input=[user("README에 구조도를 넣어 줘")], tools=TOOLS)
while resp.has_tool_call():
    out = run_tool(resp.tool_call)                  # 로컬에서 실행
    resp = post(previous_response_id=resp.id,       # 앞 대화는 서버가 붙인다
                input=[out])                        # 새 항목 하나만 보냄
print(resp.text)

# 방식 2: Codex처럼 무상태. 매번 전부 보내지만 서버에 남는 것이 없다
items = [permissions, user_instructions, env_context,
         user("README에 구조도를 넣어 줘")]
while True:
    resp = post(instructions=BASE, tools=TOOLS, input=items)   # 대화 전체
    items += resp.output                            # 추론·도구 호출 항목을 뒤에만 붙인다
    if not resp.has_tool_call():
        break                                       # 어시스턴트 메시지면 턴 끝
    items.append(run_tool(resp.tool_call))          # 도구 결과도 뒤에만
print(resp.text)
# items는 앞을 한 번도 고치지 않는다 → 직전 요청이 다음 요청의 접두부 → 캐시가 맞는다
```

방식 2는 보내는 바이트가 대화 길이의 제곱으로 는다. 그런데도 괜찮은 까닭은 뒤에서 다룬다.

## 에이전트 루프란 무엇인가

에이전트는 무엇으로 움직이나? 저자는 모든 AI 에이전트의 한가운데에 같은 루프가 있다고 말한다.

사용자가 말을 건넨다. 에이전트는 그 말을 프롬프트에 넣어 모델에게 보낸다. 이것이 추론이다. 모델의 답은 둘 중 하나다. 사용자에게 하는 말이거나 도구를 불러 달라는 요청이다. 도구 요청이면 에이전트가 도구를 실행한다. 결과를 프롬프트에 붙여 다시 보낸다. 모델이 더는 도구를 부르지 않고 사용자에게 말을 걸 때까지 이 일을 되풀이한다.

사용자 입력에서 에이전트의 마지막 말까지를 한 턴이라 부른다. 한 턴 안에서 추론과 도구 호출이 수십, 수백 번 오갈 수 있다. 코딩 에이전트에게 진짜 결과물은 디스크에 쓴 코드다. 그래도 턴은 늘 "파일을 추가했습니다" 같은 말로 끝난다. 그 말이 사용자에게 차례를 돌려주는 신호다.

여기서 문제가 하나 생긴다. 다음 턴을 보낼 때는 앞 턴의 메시지와 도구 호출이 모두 프롬프트에 들어간다. 대화가 길수록 프롬프트도 길어진다. 모델마다 한 번에 다룰 수 있는 토큰 수, 곧 컨텍스트 창이 정해져 있다. 한 턴에 도구를 수백 번 부르면 창이 넘칠 수 있다. 그래서 에이전트는 컨텍스트 창을 관리하는 데 큰 책임을 진다.

## Codex는 어디로 요청을 보내나

Codex CLI는 추론할 때 Responses API로 HTTP 요청을 보낸다. 주소는 설정으로 바꿀 수 있다. Responses API 모양만 맞추면 어느 서버든 된다.

- ChatGPT 계정으로 로그인하면 ChatGPT 백엔드의 Codex 전용 주소로 간다.
- API 키를 쓰면 OpenAI API의 `/v1/responses`로 간다.
- `--oss` 옵션을 주면 내 컴퓨터에서 도는 ollama[^ollama]나 LM Studio[^lmstudio]의 gpt-oss[^gptoss]로 간다.
- Azure 같은 클라우드에 올린 Responses API에도 붙는다.

## 첫 프롬프트는 어떻게 쌓이나

Responses API를 부를 때 사용자는 모델이 읽을 프롬프트를 직접 쓰지 않는다. 몇 개의 칸을 채워 보내면 서버가 프롬프트로 엮는다. 프롬프트는 항목의 목록이다. 항목마다 역할이 붙는다. 무게가 큰 쪽부터 system, developer, user, assistant 순이다.

저자가 짚는 칸은 셋이다.

- `instructions`: 모델의 기본 지침이다. 설정 파일에 지정한 파일이 있으면 그 파일을 쓴다. 없으면 Codex 저장소에 모델별로 들어 있는 기본 지침을 쓴다.
- `tools`: 모델이 부를 수 있는 도구 목록이다. Codex가 직접 주는 도구(셸 실행, 계획 갱신), Responses API가 주는 도구(웹 검색), 사용자가 MCP[^mcp] 서버로 붙인 도구가 함께 들어간다.
- `input`: 텍스트·이미지·파일 같은 입력 항목의 목록이다.

`input`에는 사용자 메시지보다 먼저 들어가는 항목이 넷 있다.

| 순서 | 역할 | 내용 |
|---|---|---|
| 1 | developer | 샌드박스 권한 안내. 어느 폴더에 쓸 수 있는지, 네트워크는 되는지, 언제 사용자에게 허락을 구하는지 |
| 2 | developer | (있으면) 설정 파일의 개발자 지침 |
| 3 | user | (있으면) 사용자 지침. AGENTS.md들을 홈 폴더부터 프로젝트 루트, 현재 폴더까지 차례로 모은 것(기본 32KiB까지)과 스킬 목록 |
| 4 | user | 환경 정보. 현재 작업 폴더와 셸 이름 |
| 5 | user | 사용자가 친 메시지 |

1번의 권한 안내는 Codex가 주는 셸 도구에만 해당한다. MCP 서버가 준 도구는 Codex가 샌드박스에 가두지 않는다. 안전장치는 그런 도구가 스스로 달아야 한다. 3번은 구체적인 지침일수록 뒤에 온다. 홈 폴더의 지침보다 현재 폴더의 지침이 더 뒤에 놓인다.

서버는 요청을 받아 프롬프트를 이렇게 엮는다. 맨 앞에 서버가 정한 system 메시지, 이어서 `tools`, `instructions`, 그리고 `input`이 차례로 온다. 앞의 세 칸의 순서는 서버가 정한다. 그중 내용까지 서버가 정하는 것은 system 메시지 하나다.

## 첫 턴은 어떻게 도나

요청을 보내면 서버는 SSE[^sse] 스트림으로 답한다. 이벤트가 한 줄씩 흘러온다. 추론 요약이 조금씩 오고 출력 항목이 추가된다. 답 텍스트가 조각조각 온 뒤에 완료 이벤트가 온다. Codex는 이 이벤트를 받아 두 갈래로 쓴다. 텍스트 조각은 화면에 흘려 보여 준다. 다 만들어진 출력 항목은 다음 요청의 `input`에 붙일 항목으로 바꾼다.

첫 응답에 추론 항목 하나와 셸 도구 호출 하나가 왔다고 하자. 모델은 `cat README.md`를 돌려 달라고 했다. Codex는 명령을 실행한다. 그러고 나서 다음 요청의 `input` 끝에 세 항목을 붙인다. 추론 항목, 도구 호출 항목, 도구 결과 항목이다. 추론 항목에는 암호화된 내용이 함께 들어 있다. 클라이언트는 읽을 수 없지만 서버는 풀어서 모델에게 앞의 생각을 이어 준다.

여기서 눈여겨볼 대목이 있다. 두 번째 프롬프트는 첫 번째 프롬프트를 한 글자도 바꾸지 않고 앞부분으로 품는다. 뒤에 항목이 붙을 뿐이다. 저자는 프롬프트 캐싱을 살리려고 일부러 그렇게 짰다고 강조한다.

모델이 도구를 더 부르지 않고 "구조도를 넣었습니다"라고 말하면 턴이 끝난다. Codex는 그 말을 보여 주고 입력 창에 커서를 둔다. 사용자가 "괜찮은데 자전거 보관소가 빠졌네" 하고 답하면 어시스턴트 메시지와 이 새 사용자 메시지가 다시 `input` 끝에 붙는다. 대화는 그렇게 계속 길어진다.

## 매번 전부 보내면 느리지 않나

"대화 전체를 매번 보내면 보내는 양이 대화 길이의 제곱으로 늘지 않나?" 저자는 그 말이 맞다고 인정한다. 그런데도 Codex는 `previous_response_id`를 쓰지 않는다. 왜인가?

첫째, 요청이 무상태라 Responses API를 구현하는 쪽이 단순해진다. 둘째, 데이터 비보존(ZDR) 고객을 지원하기 쉽다. 서버가 이전 대화를 기억하려면 대화를 저장해야 한다. 저장 자체가 ZDR과 맞지 않는다. 그럼 ZDR 고객은 앞 턴의 추론을 잃나? 그렇지 않다. 추론 항목의 암호화된 내용은 클라이언트가 들고 다닌다. 서버는 복호화 키만 보관한다. 데이터는 남기지 않는다.

진짜 비용은 네트워크가 아니라 모델 샘플링이다. 그래서 프롬프트 캐싱이 중요하다. 캐시가 맞으면 앞 부분의 계산을 다시 쓰므로 샘플링 비용이 제곱이 아니라 선형으로 는다.

캐시는 프롬프트의 앞부분이 정확히 같을 때만 맞는다. 그러니 지침이나 예시처럼 변하지 않는 것은 앞에, 바뀌는 것은 뒤에 둬야 한다. 이미지와 도구 목록도 요청마다 똑같아야 한다.

Codex에서 캐시를 깨는 일은 이런 것들이다.

- 대화 중에 모델이 쓸 수 있는 도구를 바꾼다.
- 대상 모델을 바꾼다. 모델마다 기본 지침이 달라서 프롬프트 앞쪽이 바뀐다.
- 샌드박스 설정, 승인 방식, 작업 폴더를 바꾼다.

저자는 실제로 겪은 일도 적었다. MCP 도구를 처음 붙였을 때 도구 목록의 순서가 요청마다 달라지는 버그가 있었다. 순서만 달라져도 캐시가 깨졌다. MCP 서버는 도구 목록이 바뀌었다고 알려 오기도 해서 더 까다롭다. 긴 대화 한가운데서 그 알림을 반영하면 비싼 캐시 미스가 난다.

그래서 Codex는 설정이 바뀌어도 앞의 메시지를 고치지 않는다. 바뀐 내용을 새 메시지로 뒤에 붙인다. 샌드박스나 승인 방식이 바뀌면 처음과 같은 형식의 권한 안내를 developer 메시지로 새로 넣는다. 작업 폴더가 바뀌면 같은 형식의 환경 정보를 user 메시지로 새로 넣는다.

## 컨텍스트 창이 차면

캐시 다음으로 지켜야 할 자원은 컨텍스트 창이다. 보통은 토큰이 한도를 넘을 때 대화를 압축한다. 지금까지의 `input`을 더 짧은 항목 목록으로 갈아 끼운다. 이 목록이 대화 전체를 대표한다.

처음에는 사용자가 `/compact`를 직접 쳐야 했다. 그러면 Codex가 대화 전체와 요약 지침을 Responses API에 보내고 돌아온 요약 메시지를 새 `input`으로 삼았다.

지금은 Responses API에 압축 전용 엔드포인트가 있다. 이 엔드포인트가 돌려주는 항목 목록에는 `type=compaction`이라는 특별한 항목이 들어 있다. 모델이 원래 대화를 어떻게 이해했는지가 그 안에 암호화돼 들어 있다. Codex는 토큰 수가 설정한 한도를 넘으면 이 엔드포인트를 자동으로 부른다.

## 옮긴 이의 덧붙임

이 글에서 하나만 가져간다면 "앞은 고치지 말고 뒤에만 붙여라"다. 설정이 바뀌면 고치고 싶은 마음이 든다. 처음의 권한 안내를 새 권한으로 바꿔 쓰는 편이 깔끔해 보인다. 그러나 그 순간 그 뒤의 모든 토큰이 캐시에서 떨어진다. Codex는 깔끔함 대신 덧붙이기를 고른다. 모델에게는 "처음엔 이랬는데 지금은 이렇다"는 기록이 남는다. 계산은 앞부분을 다시 쓴다.

[하니스 엔지니어링 101](/compendium/notes/harness-engineering-101/)이 장난감 하니스로 보여 준 원리는 실제 제품에서도 그대로 통한다. 배열 하나와 while 루프 하나, 그리고 캐시를 지키는 규율. 세계적인 코딩 에이전트도 뼈대는 그만큼 단순하다.

[^codex]: Codex — OpenAI의 소프트웨어 에이전트 제품군(CLI, 클라우드, VS Code 확장). 이 글은 모든 Codex의 바탕이 되는 오픈소스 하니스인 Codex CLI([github.com/openai/codex](https://github.com/openai/codex))를 다룬다.
[^responses]: Responses API — OpenAI의 모델 호출 API. 입력과 출력을 항목 목록으로 다룬다. 이 글에서 Codex가 매 추론마다 부르는 유일한 창구다.
[^agents]: AGENTS.md — 저장소에 두는 에이전트용 안내 파일. 여러 코딩 에이전트가 함께 쓰는 관례다. Codex는 폴더를 따라 올라가며 이 파일들을 모아 사용자 지침으로 넣는다.
[^zdr]: ZDR(Zero Data Retention) — 요청과 응답을 서버에 남기지 않는 OpenAI의 데이터 비보존 계약. Codex가 대화 상태를 서버에 맡기지 않는 가장 큰 이유다.
[^ollama]: ollama — 오픈 모델을 내 컴퓨터에서 돌리는 도구. Codex의 `--oss` 옵션이 붙는 로컬 서버 중 하나다.
[^lmstudio]: LM Studio — 오픈 모델을 내려받아 로컬에서 돌리는 데스크톱 앱. ollama와 같은 역할로 쓰인다.
[^gptoss]: gpt-oss — OpenAI가 공개한 오픈 웨이트 모델. `--oss`로 Codex를 로컬에서 돌릴 때 쓰는 모델이다.
[^mcp]: MCP(Model Context Protocol) — 외부 도구를 에이전트에 붙이는 표준 프로토콜. 이 글에서는 도구 목록이 바뀌어 캐시를 깨는 원인으로 등장한다.
[^sse]: SSE(Server-Sent Events) — 서버가 HTTP 연결 하나로 이벤트를 차례로 흘려보내는 웹 표준. Responses API가 답을 스트리밍하는 방식이다.
