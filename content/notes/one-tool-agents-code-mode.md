## 한눈에 보기

에이전트에게 도구는 몇 개가 맞을까? 저자의 답은 "곧 하나"다.

| 항목 | 내용 |
|---|---|
| 주장 | 에이전트의 도구 목록이 `exec(code)` 하나로 접히고 있다 |
| 이유 | 보통의 도구 호출은 한 차례에 한 동작뿐이다. 코드는 여러 동작을 한 번에 엮는다 |
| 방법 | 도구 스키마를 짧은 타입 선언으로 바꿔 보여 주고, 모델이 쓴 스크립트를 샌드박스에서 돌린다 |
| 왜 bash가 아닌가 | 타입, 탐색 비용, 멀티모달 출력, 자격 증명 대리, 상태 저장 |
| 현황 | Pi, Factory Droid, OpenAI Codex가 기본값으로 쓴다. Factory는 정확도가 오르고 비용이 줄었다고 밝혔다 |
| 숙제 | bash와 사람이 읽는 텍스트에 맞춰 만든 도구·CLI·스킬은 그대로 잘 붙지 않는다 |

## 먼저, Code Mode란 무엇인가

참고: [Cloudflare의 Code Mode 발표](https://blog.cloudflare.com/code-mode/), [Pi 문서의 Codemode 항목](https://pi.dev/docs/latest/codemode)

원문은 Code Mode를 안다고 전제하고 빠르게 넘어간다. 모르는 분을 위해 먼저 짚는다.

Code Mode는 프로그래매틱 도구 호출(programmatic tool calling)이라고도 부른다. 생각은 단순하다. 모델에게 도구 수십 개를 따로따로 주지 않는다. 대신 "코드를 실행하라"는 도구 하나만 준다. 모델은 짧은 TypeScript나 파이썬 스크립트를 쓴다. 그 스크립트가 격리된 샌드박스 안에서 진짜 도구들을 부른다. 결과를 걸러 다음 도구로 넘긴다. 모델에게 돌아오는 것은 스크립트가 일부러 내보낸 결과뿐이다.

| | 보통의 도구 호출 | Code Mode |
|---|---|---|
| 모델이 보는 도구 | 도구마다 JSON 스키마 하나씩, 수십 개 | `exec(code)` 하나와 짧은 타입 선언 |
| 한 차례에 하는 일 | 동작 하나, 잘해야 서로 무관한 호출 몇 개 | 서로 이어지는 동작 여러 개 |
| 중간 결과 | 매번 컨텍스트에 쌓인다 | 샌드박스 메모리 안에서 처리되고 사라진다 |
| 거르기·집계 | 모델이 읽고 판단한다 | 코드가 한다 |

예를 들어 보자. "모든 프로젝트에서 담당자가 없는 이슈를 보관 처리하라"는 일이다. 원문의 예시는 TypeScript인데, 차이를 보기 쉽게 파이썬으로 옮겼다. 먼저 보통의 도구 호출이다. `model.next_action()`은 모델이 다음 할 일을 정하는 추론 한 번이다. 그때마다 지금까지 쌓인 컨텍스트를 전부 읽는다.

```python
# 보통의 도구 호출: 한 차례에 동작 하나, 결과는 모두 컨텍스트로
context = ["모든 프로젝트에서 담당자 없는 이슈를 보관해 줘"]
projects = call_tool("linear.list_projects")          # 왕복 1번
context.append(projects)                              # 프로젝트 12개가 컨텍스트에

for p in projects:
    model.next_action(context)                        # 프로젝트마다 추론 1번
    issues = call_tool("linear.list_issues", project_id=p["id"])
    context.append(issues)                            # 이슈 원본 JSON이 통째로 쌓인다

targets = model.next_action(context)                  # 담당자 없는 이슈 고르기도 모델 몫
for issue in targets:
    model.next_action(context)                        # 보관도 하나씩, 42번
    context.append(call_tool("linear.archive_issue", id=issue["id"]))

answer = model.next_action(context)                   # 왕복 약 55번
```

다음은 Code Mode다. 모델은 아래 스크립트를 인자로 넣어 `exec`를 한 번 부른다.

```python
# Code Mode: 모델은 exec(code)를 한 번 부른다. 아래는 샌드박스 안에서 돈다
async def main(tools, text):
    projects = await tools.linear.list_projects()
    batches = await asyncio.gather(                   # 12개 프로젝트를 동시에 조회
        *[tools.linear.list_issues(project_id=p["id"]) for p in projects])
    unassigned = [i for b in batches for i in b if not i.get("assignee")]
    await asyncio.gather(                             # 42개를 동시에 보관
        *[tools.linear.archive_issue(id=i["id"]) for i in unassigned])
    text(f"프로젝트 {len(projects)}곳에서 담당자 없는 이슈 {len(unassigned)}개를 보관했다")

# 모델이 받는 것은 text()로 내보낸 한 줄뿐이다.
# API 호출 55번과 이슈 원본 JSON은 샌드박스 안에서만 오간다.
```

왕복 55번이 한 번으로 준다. 컨텍스트에는 이슈 목록 대신 한 줄짜리 요약이 들어온다. Code Mode는 이게 전부다. 나머지는 이걸 어떻게 안전하고 쓸모 있게 만드느냐다.

> 해설 — 이름은 Cloudflare[^cloudflare]가 2025년에 먼저 붙였다. 아르민 로나허의 하니스 Pi[^pi]에서는 같은 생각을 `codemode`라는 도구로 넣었다. Pi의 설계(QuickJS 샌드박스, 동시 실행 제한, MCP 지연 노출)는 [Codemode 노트](/compendium/notes/codemode/)에 자세히 정리해 두었다. 이 글은 특정 하니스보다 "업계가 왜 이쪽으로 모이는가"에 초점을 둔다.

## 한 번에 한 동작에서, 코드 속 연쇄로

왜 하필 지금일까? 저자는 도구 호출이 걸어온 길부터 돌아본다.

처음에는 도구를 몇 개만 줬다. 모델이 많은 도구 가운데 제대로 고르지 못했기 때문이다. 모델이 나아지자 도구 수십 개, MCP[^mcp] 서버 여러 개를 붙였다. 그러자 이번엔 컨텍스트 창이 모자랐다. 이건 도구 검색(tool search)과 점진적 공개(progressive disclosure)로 풀었다. 필요할 때 필요한 도구만 찾아 불러오는 방식이다.

그래도 남는 한계가 있었다. 보통의 도구 호출은 한 차례에 동작 하나다. 모델이 JSON으로 동작 하나를 적는다. 결과가 돌아오기를 기다린다. 결과를 프롬프트 기록에 붙인다. 다시 추론한다. 기껏해야 서로 무관한 호출 몇 개를 한꺼번에 던지는 정도다. 파일 세 개를 동시에 읽는 식이다. 앞 결과에 따라 뒤 동작이 달라지는 일은 차례를 여러 번 넘겨야 한다.

저자는 최근 모델이 서로 이어지는 동작을 한 번에 엮는 솜씨가 크게 늘었다고 본다. 이를테면 이런 일들이다.

- 조사와 거르기: 출처를 받고 읽고 대조하는 세 차례를 스크립트 하나로 줄인다. 상관없는 결과는 코드가 걸러 낸다.
- 여러 파일 수정과 즉석 검증: 보통의 편집 도구는 한 번에 파일 하나다. 스크립트 안에서는 여러 파일을 맞춰 고친 뒤 검사를 돌리고 통과 여부에 따라 갈라질 수 있다.
- 브라우저와 컴퓨터 사용: 버튼 누르기, 양식 채우기, 선택자 기다리기, 표 넘기기는 순서가 뻔하다. 클릭마다 모델을 왕복할 이유가 없다. 페이지 상태가 바뀔 때만 돌아오면 된다.
- 병렬 분기와 하위 에이전트(sub-agent): 조회 20건이나 전문 모델 호출을 동시에 돌려 그 결과를 다른 API로 넘긴다. 단계 사이에 모델의 컨텍스트를 거치지 않는다.

이게 가능해진 데는 세 가지가 겹쳤다. 최전선 모델들은 코드로 많이 훈련된다. 모델 회사들은 Code Mode용 사후 학습(post-training)을 하기 시작했다. 그리고 MCP 서버가 입력 스키마와 함께 출력 스키마(`outputSchema`)를 내놓는 일이 늘었다. 반환 타입을 미리 알면 모델은 결과를 보기 전에 코드를 쓸 수 있다. 도구 A의 출력을 도구 B에 잇는 코드다.

> 해설 — 반환 타입을 모르면 모델은 일단 한 번 불러서 결과 모양을 봐야 한다. 그러면 다시 한 차례에 한 동작으로 돌아간다. 출력 스키마가 있어야 "보지 않고 잇는" 코드가 나온다. 세 번째가 눈여겨볼 대목인 셈이다.

## Code Mode는 어떻게 도나

모델 쪽에서 보이는 도구는 `exec(code)` 하나다. 하니스는 도구 80개의 JSON 스키마를 그대로 넘기지 않는다. 대신 짧은 타입 선언으로 바꿔서 보여 준다. 모델은 스크립트 안에서 `tools.<서버>.<도구>(인자)`를 부른다. 원문은 TypeScript 선언으로 보여 주는데 파이썬으로 옮기면 대략 이런 모양이다.

```python
# 모델이 보는 것: 도구 80개의 JSON 스키마 대신, 짧은 타입 선언
class linear:
    async def list_projects() -> list[Project]: ...
    async def list_issues(project_id: str) -> list[Issue]: ...
    async def archive_issue(id: str) -> Ok: ...

ALL_TOOLS: dict[str, ToolInfo]        # 도구가 수백 개면 이름만 두고 코드로 찾아 쓴다

def text(s: str) -> None: ...          # 여기 넘긴 것만 모델의 컨텍스트에 들어간다
def image(data: bytes, mime: str = "image/png") -> None: ...
def audio(data: bytes, mime: str = "audio/wav") -> None: ...

def store(key: str, value) -> None: ... # 차례를 넘어 남기는 상태, 토큰을 쓰지 않는다
def load(key: str): ...
```

- 도구 노출: 도구가 많으면 전부 펼치지 않는다. 이미 만들어 둔 도구 검색을 쓰거나, 샌드박스 안에 전체 도구 목록(`ALL_TOOLS`)을 두고 코드로 훑게 한다.
- 출력 도우미: `text()`, `image()`, `audio()`에 넘긴 것만 모델의 다음 차례에 실린다. 스크립트가 무엇을 보여 줄지 고른다.
- 상태 도우미: `store()`와 `load()`로 큰 값을 호스트 메모리에 남겨 둔다. 다음 차례에 다시 쓰더라도 컨텍스트를 거치지 않는다.

앞의 이슈 보관 예시에서 샌드박스는 API 호출 55번을 돌린 뒤 결과를 메모리에서 걸러 한 줄만 돌려준다. 원문 표현으로는 프로젝트 12곳에서 이슈 42개를 보관했다는 한 줄이다.

## 왜 bash가 아니라 JS·파이썬 샌드박스인가

bash로도 도구 대리 실행은 만들 수 있다. 그런데 왜 굳이 언어 런타임일까? 저자는 다섯 가지를 든다.

- 타입이 있는 함수: MCP 서버와 내부 API를 타입이 붙은 함수로 그대로 부른다. 네이티브 객체를 주고받는다. 동시 실행과 예외 처리는 언어가 해 준다. bash에서처럼 문자열 이스케이프에 매달리지 않는다.
- CLI 탐색 비용이 없다: bash에 낯선 CLI나 스크립트를 주면 모델은 일하기 전에 이것저것 들춘다. 하위 명령마다 `--help`를 돌리고 스크립트 소스를 읽는다. 플래그와 출력 형식을 알아내느라 차례와 토큰을 쓴다. 타입 선언은 계약서를 미리 건넨다. 모델은 바로 움직일 수 있다.
- 멀티모달 컨텍스트: 셸이 돌려주는 건 표준 출력 텍스트뿐이다. 스크린숏을 보고 싶어도 `cat screenshot.png`로는 안 된다. 그래서 bash 하니스는 이미지 보기 도구를 따로 붙여야 했다. 샌드박스에서는 `image()`를 부르면 호스트가 실제 이미지를 다음 차례에 붙여 준다.
- 자격 증명과 정책 대리: `tools.*` 호출은 모두 구조화된 다리를 건너 호스트로 간다. 호스트는 샌드박스 밖에서 OAuth 토큰을 넣고 스키마를 검사할 수 있다. 지우기 같은 위험한 호출 앞에서 사용자 확인을 받을 수도 있다. 스크립트는 토큰을 볼 일이 없다.
- 상태 관리: 보통의 도구 호출에서 상태를 둘 곳은 프롬프트 기록뿐이다. 큰 조회 결과를 다음 차례에 다시 쓰려면 원본 JSON을 매 차례 컨텍스트에 싣고 다녀야 한다. 키-값 저장소를 열어 주면 상태를 컨텍스트 밖에 둔다.

> 해설 — 다섯 가지 가운데 두 번째와 네 번째가 실무에서 크게 와닿는다. `--help`를 연달아 치는 에이전트는 누구나 본 적이 있다. 자격 증명 대리는 보안 쪽 이점이다. 모델이 쓴 코드는 믿을 수 없는 코드로 다루고 비밀은 경계 밖에 두는 설계다.

## 도구 하나짜리 에이전트 만들기

원문은 Gemini[^gemini] Interactions API로 도구 하나짜리 에이전트를 짜는 예제를 싣는다. 저자 스스로 "실행 가능한 의사 예제"라고 부른다. 흐름만 옮기면 이렇다.

1. 호스트에 진짜 도구 셋을 둔다. PR의 바뀐 파일 목록 받기, 파일 보안 검사, PR에 댓글 달기다. 예제에서는 가짜 값을 돌려주는 함수다.
2. 모델에게는 `exec` 도구 하나만 준다. 도구 설명 안에 세 함수의 타입 선언과 `text()`를 적는다.
3. 첫 차례에 "PR 42번에서 추가된 줄이 50줄 넘는 `.ts` 파일을 검사하고, 찾은 것을 댓글로 달고, 한 줄로 요약하라"고 시킨다. 모델은 스크립트 하나를 내놓는다.
4. 호스트가 그 스크립트를 별도 실행 문맥에서 돌린다. 스크립트는 파일 목록을 받아 메모리에서 거른 뒤 남은 파일만 검사한다. 찾은 게 있으면 댓글을 달고 `text()`로 한 줄을 남긴다.
5. 둘째 차례에 그 한 줄만 함수 결과로 돌려보낸다. 파일 객체나 검사기 원본 출력은 모델의 컨텍스트에 한 번도 들어가지 않는다.

예제는 Node.js의 `node:vm`으로 스크립트를 돌린다. 저자는 주석에서 믿을 수 없는 코드라면 QuickJS[^quickjs]나 isolated-vm[^isolatedvm]을 쓰라고 적어 둔다.

> 해설 — Node.js 공식 문서도 `vm` 모듈은 보안 장치로 쓸 수 없다고 못 박는다. 그러니 이 주석을 흘려 읽으면 안 된다. 실서비스라면 모델이 쓴 코드를 진짜 격리된 런타임에서 돌려야 한다. Pi가 WASM 위의 QuickJS를 고른 것도 그래서다. 예제에 나오는 모델 이름은 원문 그대로 옮겼다.

## 하니스들은 이미 기본값으로 쓴다

이건 먼 미래 얘기일까? 저자는 이미 벌어지는 일이라고 말한다. 코딩 에이전트와 개발 프레임워크가 한쪽으로 모이고 있다. Code Mode를 도구 지휘의 기본값으로 삼는 쪽이다.

- 하니스: Pi, Factory Droid[^factory], OpenAI Codex[^codex]가 Code Mode를 싣거나 기본값으로 쓴다.
- Factory는 Droid 1.0을 Code Mode로 바꾼 뒤 Terminal-Bench[^tbench] 4 정확도가 3.5점 올랐고 모델 비용은 15% 줄었다고 밝혔다.
- 프레임워크: Pydantic AI[^pydanticai], LangChain[^langchain], Cloudflare Agents SDK가 비슷한 Code Mode 도구를 이미 지원한다.

## 다음은

그럼 모든 에이전트가 곧 `exec` 하나만 갖게 될까? 저자는 꼭 그렇지는 않다고 답한다. 이건 하니스 엔지니어링 문제이면서 연구와 제품의 문제이기도 하다.

실험을 시작하면 금방 부딪히는 게 있다. 지금까지 만든 도구, CLI, 에이전트 스킬(Agent Skills) 상당수가 그대로는 잘 붙지 않는다. bash와 사람이 읽는 텍스트에 맞춰 다듬었지, 타입이 있는 코드 실행을 전제하지 않았기 때문이다. 저자는 그래서 한 걸음 물러나 에이전트에게 정말 무엇이 필요한지 따져 보라고 권하며 글을 맺는다.

## 읽으며 짚어 둘 점

- 같은 결론, 두 방향: 아르민 로나허는 "MCP를 잔뜩 붙이지 말고 CLI를 쓰라"던 쪽에서 출발해 Codemode에 닿았다([노트](/compendium/notes/codemode/)). 슈미트는 도구 호출이 커져 온 역사에서 출발해 같은 자리에 닿는다. 출발점이 달라도 "도구를 나열하지 말고 코드로 엮게 하라"는 결론은 같다.
- 숫자는 한 곳에서 나왔다: 정확도 3.5점, 비용 15%는 Factory가 밝힌 수치다. 이 글에서 따로 검증하지는 않았다. 작업 종류에 따라 효과는 크게 다를 수 있다.
- bash를 버리자는 말은 아니다: 저자 자신도 bash 도구를 다룬 글을 쓴 사람이다. 주장은 "조합은 타입 있는 런타임이 더 잘한다"에 가깝다. 파일을 뒤지고 프로그램을 돌리는 일은 여전히 셸이 편하다.
- 격리는 공짜가 아니다: 모델이 쓴 코드를 돌리는 순간 샌드박스 설계가 하니스의 핵심이 된다. 네트워크·파일시스템을 어디까지 열지, 위험한 호출에서 누가 확인할지가 새 숙제다.

## 정리

도구 호출의 단위가 바뀌고 있다. 한 차례에 동작 하나씩 부르던 것을 이제는 스크립트 한 편에 담아 넘긴다. 모델은 계획을 코드로 적는다. 샌드박스가 그 코드를 돌리면 컨텍스트에는 결과의 요점만 남는다. 도구를 몇 개 줄지 고민하던 사람들은 이제 다른 질문을 마주한다. 그 하나뿐인 도구 안에서 무엇을 할 수 있게 할 것인가.

[^cloudflare]: Cloudflare: CDN·엣지 컴퓨팅 회사. 2025년 'Code Mode'라는 이름으로 MCP 도구를 타입 있는 API로 바꿔 모델이 코드로 부르게 하는 방식을 발표했고, 이 글의 용어가 여기서 왔다.
[^pi]: Pi: 아르민 로나허가 만든 오픈소스 코딩 에이전트 하니스. `codemode` 도구로 같은 방식을 구현했고, 이 글에서는 Code Mode를 기본으로 쓰는 하니스의 예로 나온다.
[^mcp]: MCP(Model Context Protocol): Anthropic이 2024년 공개한 개방 규격. 에이전트가 외부 서비스의 도구·데이터를 같은 방식으로 찾고 부르게 한다. 이 글에서는 `outputSchema`로 반환 타입을 알려 주는 점이 중요하다.
[^gemini]: Gemini: Google DeepMind의 대형 언어 모델 계열. 저자가 일하는 회사의 모델이고, 예제는 그 Interactions API로 짰다.
[^quickjs]: QuickJS: 파브리스 벨라르(Fabrice Bellard)가 만든 작은 내장형 JavaScript 엔진. 모델이 쓴 코드를 격리해 돌리는 런타임으로 원문 주석에 추천된다.
[^isolatedvm]: isolated-vm: Node.js에서 V8 격리 공간을 따로 만들어 코드를 돌리는 라이브러리. `node:vm`보다 강한 격리가 필요할 때 쓰는 대안으로 나온다.
[^factory]: Factory: 소프트웨어 개발용 AI 에이전트 'Droid'를 만드는 회사. Droid 1.0을 Code Mode로 바꾼 뒤의 성능·비용 수치를 이 글이 인용한다.
[^codex]: OpenAI Codex: OpenAI의 코딩 에이전트(CLI 포함). 이 글에서는 Code Mode를 싣고 있는 하니스의 예다.
[^tbench]: Terminal-Bench: 에이전트가 터미널에서 실제 작업을 해내는지 재는 벤치마크. Factory의 정확도 수치가 이 벤치마크 4판 기준이다.
[^pydanticai]: Pydantic AI: 데이터 검증 라이브러리 Pydantic 팀이 만든 파이썬 에이전트 프레임워크. Code Mode 비슷한 도구를 지원하는 예로 나온다.
[^langchain]: LangChain: LLM 앱·에이전트를 짜는 오픈소스 프레임워크. 역시 Code Mode 비슷한 도구를 지원하는 예로 나온다.
