## 한눈에 보기

모델 비용을 줄이려면 무엇부터 따져야 할까? 보통은 "어느 모델이 싸고 쓸 만한가"부터 묻는다. 이 글은 한 걸음 앞에서 묻는다. 이 단계에 모델이 필요하기는 한가?

| 항목 | 내용 |
|---|---|
| 핵심 주장 | 가장 큰 비용 손잡이는 모델을 부르느냐 마느냐다. 모델 선택은 그다음이다 |
| 흔한 실수 | 시제품에서 모델 호출이 잘 되니 입력 검증·형식 변환·라우팅까지 전부 모델에 맡긴다 |
| 판단법 | 단계마다 세 질문을 차례로 던지고 처음 맞는 곳에서 멈춘다 |
| 세 갈래 | 규칙은 코드가, 정해진 보기에서 고르는 일은 결정 호출이 맡는다. 모델에는 열린 일만 간다 |
| 모델을 쓸 때 | 품질 하한을 넘는 가장 싸고 빠른 모델. 새 모델이 나오면 골든 평가 세트로 먼저 시험한다 |
| 첫걸음 | 호출량이 많은 워크플로 하나를 골라 그중 얼마가 애초에 모델이 필요 없었는지 잰다 |

## 먼저, '결정 호출'이란 무엇인가

참고: [Structured outputs on Amazon Bedrock](https://aws.amazon.com/blogs/machine-learning/structured-outputs-on-amazon-bedrock-schema-compliant-ai-responses/)

이 글에는 '제약된 결정 호출(constrained decision call)'이라는 낯선 말이 나온다. 무엇일까? 모델에게 글을 쓰게 하지 않고 미리 정해 둔 보기 중 하나만 고르게 하는 호출이다.

예를 들어 보자. 고객 문의를 네 개 창구(결제·기술·계정·기타) 중 하나로 보내야 한다. 모델에게 "어느 창구로 보낼까요?"라고 그냥 물으면 어떻게 될까? "결제 문제로 보입니다만, 계정 쪽일 수도 있습니다" 같은 문장이 돌아온다. 코드는 이 문장을 다시 해석해야 한다. 그 사이에 틀릴 구멍이 생긴다.

결정 호출은 답의 꼴을 묶는다. 구조화 출력(structured outputs)[^bedrock]으로 JSON 스키마를 주고 답은 그 안의 보기 중 하나여야 한다고 못 박는다. 여기에 '모르겠음(unsure)'이라는 보기를 하나 더 둔다. 모델이 자신 없으면 그걸 고르고 그 건은 더 큰 모델이나 사람에게 넘긴다.

| | 그냥 생성 | 결정 호출 |
|---|---|---|
| 모델이 내는 것 | 자유로운 문장 | 보기 중 하나 (예: `billing`) |
| 코드가 할 일 | 문장을 해석해 창구 이름을 뽑아냄 | 값을 그대로 씀 |
| 자신 없을 때 | 그럴듯한 문장으로 얼버무림 | `unsure`를 고르고 위로 넘김 |
| 출력 토큰 | 수십에서 수백 개 | 몇 개 |

아래는 보통 방식과 이 글이 권하는 방식을 파이썬으로 옮겨 비교한 것이다. 원문의 예시는 Step Functions 설정(JSON)과 JSON 스키마다. 흐름이 한눈에 보이도록 파이썬 의사 코드로 바꿔 적었다.

```python
# 보통 방식: 모든 단계를 모델에 맡긴다
def handle(msg, order_no):
    # 1) 주문번호 형식 검사 — 모델 왕복 1번
    ok = llm(f"이 주문번호가 'ORD-' 뒤 숫자 8자리 형식인가? {order_no}")
    if "아니" in ok:              # 문장을 다시 해석해야 한다
        return "주문번호를 확인해 주세요"
    # 2) 의도 분류 — 모델 왕복 1번, 답은 자유 문장
    intent = llm(f"이 문의를 결제/기술/계정/기타 중 어디로 보낼까? {msg}")
    queue = parse_queue(intent)   # 문장에서 창구 이름을 뽑는 취약한 코드
    # 3) 답장 초안 — 모델 왕복 1번 (여기만 진짜 모델이 필요하다)
    return llm(f"{queue} 창구 상담원으로서 답장을 써라: {msg}")
    # 요청 1건마다 모델 3번, 지연도 세 번 쌓인다
```

```python
# 이 글이 권하는 방식: 규칙 → 결정 호출 → 모델
import re
ORDER = re.compile(r"^ORD-\d{8}$")          # 모델이 한 번 써 주고, 사람이 검토해 커밋한 규칙
QUEUES = ["billing", "technical", "account", "other", "unsure"]

def handle(msg, order_no):
    if not ORDER.match(order_no):           # 1) 규칙: 모델 0번, 1ms 미만
        return "주문번호를 확인해 주세요"
    if re.search(r"refund|환불", msg, re.I):  # 2) 빠른 길: 키워드로 끝나는 건 코드가 처리
        queue = "billing"
    else:                                   # 남은 것만 결정 호출 — 작은 모델, 답은 보기 중 하나
        queue = small_llm(msg, enum=QUEUES)
        if queue == "unsure":               # 자신 없으면 위로 넘긴다
            queue = big_llm(msg, enum=QUEUES[:-1])
    return llm(f"{queue} 창구 상담원으로서 답장을 써라: {msg}")  # 3) 열린 일만 모델
    # 대부분의 요청이 모델 1번(답장)으로 끝난다
```

달라진 건 모델이 판단해야 하는 곳에만 모델이 남았다는 점 하나다.

## 왜 쓸데없는 모델 호출이 쌓이나

처음에는 다 시제품에서 시작한다. 한 단계에 모델을 붙였더니 잘 돌아간다. 그러면 다음 단계에도 붙인다. 입력 검증, 요청 본문 형식 바꾸기, 경로 고르기까지 모델이 맡는다. 시제품 단계에서는 호출 수가 적어서 아무도 비용을 모른다.

실서비스로 가면 사정이 달라진다. 필요 없는 모델 호출의 값을 치르기 시작한다.

1. 돈. 값어치 낮은 단계라도 요청 수만큼 비용이 는다.
2. 시간. 모델 호출 하나가 수백 밀리초다. 사슬로 엮으면 그만큼 지연이 쌓인다.
3. 들쭉날쭉함. 같은 입력에 다른 답이 나온다. 시험이 어려워지고 감사가 느려진다.

새 모델이 나올 때마다 "어느 모델로 바꿀까"를 두고 또 논쟁하는 것도 덫이다. 그 앞의 질문, 이 단계에 모델이 필요한가는 아무도 묻지 않는다. AWS의 비용 지침(Well-Architected 생성형 AI 렌즈[^wa])도 모델 고르기에서 시작한다. 이 글은 그보다 한 칸 앞에서 출발한다.

## 단계마다 던지는 세 가지 질문

워크플로의 단계 하나하나를 붙잡고 아래 세 질문을 차례로 던진다. 처음으로 "예"가 나오는 곳에서 멈춘다.

1. 성공했는지를 규칙으로 확인할 수 있나? 형식, 스키마, 키워드, 숫자 범위 같은 것. 규칙이 일부만 해결하면 그 규칙을 '빠른 길'로 먼저 돌린다.
2. 모델이 규칙을 한 번만 써 줄 수 있나? 정규식이나 JSON 스키마를 모델이 초안으로 쓰고 사람이 검토해 커밋한다.
3. 정해진 보기 중 하나를 고르는 일인가? 경로, 분류, 예·아니오 같은 것.

셋 다 "아니오"면 그 단계는 열린 일이다. 그때만 알맞은 크기의 모델로 보낸다.

원문의 예시인 고객지원 도우미 다섯 단계를 이 질문에 태워 보면 이렇다.

| 단계 | 어느 질문에서 멈추나 | 어디서 돌리나 |
|---|---|---|
| 주문번호 형식 확인 | 1번. 규칙으로 성공을 확인할 수 있다 | API Gateway[^apigw] 요청 검증 또는 Lambda[^lambda] 함수 |
| 의도별로 메시지 보내기 | 1번이 일부만 해결. '환불' 같은 키워드는 빠른 길로, 나머지는 3번으로 | Step Functions[^sfn] Choice 상태, 나머지는 결정 호출 |
| 택배사 메일에서 송장번호 뽑기 | 2번. 모델이 정규식을 한 번 써 주면 된다 | 커밋한 정규식을 Lambda에서 |
| 티켓을 네 창구 중 하나로 | 3번. 정해진 보기에서 고른다 | 결정 호출. 자신 없으면 큰 모델로 |
| 고객에게 보낼 답장 쓰기 | 셋 다 아니오. 열린 일이다 | Bedrock 모델 중 요구를 만족하는 가장 작은 것 |

그러면 규칙으로 될 일을 모델에 맡기면 무엇을 잃나? 원문의 비교를 옮긴다.

| | 결정적 코드 | 모델 호출 |
|---|---|---|
| 호출당 비용 | 대개 몇 자릿수 싸다 | 토큰당 과금. 규모가 커지면 무시 못 한다 |
| 지연 | 한 자릿수 밀리초 이하 | 수백 밀리초 |
| 잘 정의된 규칙의 정확도 | 적힌 규칙 그대로 정확하다 | 높지만 오류율이 0은 아니다 |
| 감사 | 규칙이 소스 저장소에 있다 | 감사인에게 설명하기 어렵다 |
| 시간이 지나면 | 내가 고치기 전까지 그대로다 | 모델 버전을 옮기거나 옛 버전이 없어지면 바뀐다 |

모델은 환각(hallucination)도 하고 같은 입력에 다른 답도 낸다. 온도(temperature)를 0으로 두면 덜하다. 그래도 똑같은 출력을 보장하지는 않는다. 규칙에는 이 두 문제가 없다. 그래서 규제가 있는 업무는 규칙을 좋아한다.

합격 시험을 규칙으로 쓸 수 있으면 그 단계도 대개 규칙으로 쓸 수 있다. 원문이 내놓는 시금석인데 꽤 쓸 만하다. "답이 맞았는지 코드로 판정할 수 있나?"를 물어보면 된다.

## 생성하지 말고 고르게 하라

라우팅이나 분류는 규칙과 생성 사이 어딘가에 있다. 규칙 하나로 모든 경우를 가를 수는 없다. 그렇다고 글을 지어낼 필요도 없다. 미리 정한 보기 중 하나만 고르면 된다.

이런 단계에는 부품을 따로 쓴다. 출력을 허용된 답으로 묶고 언제 위로 넘길지 신호를 주는 부품이다. 자신 있는 답은 그대로 가고 자신 없는 답은 위로 올라간다. AWS에서 이걸 만드는 길은 이렇다.

1. 작은 Bedrock 모델 + 구조화 출력. 답을 보기(enum)로 묶고 `unsure`를 보기에 넣는다. 다만 이건 모델이 스스로 매긴 판단이지 보정된(calibrated) 점수가 아니다. 위로 넘기는 기준으로 쓰기 전에 정답이 붙은 데이터로 확인해야 한다.
2. 임베딩 유사도. 입력을 임베딩해 가장 가까운 라벨 예시를 고른다. 유사도 점수를 넘김 신호로 쓴다. 그 threshold는 라벨 데이터로 정한다.
3. Strands Decider[^decider]. 실험 단계의 오픈소스 결정 모델(Apache 2.0)이다. 보기에서 고르거나 기준표로 점수를 매기고 답마다 보정된 확신도를 함께 준다. README에 따르면 짧은 분류 과제에서 확신도 0.9 이상인 답은 약 95%가 맞았다. 실험 모델이니 내 데이터로 다시 확인하라고 원문은 덧붙인다. SageMaker[^sagemaker] 엔드포인트 같은 곳에 직접 올려 쓴다.
4. SageMaker에서 직접 학습한 분류기. 라벨 데이터가 있으면 클래스별 확률을 싸고 빠르게 낸다.

원문의 JSON 스키마는 위 파이썬 예시의 `QUEUES`와 같다. 창구 넷에 `unsure`를 더한 다섯 보기로 답을 묶는다. Bedrock은 스키마의 모든 객체에 `additionalProperties: false`를 요구한다는 점도 짚는다.

넷 중 무엇을 쓰든 원칙은 같다. 넘김 신호는 내 라벨 데이터로 검증하고 threshold도 거기서 정한다. 그리고 환불 한도 같은 권한 결정은 규칙에 남겨 둔다. 모델이 "환불해도 된다"고 고를 수는 있다. 얼마까지 해 줄지는 코드가 정한다.

## 결정적 빠른 길

비용 패턴은 흔히 모델끼리의 라우팅을 다룬다. 싼 모델로 갈까, 비싼 모델로 갈까. 빠른 길(fast path)은 그보다 한 층 앞에 있다. 결정적 검사를 먼저 돌리고 규칙이 못 가른 것만 모델로 보낸다.

의도 라우팅이 좋은 예다. 메시지 상당수에는 헷갈릴 것 없는 신호가 있다. '환불', '비밀번호 재설정' 같은 말이다. 키워드 일치 검사는 이걸 한 자릿수 밀리초 안에 가른다. 규칙이 요청의 95%를 해결하면 모델을 더 싼 걸로 바꾸기도 전에 모델까지 가는 건 20건 중 1건으로 준다. 이 숫자는 셈을 보이려는 예시일 뿐 실측치는 아니라고 원문도 밝힌다.

하루 요청 100만 건으로 셈을 이어 보자(노트에서 붙인 예시다).

| | 모든 요청을 모델로 | 빠른 길 95% |
|---|---|---|
| 모델까지 가는 요청 | 1,000,000건 | 50,000건 |
| 코드가 끝내는 요청 | 0건 | 950,000건 |
| 모델 비용 | 100 | 5 |

모델 단가를 반으로 깎는 협상보다 모델을 부르지 않는 쪽이 비용을 훨씬 크게 줄인다.

AWS에서는 이미 있는 부품으로 조립한다.

- API Gateway 요청 검증: 잘못된 입력을 계산이 돌기 전에 돌려보낸다.
- Step Functions Choice 상태: 모델을 부르기 전에 갈래를 나눈다. 원문 예시는 JSONata[^jsonata] 식으로 '환불'과 '비밀번호 재설정'을 정규식으로 잡아 곧장 코드 흐름으로 보내고 나머지만 결정 호출로 넘긴다.
- Lambda: Choice 상태로는 모자란 검증·스키마 검사를 맡는다.
- 결정 호출이나 Bedrock 모델: 남은 것만 받는다.

모델이 규칙을 한 번 써 주게 하는 길도 있다. 매번 모델을 돌리는 대신 정규식이나 JSON 스키마 초안을 한 번 쓰게 한다. 사람이 검토하고 커밋한다. 그 뒤로는 규칙의 속도와 값으로 돈다.

여기에는 단서가 붙는다.

- 모델이 쓴 정규식은 맞는 입력과 틀린 입력으로 시험한다. `(a+)+`처럼 반복을 겹친 꼴은 피한다. 어떤 입력에서는 일치 검사가 한없이 느려진다. 정규식 서비스 거부 공격(ReDoS)이라 부른다.
- 규칙을 설정 파일에 둔다면 정규식·스키마 검사·키워드 목록·범위 검사처럼 정해진 부품만 허용한다. 설정 파일에서 임의의 코드를 실행하게 두면 안 된다.

생성이 꼭 필요할 때도 구조화 출력을 쓰면 응답이 스키마에 맞게 온다. 따로 파싱 코드를 짤 필요가 없다. 다만 스키마에 맞는다고 내용까지 맞는 건 아니다. 숫자 범위나 길이 제한은 여전히 코드로 검사한다.

## 모델을 써야 한다면 크기를 맞춰라

모델이 꼭 필요한 단계라면 무엇을 고를까? 품질 하한을 넘는 것 중 가장 싸고 빠른 모델이다. 가장 새것이거나 가장 큰 것이 아닐 때가 많다. 비교하기 전에 요구부터 적는다.

- 품질 하한: 받아들일 수 있는 최소 품질. 골든 평가 세트(golden evaluation set), 즉 정답이 붙은 과제 예시 모음으로 잰다.
- 비용 상한: 요청 하나, 또는 성공한 결과 하나에 낼 수 있는 최대 금액.
- 지연 목표: 사용 경험이 견딜 수 있는 p95나 p99 응답 시간.
- 규정 제약: 데이터 저장 위치 같은 조건. 후보를 아예 빼 버리기도 한다.

Bedrock은 여러 모델 계열과 크기를 한 API 뒤에 둔다. 그래서 연동을 바꾸지 않고 과제마다 크기를 맞출 수 있다. 지능형 프롬프트 라우팅(Intelligent Prompt Routing)은 같은 계열 안에서 요청마다 알맞은 모델로 보낸다. 모델 증류(Model Distillation)는 큰 모델의 지식을 내 용도에 맞게 작고 싼 모델로 옮긴다.

새 최전선(frontier) 모델이 나오면 모델 회사는 넓은 벤치마크로 성능을 잰다. 내 업무는 다르다. 과제 하나에 품질 하한 하나다. 큰 모델이 그 과제를 더 잘하지 못하면서 비용과 지연만 늘릴 수도 있다. 그러니 바꾸기 전에 내 골든 평가 세트와 지연 목표로 먼저 시험한다.

## 모델 선택을 '시험을 거친 설정'으로 다뤄라

원문은 모델 선택을 코드처럼 다루라고 한다.

1. 과제마다 골든 평가 세트를 두고 지속적 통합(CI)에서 돌린다.
2. 내 요구로 문을 건다. 더 싼 모델이 품질 하한 아래로 떨어지면 회귀(regression)로 본다.
3. 모델을 설정 플래그 뒤에 둔다. 바꿨다가 문제가 생기면 되돌릴 수 있게.
4. 알맞은 채점자를 쓴다. 규칙은 정답 데이터로 확인한다. 모델 판정(model-as-judge)은 열린 출력에만 쓴다.
5. 표류(drift)를 지켜본다. 규칙이 처리한 요청 일부를 그림자 모드(shadow mode)로 모델에도 흘려 본다. 둘의 답이 갈리기 시작하면 그 단계를 다시 분류한다.

다섯 번째가 재미있다. 규칙도 낡는다. 고객이 쓰는 말이 바뀌면 '환불' 키워드가 놓치는 문의가 늘어난다. 모델에게 일을 맡기지 않고 감시자로 옆에 세워 두면 규칙이 언제 낡았는지 알 수 있다.

## 실제로 해 보기

원문이 권하는 순서는 이렇다.

1. 계측한다. 호출마다 결정적 코드, 결정 호출, 모델 호출 중 무엇인지 꼬리표를 단다. 성공한 결과 하나당 비용을 잰다.
2. 규칙을 코드로 옮긴다. 규칙으로 확인할 수 있는 단계를 Lambda나 Step Functions로 돌린다. 대개 이게 가장 크고 안전한 이득이다.
3. 결정 호출을 넣는다. 보기에서 고르는 단계는 자신 없을 때 위로 넘기는 호출로 바꾼다.
4. 모델을 바꾸기 전에 시험한다. 새 모델은 골든 평가 세트를 통과해야 기본값이 된다.

## 맺으며

규칙은 결정적 코드로, 정해진 보기는 결정 호출로, 열린 일은 크기를 맞춘 모델로. 원문의 마지막 당부는 짧다. 어느 모델을 쓸지 묻기 전에 이 단계에 모델이 필요한지부터 물어라.

읽고 나니 망치 이야기가 떠오른다. 망치를 처음 손에 쥐면 모든 게 못으로 보인다고 한다. LLM이 그 망치다. 이 글도 망치를 내려놓으라고 하지는 않는다. 못이 아닌 것에는 드라이버를 쓰자는 얘기다. 그리고 무엇이 못인지는 "정답을 코드로 판정할 수 있나?"라는 질문 하나로 대부분 가려진다.

[^bedrock]: Amazon Bedrock — AWS의 생성형 AI 서비스. 여러 회사의 모델을 한 API로 부른다. 이 글에서는 결정 호출(구조화 출력)과 크기를 맞춘 모델을 돌리는 곳이다.
[^wa]: AWS Well-Architected — AWS가 내는 설계 모범 사례 모음. 생성형 AI 렌즈와 에이전트 AI 렌즈가 있다. 이 글은 생성형 AI 렌즈에서 모델 크기 맞추기를, 에이전트 AI 렌즈에서 확신도에 따른 단계별 넘김을 인용한다.
[^apigw]: Amazon API Gateway — HTTP API의 입구를 만들어 주는 AWS 서비스. 이 글에서는 요청 형식이 틀리면 계산을 돌리기 전에 막는 검증 단계로 쓴다.
[^lambda]: AWS Lambda — 서버 없이 함수 하나를 올려 실행하는 AWS 서비스. 이 글에서는 규칙(검증·정규식·스키마 검사)을 돌리는 곳이다.
[^sfn]: AWS Step Functions — 여러 단계를 상태 기계로 엮는 워크플로 서비스. Choice 상태는 조건에 따라 다음 단계를 고르는 갈림길이다. 이 글에서는 모델을 부르기 전에 키워드로 갈래를 나누는 빠른 길이다.
[^jsonata]: JSONata — JSON 데이터를 질의하고 변환하는 식 언어. Step Functions에서 조건식을 쓸 때 고를 수 있다. 이 글의 예시에서 메시지에 '환불'이 들어 있는지 정규식으로 검사한다.
[^decider]: Strands Decider — 실험 단계의 오픈소스 결정 모델. GitHub의 strands-labs 조직에 공개돼 있다([저장소](https://github.com/strands-labs/strands-decider)). 이 글에서는 결정 호출의 한 선택지로 소개된다. 답과 함께 보정된 확신도를 준다.
[^sagemaker]: Amazon SageMaker AI — 모델을 학습시키고 엔드포인트로 올려 서비스하는 AWS 서비스. 이 글에서는 Strands Decider나 직접 학습한 분류기를 올리는 곳이다.
