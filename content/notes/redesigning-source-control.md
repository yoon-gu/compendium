## 한눈에 보기

코딩이 더는 병목이 아니게 되자, 사람 속도에 맞춰 만든 개발 인프라가 병목이 됐다. Anthropic은 git을 고치는 대신 "클라이언트는 늘 온라인"이라는 전제에서 버전 관리 시스템을 새로 설계했다.

| 항목 | 내용 |
|---|---|
| 문제 | 하루 병합 변경 2,500건(2026년 5월) → 30,000건 이상(9월). git 미러 수백 대로 버티다 한계 |
| 규모 | main 이력 약 100GB, 압축 작업 사본 25GB 이상, CI 체크아웃 하루 약 2,500만 회. 그대로 받으면 하루 600PB 넘는 git 트래픽 |
| 해법 | 사내 버전 관리 시스템 Scion[^scion]. 서버가 이력·커밋·병합을 맡고 클라이언트는 필요한 파일만 받는다 |
| 함께 만든 것 | 코드 리뷰 도구 Antique[^antique], 코드 검색, 소스 컨트롤 IAM, 리뷰된 코드를 대량으로 병합하는 새 방식 |

| 결과 | 인프라 CPU·메모리 200분의 1, 체크아웃 분 → 초, CI CPU 25% 여유, 캐시 적중률 99% 이상 |
| 교훈 | 엔지니어의 일은 Claude[^claude]에게 "아니오"라고 말하는 설계 판단 쪽으로 옮겨 갔다 |

## 먼저, 모노레포와 git의 체크아웃 문제

배경 자료: [git-scm.com — git clone](https://git-scm.com/docs/git-clone), [git sparse-checkout](https://git-scm.com/docs/git-sparse-checkout)

모노레포(monorepo)는 회사의 여러 서비스와 라이브러리를 저장소 하나에 모아 두는 방식이다. 의존성을 한곳에서 관리하고 변경 하나로 여러 프로젝트를 함께 고칠 수 있어 구글, 메타 같은 큰 회사들이 써 왔다.

git[^git]은 분산(decentralized) 버전 관리 시스템이다. `git clone`을 하면 전체 이력이 로컬로 내려오고, 그 뒤에는 서버 없이도 커밋·로그·blame을 할 수 있다. 사람이 노트북에서 일할 때는 이게 장점이다. 문제는 저장소가 크고 체크아웃하는 쪽이 사람이 아니라 하루 수천만 번 도는 CI 작업과 에이전트일 때다.

| | git (분산, 오프라인 우선) | Scion (서버 중심, 온라인 전제) |
|---|---|---|
| 클라이언트가 받는 것 | 전체 이력(또는 shallow·sparse로 줄인 일부) | 지금 읽을 트리와 파일만, 필요할 때 |
| 커밋·병합·리베이스 | 클라이언트에서 | 서버에서 (변경 크기에 비례한 비용) |
| 이력·blame 조회 | 로컬 저장소가 있어야 | API로 바로 (체크아웃 없이) |
| 저장 단위 | 패키지 파일(packfile)로 묶음, 정기 정리 필요 | 내용 주소 기반 객체, 패키지 정리 없음 |
| 확장 방법 | 미러·시드를 늘려 부하 분산 | 서버를 수평으로 늘림. 어디에도 전체 사본 없음 |

얕은 클론(shallow clone)은 최근 이력만, 희소 체크아웃(sparse checkout)은 일부 디렉터리만 받는 git 기능이다. Anthropic도 이런 기능과 사내 미러를 다 써 봤지만 병합량이 늘수록 운영이 버거워졌다.

CI 작업 하나가 "어느 커밋에서 테스트가 깨졌는지" 찾는 상황을 두 방식으로 비교해 보면 차이가 잘 보인다. 아래는 옮긴 이가 지어낸 파이썬 예시다. 원문에는 코드가 없고 `scion` API 이름도 가상이다.

```python
# git 방식: 이력을 찾으려면 먼저 저장소를 받아야 한다
subprocess.run(["git", "clone", "--filter=blob:none", "--no-checkout", REPO, "repo"])  # 수 GB, 수 분
subprocess.run(["git", "-C", "repo", "sparse-checkout", "set", "services/billing"])
subprocess.run(["git", "-C", "repo", "bisect", "start", BAD, GOOD])
# bisect 단계마다 체크아웃과 테스트를 반복한다
# 작업 하나가 받는 데이터: 이력 메타데이터 전체 + 단계마다 바뀐 파일
# 이런 작업이 하루 수백만 번이면 미러 서버가 트래픽을 감당해야 한다

# Scion 방식(가상 API): 이력은 서버에 묻고, 파일은 테스트가 읽는 것만 받는다
changes = scion.log(path="services/billing", since=GOOD, until=BAD)   # 서버 RPC 한 번
for c in bisect_order(changes):
    with scion.virtual_checkout(c.id, paths=["services/billing"]) as wc:  # 읽는 파일만 내려옴
        if run_tests(wc): ...
# 작업 하나가 받는 데이터: 변경 목록 + 테스트가 실제로 연 파일
# 자동 되돌리기(revert)처럼 체크아웃이 아예 필요 없는 작업도 많다
```

## 들어가며 — 코딩은 더 이상 병목이 아니다

Anthropic에서는 Claude가 연구를 반복하고, 프로그램을 최적화하고, 서비스를 빠르게 만든다. 그러자 병목이 다른 곳으로 옮겨 갔다. 소스 컨트롤, 빌드, CI처럼 사람 규모에 맞춰 만든 개발 인프라다.

모노레포에 하루 병합되는 변경은 2026년 5월 약 2,500건에서 9월 30,000건 이상으로 10배 넘게 늘었다. 저자들은 병목 하나를 없애면 산출이 더 늘어나므로 이 증가가 계속될 거라고 본다. 그래서 사내 버전 관리 시스템 Scion을 만들고 다섯 달 만에 모노레포를 git에서 옮겼다. 같은 기간에 코드 리뷰 도구, 코드 검색, IAM, 리뷰된 코드를 대량으로 병합하는 새 방식도 함께 만들었다.

## 모노레포가 커지자 생긴 일

Anthropic은 대부분의 회사보다 Claude를 훨씬 많이 써서 소프트웨어를 만들기 때문에 확장 한계에 먼저 부딪힌다. 숫자가 그 규모를 보여 준다.

- main 브랜치 이력이 100GB에 가깝다.
- 압축한 작업 사본만 25GB가 넘는다.
- CI 체크아웃이 하루 약 2,500만 번 일어난다.
- 아무 요령 없이 받으면 하루 600PB가 넘는 git 트래픽이 된다.

그래서 얕은 클론, 희소 클론, promisor 원격(partial clone에서 빠진 객체를 나중에 받아 오는 원격), 사내 미러, 블롭 저장소에 둔 시드 같은 우회책을 다 썼다. 가장 많을 때는 사내 미러를 수백 대 돌렸지만 병합 속도가 오를수록 운영이 어려워졌다.

핵심 깨달음은 이것이다. 이 저장소의 클라이언트는 거의 전부 늘 온라인인 에이전트와 작업이다. git이 자랑하는 오프라인 우선 성질이 오히려 발목을 잡고 있었다.

> 해설 — git은 서버 없이도 커밋하고 이력을 볼 수 있게, 그러니까 오프라인에서 일하는 개발자를 위해 설계됐다. 2005년 리눅스 커널 개발에는 맞는 전제다. 하지만 클라이언트가 데이터센터 안의 CI 작업과 에이전트라면 전체 이력을 매번 복제하는 건 낭비다. 전제가 바뀌면 같은 도구가 장점에서 짐으로 뒤집힌다는 좋은 예다.

## 에이전트 규모 소스 컨트롤의 원칙 여섯 가지

저자들은 구글의 Piper[^piper]와 메타의 Sapling[^sapling] 같은 선례를 밝히며 원칙 여섯 가지를 세운다.

1. 클라이언트는 늘 온라인이다. 서버에 닿을 수 있다고 보고 데이터는 필요할 때 받는다.
2. 클라이언트와 서버는 비대칭이다. 이력, blame, 커밋, 병합, 리베이스는 서버가 맡는다. 클라이언트는 크기가 정해진 캐시와 작업 사본 파일만 들고 있어 받는 데이터가 훨씬 적다.
3. API가 빠짐없다. 모든 조회를 프로그램으로 할 수 있어서 자동 bisect나 자동 revert처럼 로컬 저장소가 필요 없는 작업이 많다.
4. 수평으로 확장된다. 데이터는 흩어져 있고 어디에도 저장소 전체 사본이 없다. 패키지 파일 정리도 필요 없다.
5. 커밋은 싸고, 증분이고, 잠금이 없다. 커밋은 서버에서 일어나고 비용은 변경 크기에 비례한다. 전역 상태는 확장의 적이라 main과 릴리스 브랜치 말고는 ref를 쓰지 않도록 권한다.
6. 작업 사본은 선택이고 희소하다. 많은 CI 작업과 쓰기 작업은 체크아웃 자체를 건너뛴다. 희소·가상 체크아웃은 실제로 읽는 파일만 내려받는다.

## Scion은 어떻게 동작하나

### 데이터 구조

기본 단위는 쓰기 앞 로그(write-ahead log)에 쌓이는 체인지셋(changeset)이다. git 커밋은 트리 전체를 가리키지만, 체인지셋은 첫 번째 부모에 비해 바뀐 파일만 나열하고 각 파일 내용은 내용 주소(content-addressed) 포인터로 가리킨다. 병합 커밋을 첫 번째 부모 기준으로 저장하는 건 취향의 문제인데, 트렁크 기반 모노레포에서는 main 줄기의 이력이 주로 중요하기 때문이라고 원문 각주가 밝힌다.

체인지셋은 서버에서 높은 처리량으로 만들어진다. 패키지 파일도, 잠금도, ref 이동도 없다. ref가 있긴 하지만 하나를 옮기는 일은 Spanner[^spanner] 행 하나에 대한 비교 후 교환(compare-and-swap) 한 번이다.

blame, 경로별 이력, 커밋 그래프 건너뛰기 리스트(skip list) 같은 파생 데이터는 하나의 일반적인 재귀 방식으로 계산한다. 덕분에 새 파생 데이터를 쉽게 추가할 수 있고(나중에 경로 기반 파일 검색 인덱스도 이렇게 붙였다), 미리 계산할지 나중에 계산할지 고를 수 있고, 내부 구현을 바꿔도 클라이언트는 영향을 받지 않는다.

### 확장

소수의 서버가 모든 소스 컨트롤 조회에 답한다. 내용 주소 데이터는 절대 바뀌지 않으니 어느 서버든 캐시해도 되고, 그래서 서버들은 거의 서로 조율할 필요 없이 수평으로 늘어난다.

처음에 Scion은 메타데이터 조회만 맡았다. 나중에 자체 클라이언트 `scn`과 파일 내용을 주고받는 자체 프로토콜이 생겼다. git의 fetch는 주고받을 객체를 협상한 뒤 큰 패키지 파일 하나로 보내지만, `scn`은 클라이언트가 원하는 트리와 블롭만 재귀적으로, 끊겨도 이어서 받을 수 있게 가져온다. 그래서 희소·가상 체크아웃에 특별한 지원이 필요 없다.

구조는 세 층이다.

| 층 | 역할 |
|---|---|
| scion-daemon | 노드마다 하나. 그 노드의 모든 작업이 쓸 객체를 들고 있다 |
| scion-cache | 지역별 캐시 서버. daemon의 요청을 받는다 |
| scion-server | 원본 서버. Spanner나 클라우드 저장소에서 읽는다 |

층 사이 경계를 엄격하게 지켜 장애가 번지지 않게 했다. 결과는 이렇다.

- 층마다 캐시 적중률이 99%를 넘고 오래 남는 상태가 없다.
- 예전 git 미러 인프라보다 CPU와 메모리를 200분의 1만 쓴다.
- CI와 연구용 체크아웃이 분 단위에서 초 단위로, 약 100배 빨라졌다.
- CI의 CPU 용량이 25% 남게 됐다.

## Scion을 만들며 배운 것

### 작은 팀의 빠른 이전

일곱 명이 Scion, Antique와 관련 시스템을 만들고 다섯 달 만에 이전을 끝냈다. 그사이 병합량은 10배로 늘었다. 저자들은 이런 방식이 다른 곳으로도 퍼질 거라고 본다. 팀이 Scion을 만들기 시작한 시점은 Claude Mythos Preview[^mythos]와 Claude Tag[^tag]가 사내에서 쓰이기 시작한 무렵이다.

### 엔지니어의 역할이 바뀐다

엔지니어들은 Claude가 자신들보다 코드를 더 잘 쓴다고 판단한다. 대신 그들은 시스템 수준의 설계 판단을 맡는다. 일의 상당 부분이 Claude에게 "아니오"라고 말하는 것, 그러니까 에이전트가 과하게 설계하거나 제약을 어길 때 막는 일이었다고 한다. 에이전트끼리 서로 검토하게 하는 방식(adversarial review)은 근시안적일 수 있어서, 사람 리뷰어는 모든 줄 대신 변경의 의도에 집중한다.

### 품질과 최적화

코드베이스는 철저히 테스트한다. 외부에 의존하지 않는(hermetic) 시뮬레이션, 퍼징(fuzzing), 속도 제한을 갖췄다. 저자들은 Scion을 자신들이 다뤄 본 코드베이스 중 가장 잘 테스트되고 방어된 축에 든다고 말한다.

Claude는 전문가가 며칠 걸렸을 최적화를 찾아냈다. Claude Mythos Preview의 초기 내부 버전에게 손으로 짠 git → Scion 수집(ingestion) 파이프라인 시제품을 다시 쓰게 했더니, 기존 수집 순서 불변식을 지키면서 메모리는 20분의 1, 속도는 4배가 됐다.

### 보안

Scion은 저장소 단위 접근 제어와 디렉터리별 권한을 지원한다. 리뷰 도구 Antique는 승인 규칙을 의미 단위로 표현할 수 있어서, 사소한 변경과 민감한 변경을 다르게 다룰 수 있다.

### 운영

팀은 Claude Tag로 시스템을 지켜본다. Slack 채널마다 Claude 하나를 붙여 한 구성 요소의 건강만 보게 하는데, 원문은 이를 '슈퍼팬(superfan)' Claude라고 부른다. 예를 들어 scion-daemon 담당, scion-cache 담당, Antique 병합 큐 담당이 따로 있다. 이들은 텔레메트리와 로그를 보고 대시보드의 이상한 패턴을 찾아, 전통적인 알림이 놓치는 미묘한 문제를 잡아낸다.

### 사람 규모의 작업 방식 다시 보기

전통적인 병합 큐와 전역 잠금은 에이전트 규모에서 통하지 않는다. 팀은 병합 뒤 테스트와 배포 전 테스트에 기대고, 동시에 들어온 변경끼리 충돌할 수 있다는 걸 받아들인다. 충돌이 나도 사람이 알아채기 전에 Claude가 보통 먼저 고친다.

> 해설 — 이 절이 글에서 가장 일반화하기 좋은 대목이다. "병합 전에 모든 걸 막는다"는 사람 규모의 안전장치가 변경이 하루 3만 건이면 그 자체로 병목이 된다. 대신 병합 뒤에 빨리 잡고 빨리 고치는 쪽으로 옮겨 갔다. 고치는 주체도 에이전트라 가능한 선택이다. 다만 원문은 이 방식의 실패율이나 되돌린 비율 같은 수치는 내놓지 않는다.

## 더 넓은 생태계에 기여하기

Scion은 git을 대신하는 범용 도구가 아니다. 엔지니어가 수만 명이거나 에이전트가 아주 많은 초대형 모노레포에 맞는다. 저자들은 Anthropic의 사내 토큰 사용량이 유난히 많다는 점도 인정한다.

Scion을 공개하는 건 현실적이지 않다고 한다. git과 갈라진 데다 리뷰·검색·CI 도구를 따로 갖춰야 하기 때문이다. 대신 생각을 공유해 git 사용자들이 일부를 가져다 쓸 수 있게 하겠다고 한다. 서버 쪽 RPC, 새 서버 구조, 고친 협상 프로토콜, 조합 가능한 희소·얕은 기능이 그 후보다. 20년 가까운 git 커뮤니티의 작업에 감사를 표하고, GitHub[^github], GitLab[^gitlab], 오픈소스 커뮤니티와 협력하고 싶다고 맺는다.

## 정리

이 글의 요지는 "클라이언트가 바뀌면 인프라의 전제도 바뀐다"이다. git은 오프라인에서 일하는 사람을 위해 설계됐고, Anthropic의 클라이언트는 늘 온라인인 에이전트와 CI 작업이었다. 그래서 이력과 연산은 서버로 옮기고, 클라이언트는 읽는 파일만 받고, 병합 전 잠금 대신 병합 뒤 복구를 택했다. 일곱 명이 다섯 달 만에 이걸 해냈다는 사실은 그 자체로 에이전트 시대의 개발 속도를 보여 준다.

다만 읽을 때 염두에 둘 점도 있다. 성능 수치는 모두 Anthropic이 직접 잰 것이고, 그림의 세부 값은 본문에 나오지 않는다. Scion은 공개되지 않으므로 같은 결과를 바깥에서 재현할 방법은 없다. 대부분의 팀에게 쓸모 있는 건 시스템 자체보다 원칙 여섯 가지, 특히 "체크아웃이 필요 없는 작업은 체크아웃하지 말라"와 "전역 상태를 줄여라"일 것이다.

[^claude]: Claude — Anthropic의 AI 모델. 이 글에서는 코드를 쓰는 주체이자 운영 감시를 맡는 에이전트로 나온다.
[^scion]: Scion — Anthropic이 만든 사내 버전 관리 시스템. 서버가 이력과 커밋을 맡고 클라이언트(`scn`)는 필요한 파일만 받는다. 공개되지 않았다.
[^antique]: Antique — Scion과 함께 만든 사내 코드 리뷰 도구. 병합 큐와 의미 단위 승인 규칙을 갖췄다.

[^piper]: Piper — 구글의 사내 버전 관리 시스템. 초대형 모노레포를 서버 중심으로 다루는 선례로 언급된다.
[^sapling]: Sapling — 메타가 공개한 소스 컨트롤 시스템. 대형 저장소를 위한 선례로 언급된다.
[^spanner]: Spanner — 구글 클라우드의 전 세계 분산 데이터베이스. Scion은 ref 이동을 Spanner 행 하나의 비교 후 교환으로 처리한다.
[^mythos]: Claude Mythos Preview — Anthropic의 Claude 모델 미리보기판. 이 글에서는 내부 초기 버전이 수집 파이프라인을 다시 써서 메모리 20분의 1, 속도 4배를 냈다.
[^tag]: Claude Tag — Slack에서 Claude를 쓰게 해 주는 Anthropic 제품. 이 글에서는 구성 요소마다 붙은 '슈퍼팬' Claude가 시스템을 감시한다.
[^github]: GitHub — git 저장소 호스팅 서비스. 저자들이 협력하고 싶은 상대로 꼽는다.
[^gitlab]: GitLab — git 저장소 호스팅·DevOps 플랫폼. 저자들이 협력하고 싶은 상대로 꼽는다.
