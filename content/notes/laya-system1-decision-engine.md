## 문제의식: System 1에 System 2를 쓰고 있다

지원 티켓이 들어왔을 때, 메일이 도착했을 때, API에 프롬프트가 들어왔을 때 실제로 필요한 답은 대개 구조화된 짧은 것들이다 — 어느 부서로 보낼까, 피싱인가, 탈옥 시도인가, 긴급도는 0-3 중 어디인가.

여기에 8B·70B·프런티어 생성 모델을 부르는 것은 과하다는 게 출발점이다. 토큰이 흘러나오기를 500-2,000ms 기다리고, 추론 비용을 내고, 자유 형식 텍스트에서 라벨을 뽑으려 정규식이나 JSON 파서를 붙여야 한다. 더 나쁜 것은 신뢰도다. LLM이 `"confidence: 0.95"`를 출력할 때 그것은 **확신 있어 보이는 토큰을 예측한 것**일 뿐 수학적 캘리브레이션(calibration)은 없다.

그래서 필요한 것은 인간 뇌의 System 1처럼 동작하는 모델 — 30-35ms 안에 끝나는 반사적 결정과, 정직한 확률.

## 세 가지 결정 원형

Laya는 임의의 상태(원문 텍스트, 이메일, 티켓, JSON 문서)에 대해 타입이 정해진 질문들을 **단일 forward pass**로 평가한다.

- **choice** — 기준 딕셔너리에서 하나 고르기. 선택된 키, 전체 선택지에 대한 확률 분포, 캘리브레이션된 신뢰도를 반환
- **score** — 서열 루브릭(0, 1, 2, …) 위에 놓기. 기대 등급과 등급 분포, 신뢰도 반환
- **noul** — 참/거짓 질문. P(true)를 0.0-1.0으로 반환 (P(false)는 정의상 1 - P(true))

출력 공간이 확률과 숫자뿐이라 모델은 텍스트를 생성하지 않고, 따라서 환각도, 스키마 위반이나 깨진 JSON도 **구조적으로 불가능**하다. 이 부분이 이 접근의 실질적인 장점이다.

## 체크포인트 세 개

| 체크포인트 | 백본 | 파라미터 | 컨텍스트 | 강점 |
|---|---|---|---|---|
| `convaiinnovations/laya` | ModernBERT-large | 421M | 512 | 영어 분류, 가드레일, 메일 분류 |
| `convaiinnovations/laya-multilingual` | mmBERT-base (256k vocab) | 322M | 1024 (최대 8k) | 100개 이상 언어, 2.2배 빠름, 교차언어 NLI |
| `convaiinnovations/laya-typed-decisions` | ModernBERT-large | 421M | 1024 | 에이전트 관측, 고객 서비스, 인보이스, 보안 알림 |

세 개를 한 저장소에 묶어 두고 Hugging Face의 `allow_patterns`로 필요한 서브폴더만 내려받게 했다 — 2.5GB 전체 대신 다국어 모델만 647MB.

## 가장 값진 대목: 신뢰도는 경고해 주지 않는다

MASSIVE 벤치마크 51개 언어 스윕(선택지 20개, 무작위 기준선 0.050)에서 나온 결과가 이 글에서 가장 실용적인 부분이다. 영어 BPE 어휘(5만 토큰)를 가진 ModernBERT-large는 비라틴 문자를 제대로 토큰화하지 못하는데, **정확도가 무너져도 신뢰도는 멀쩡하다.**

| 언어 | 정확도 | 평균 신뢰도 |
|---|---|---|
| 크메르어 | 0.000 | 0.952 |
| 아르메니아어 | 0.050 (= 무작위) | 0.885 |
| 히브리어 | 0.060 | 0.964 |
| 벵골어 | 0.080 | 0.945 |
| 힌디어 | 0.100 | 0.941 |

크메르어는 100문항 중 하나도 못 맞히면서 95% 확신을 보고한다. 51개 언어 전체에서 영어 체크포인트의 평균 신뢰도는 정확도가 82%든 0%든 **0.885 아래로 내려가지 않는다.**

결론은 명확하다. 신뢰도 기반 게이팅(confidence gating)으로는 이 실패를 잡을 수 없고, 어느 모델을 쓸지는 forward pass **이전에** 결정해야 한다. 캘리브레이션을 파는 제품이 자기 모델의 신뢰도가 언제 무의미해지는지를 이렇게 드러내 놓는 것은 드문 일이다.

그래서 붙인 것이 순수 파이썬 라우터다. 들어온 텍스트의 유니코드 문자 체계(데바나가리, CJK 한자, 키릴, 아랍, 히브리, 타밀, 태국 등 22종)를 살피고 라틴 문자면 불용어 분포를 본다. 오버헤드는 영어 0.09ms, 인도계 문자 0.54ms, 200행짜리 중첩 JSON 0.73ms — 33ms forward pass에 비하면 2% 미만이다. `Router(preload=True)`로 모델을 메모리에 상주시키면 언어가 번갈아 들어올 때 생기는 7-10초 콜드 스왑도 사라진다.

## 성능 주장

제작사가 제시하는 대표 수치는 이렇다.

- 지연: 질문 1개 P50 **32.8ms**, 10개 배치 72.3ms(질문당 7.2ms)
- 캘리브레이션 오차(ECE): 0.081
- 실제 워크플로: Enron 스팸 필터링 0.993, 피싱 탐지 0.980, ToxicChat 가드레일 0.755-0.762(선택적 커버리지 50%에서 0.931), RAG 패시지 관련성 0.657, 10방향 티켓 라우팅 0.522
- 51개 언어 중 45개에서 무작위 기준선의 3배 이상

라이선스는 Apache 2.0, 가중치는 safetensors로 공개, `pip install laya`, 자체 호스팅이라 API 과금 없음.

## 저자가 스스로 적은 한계

이 글에 신뢰를 주는 절이다. 세 가지를 명시한다.

1. **선택지 20개를 넘으면 무너진다.** Banking77(77개 라벨)에서 0.425. 선택지들이 192-256 토큰의 `head_max_len` 예산을 나눠 쓰기 때문에 후보당 3-4 토큰밖에 남지 않는 구조적 제약이다. 권고는 choice 스키마를 20개 이하로 두거나 coarse-to-fine 2단계로 쪼개라는 것.
2. **제로샷 모델이 아니다.** 기본 모델의 typed-decisions 점수는 약 0.35로 사실상 무작위 수준이고, 0.766은 해당 벤치마크의 train split으로 파인튜닝해서 얻은 값이다. 전지적 제로샷 오라클이 아니라 특화시켜 쓰는 빠른 기반 모델로 보라고 말한다.
3. **온도 보정이 필요하다.** 기본 가중치는 raw temperature logit 상태로 배포되며, 질문 유형별로 스칼라 온도 하나를 자기 도메인 분포에 맞춰 적합시키면 ECE가 0.466에서 0.081로 떨어진다. 즉 위에 적힌 0.081은 **보정을 거친 뒤의 숫자**다.

## 읽을 때 감안할 점

이 글은 논문이 아니라 제작사 창업자가 쓴 제품 발표 겸 우선권 주장 글이다. 몇 가지는 구분해서 읽는 게 좋다.

- 서사의 절반은 "내가 2025년 3월(arXiv:2503.23303)과 9월(arXiv:2510.01237)에 먼저 했는데, 2026년 9월에 자금을 갖춘 프런티어 랩 TypeSafe AI가 Jev를 내놓으며 새로운 돌파구인 양 말했다"는 우선권 주장이다. 판단은 원 논문들을 직접 보고 하는 편이 낫다.
- 경쟁 제품(Jev)과의 표 비교에서 **Laya 쪽 수치는 자체 측정, Jev 쪽은 제3자 연구와 TypeSafe 발표치**라고 본문이 밝히고 있다. 같은 조건에서 나란히 돌린 값이 아니다.
- 비교 항목 선정도 유리한 쪽으로 기울어 있다. 실제로 Jev가 크게 앞서는 Banking77(0.870 대 0.425)은 비교표가 아니라 한계 절에 들어가 있다.
- 지연 비교는 자체 호스팅 GPU 대 API 호출이라 네트워크 왕복이 포함된 숫자와 아닌 숫자를 견주는 셈이다. 32.8ms가 "내 GPU에서의 forward pass"라는 점을 기억할 것.

그럼에도 핵심 논지 — 고빈도 분류·가드레일·라우팅·트리아지에 생성 모델을 부르는 것은 낭비이고, 인코더 기반 결정 모델이 더 맞는 도구다 — 는 벤치마크 숫자와 별개로 설득력이 있다. 그리고 다국어 라우팅 절의 "못 읽는 문자에도 0.9 이상 확신한다"는 관찰은 Laya를 쓰지 않더라도 분류 모델을 다국어 트래픽에 태우는 사람이라면 알아 둘 값어치가 있다.
