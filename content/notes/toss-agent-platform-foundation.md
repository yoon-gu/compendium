## 한눈에 보기

"지난달과 같은 기준으로 이번 달 데이터도 비교해줘."

데이터를 다루는 팀이 자주 받는 요청이다. 지난번 쿼리를 찾아 기간을 바꾸고 다시 돌린다. 빠진 데이터는 없는지, 집계 기준은 그대로인지도 본다. 토스 AI Platform 팀은 이 반복을 에이전트에게 맡기고 싶었다.

걸림돌은 둘이었다. 첫째, 토스는 「전자금융감독규정」의 망분리(network separation) 요건에 따라 금융 업무를 처리하는 내부망과 인터넷 환경을 나눠 운영한다. 분석할 데이터는 내부망에 있고 밖으로 옮길 수 없다. 그러니 에이전트가 내부망 안에서 직접 코드를 돌려야 한다. 그렇다고 내부망 전체를 열어 줄 수는 없다. 모델이 쓴 코드가 상관없는 데이터를 읽거나 파일을 잘못 고칠 수 있다. 프롬프트로 조심하라고 일러두는 것으로는 못 막는다.

둘째, 이어서 일할 수 있어야 한다. "지난달과 같은 기준"을 알려면 지난번 코드와 기준이 남아 있어야 한다. 매번 빈 환경에서 시작하면 사용자가 코드와 기준을 다시 챙겨야 한다.

글의 제목은 이 둘을 두 마디로 담았다. 실행은 가두고, 대화는 잇는다.

| 요구 | 토스의 답 |
|---|---|
| 모델이 쓴 코드는 정해진 곳만 만져야 한다 | 사용자마다 Pod 하나, 그 안에서 bubblewrap으로 에이전트마다 하니스를 따로 가둔다 |
| 파일 접근 | 그 에이전트의 작업 폴더와 허용한 폴더, 현재 세션 상태 경로만 연결. 참고 자료는 읽기 전용 |
| 통신 | 하니스의 네트워크는 Pod와 분리. 나가는 요청은 Runtime 프록시와 OpenSandbox egress 정책 두 단계로 거른다 |
| 인증정보 | 하니스는 실제 키 대신 대체값을 쓰고, 프록시가 나가는 길에 진짜 키로 바꾼다 |
| 이어서 일하기 | 작업 파일과 세션 상태를 영속 볼륨에 둔다. 같은 하니스는 자기 상태를 직접 읽어 이어 간다 |
| 지난 대화 보기, 다른 하니스로 넘기기 | 하니스와 상관없는 공통 실행 기록(OpenResponses 형식)을 따로 남긴다 |

## 먼저, 하니스와 샌드박스란 무엇인가

참고: [하니스 엔지니어링 101 정리 노트](/compendium/notes/harness-engineering-101/), [bubblewrap README](https://github.com/containers/bubblewrap), [OpenSandbox README](https://github.com/opensandbox-group/OpenSandbox)

모델은 글만 내놓는다. "이 코드를 돌려 봐" 하고 말할 수는 있어도 스스로 프로세스를 띄우거나 파일을 고치지는 못한다. 모델의 답을 읽고 도구를 실제로 실행할 프로그램이 따로 있어야 한다. 실행 결과를 다시 모델에 건네는 것도 이 프로그램이다. 이 프로그램을 하니스(harness)라고 한다. 코드에서 오류가 나면 오류 내용을 모델에 돌려주고 모델이 고친 코드를 다시 돌리는 것도 하니스 몫이다. 하니스 엔지니어링 101의 말을 빌리면 모델은 뇌, 하니스는 몸이다.

문제는 몸이 너무 자유로울 때다. 하니스가 돌리는 코드는 모델이 쓴 코드다. 셸 명령 한 줄이면 아무 파일이나 읽을 수 있다. 그래서 하니스를 샌드박스(sandbox), 곧 허락한 것만 보이는 울타리 안에서 돌린다.

토스가 쓴 울타리 도구는 두 겹이다.

- OpenSandbox[^opensandbox]: AI 에이전트용 오픈소스 샌드박스 런타임. Kubernetes[^k8s] 위에 샌드박스(여기서는 사용자별 Pod)를 만들고 지운다. 샌드박스마다 egress(밖으로 나가는 통신) 정책을 건다. 인증 프록시도 있어서 실제 인증정보를 샌드박스 안에 두지 않고도 외부 서비스를 부를 수 있다.
- bubblewrap[^bwrap]: 리눅스 네임스페이스(namespace)로 프로세스 하나를 가두는 작은 도구. 네임스페이스는 프로세스마다 보이는 파일시스템 연결(마운트), 프로세스 목록, 네트워크를 따로 둘 수 있게 하는 리눅스 기능이다. README가 스스로 밝히듯 bubblewrap은 정해진 보안 정책을 가진 완성품 샌드박스가 아니다. 어떤 인자를 넘기느냐가 곧 보안 수준이다.

| 항목 | 그냥 Pod 안에서 하니스 실행 | 토스 방식 (Pod + bubblewrap) |
|---|---|---|
| 보이는 파일 | Pod 안의 모든 파일, 다른 에이전트 작업물까지 | 자기 작업 폴더, 허용 폴더, 현재 세션 상태만 |
| 참고 자료 | 실수로 고칠 수 있음 | 읽기 전용 연결, 셸로 고쳐도 파일시스템이 거부 |
| 네트워크 | Pod의 네트워크를 그대로 씀 | Pod와 분리, 정해진 프록시 소켓 하나로만 나감 |
| API 키 | 환경변수에 그대로, 코드가 읽고 로그에 샐 수 있음 | 대체값만 보임, 진짜 키는 프록시가 끼움 |
| 권한 | Pod 사용자 권한 그대로 | 낮춘 사용자, capability 제거, 격리 실패하면 실행 중단 |

원문에는 코드가 없다. 아래는 차이를 보이려고 독자에게 익숙한 파이썬으로 옮겨 적은 예다. bubblewrap 인자는 실제 옵션이지만 토스의 실제 설정은 공개되지 않았다. 먼저 그냥 돌리는 경우다.

```python
# 하니스가 모델이 쓴 코드를 Pod 안에서 그대로 실행한다
import os, subprocess

def run_tool(code: str, agent: str) -> str:
    env = {**os.environ, "DOCS_API_KEY": "sk-live-..."}   # 진짜 키가 환경변수에
    r = subprocess.run(["python", "-c", code], env=env,
                       cwd=f"/workspace/{agent}", capture_output=True, text=True)
    return r.stdout + r.stderr
# cwd 는 출발점일 뿐이다. open("/workspace/문서-agent/draft.md", "w") 도 된다
# os.environ 을 print 하면 키가 결과와 로그에 남는다
# requests.get("http://아무-내부-주소") 도 Pod 네트워크로 그대로 나간다
```

다음은 토스가 택한 방향을 흉내 낸 것이다.

```python
# 같은 코드를 bubblewrap 울타리 안에서 실행한다
def run_tool(code: str, agent: str, session: str) -> str:
    cmd = ["bwrap", "--ro-bind", "/usr", "/usr", "--proc", "/proc", "--dev", "/dev",
           "--bind", f"/pv/{agent}/work", "/work",                  # 자기 작업 폴더만 쓰기 허용
           "--ro-bind", "/pv/shared/refs", "/refs",                 # 참고 자료는 읽기 전용
           "--bind", f"/pv/{agent}/sessions/{session}", "/state",   # 현재 세션 상태만
           "--bind", "/run/proxy.sock", "/run/proxy.sock",          # 밖으로 나가는 유일한 길
           "--unshare-net", "--unshare-pid", "--cap-drop", "ALL",
           "--setenv", "DOCS_API_KEY", "PLACEHOLDER",               # 진짜 키는 프록시가 끼운다
           "--chdir", "/work", "python", "-c", code]
    r = subprocess.run(cmd, capture_output=True, text=True)
    return r.stdout + r.stderr
# 다른 에이전트 폴더는 아예 마운트되지 않아 보이지 않는다
# /refs 에 쓰기를 시도하면 도구 종류와 상관없이 파일시스템이 거부한다
```

두 방식은 막는 지점에서 갈린다. 앞의 방식에서 막으려면 도구마다 권한을 따져야 한다. 뒤의 방식은 프로세스가 볼 수 있는 세상 자체를 줄인다. 하니스가 파일 읽기 도구를 쓰든, 셸을 쓰든, 직접 짠 파이썬을 쓰든 같은 제한을 받는다.

## 누가 무엇을 맡나

모델과 도구를 오가는 반복은 기존 하니스에 맡겼다. 플랫폼은 그 바깥을 맡는다. 요청한 사람이 누구인지 확인하고 실행 환경과 접근 권한을 준비한다. 역할을 이렇게 나누면 하니스를 바꿔 끼워도 사용자 관리나 저장소 연결을 다시 만들 필요가 없다.

한 사람이 여러 에이전트와 여러 대화를 하므로 단위를 셋으로 나눴다.

- Workspace: 사용자마다 하나씩 주는 개인 작업 공간
- Agent: 업무 지침과 쓸 도구를 정해 둔 에이전트. 예를 들면 데이터 분석 에이전트, 문서 작성 에이전트
- Session: 한 에이전트와 나누는 대화 하나. 분석 에이전트와 달마다 따로 대화하는 식

대화마다 실행 환경을 새로 만들면 준비와 저장소 연결을 매번 되풀이해야 한다. 토스는 사용자마다 Kubernetes의 실행 단위인 Pod를 하나 만들고 Workspace의 실행 환경으로 계속 쓴다.

사용자가 화면에서 분석을 요청하면 이렇게 흘러간다.

1. Server가 사용자와 리소스 접근 권한을 확인한다.
2. Runner가 그 Workspace의 실행 환경을 준비하고 Runtime에 실행 설정을 넘긴다.
3. Runtime이 설정대로 하니스를 가둔 뒤 실행한다.

Server와 Runner는 Workspace Pod 밖에서 돈다. 하니스는 업무에 필요한 입력과 도구만 받고 플랫폼 DB 인증정보는 받지 않는다. 분석 코드를 돌리는 데 다른 사용자의 설정이나 플랫폼 관리 기능까지 만질 권한은 필요 없으니까.

## 왜 에이전트마다 VM을 두지 않았나

한 Pod를 같이 써도 에이전트마다 볼 수 있는 파일은 달라야 한다. 분석 에이전트는 참고 문서를 읽어야 한다. 문서 작성 에이전트의 작업 파일은 고쳐서는 안 된다. 화면에서 도구 목록을 숨기거나 파일 읽기 도구에서만 권한을 확인하는 건 소용이 없다. 하니스는 셸 명령이나 직접 짠 프로그램으로 같은 파일을 열 수 있다.

가장 단단한 답은 에이전트마다 가상 머신(VM)을 따로 두는 것이다. 그러면 게스트 커널까지 나뉜다. 대신 VM마다 이미지와 작업 볼륨을 준비해야 한다. VM을 만들고 지우는 일도 플랫폼의 실행 흐름에 엮어야 한다.

토스에 필요한 건 그보다 좁았다. Workspace 실행 환경은 그대로 다시 쓰면서 그 안에서 하니스마다 파일과 통신 범위만 다르게 주면 됐다. 기존 Kubernetes와 OpenSandbox 구성은 두고 bubblewrap으로 하니스를 가뒀다.

| 방식 | 장점 | 플랫폼이 떠안는 일 |
|---|---|---|
| 에이전트마다 VM | 게스트 커널까지 따로 쓰는 격리 | VM 생성과 종료, 이미지 준비, 작업 볼륨 연결을 실행 흐름에 연동 |
| Workspace Pod 안에서 네임스페이스 | 기존 Workspace 안에서 하니스마다 파일·네트워크 범위를 줄 수 있음 | 하니스별 파일·네트워크·실행 권한 설정, 격리가 제대로 되는지 검증 |

원문은 대가도 숨기지 않는다. 호스트 커널을 함께 쓰므로 VM 같은 커널 격리는 아니다.

## 울타리 세 개

Runtime은 하니스를 띄울 때 세 가지를 묶는다.

첫째, 파일. 실행에 필요한 기본 파일 말고는 세 곳만 마운트한다. 그 에이전트의 작업 폴더, 사용자가 따로 허용한 폴더, 현재 세션의 상태가 저장된 경로다. 다른 에이전트의 작업 폴더나 다른 세션의 상태 경로는 처음부터 연결하지 않는다. 참고 자료처럼 고칠 일이 없는 경로는 읽기 전용으로 붙인다. 그러면 파일 쓰기 도구는 물론 파이썬이나 셸로 고치려 해도 파일시스템이 거부한다. 나중에 새 도구를 붙여도 같은 울타리 안에서 돌면 같은 제한을 받는다.

둘째, 프로세스와 네트워크. PID 네임스페이스로 하니스가 볼 수 있는 프로세스 목록을 가린다. 네트워크도 따로 떼어 Pod의 네트워크를 직접 쓰지 못하게 한다. 밖으로 나가야 하는 HTTP(S) 요청은 Runtime이 주는 프록시로만 보낸다.

셋째, 실행 권한. 하니스는 권한을 낮춘 사용자로 돈다. 리눅스가 프로세스에 주는 특수 권한인 capability도 걷어 내서 하니스가 울타리 설정을 바꾸지 못하게 한다. 울타리를 세우다 실패하면 실행을 멈춘다. 설정이 꼬였다고 울타리 없이 돌려 버리면 정해 둔 제한이 아무 의미가 없어지기 때문이다.

원문은 여기서 선을 하나 긋는다. 접근 제한이 결과 검증을 대신하지는 못한다. 이 구조는 허락하지 않은 파일과 시스템을 막는다. 쓰기를 허락한 폴더 안에서 파일을 잘못 고치거나 지우는 일까지 막지는 못한다. 분석 결과가 맞는지도 따로 봐야 한다.

## 같은 에이전트의 대화끼리는 무엇을 나누나

에이전트끼리 나눠 놓은 다음엔 한 에이전트의 여러 대화가 무엇을 같이 쓸지 정해야 했다. 대화마다 작업 폴더를 따로 주면 파일 충돌은 줄어든다. 하지만 지난 대화에서 만든 코드를 새 대화로 복사해야 하고 어느 사본이 최신인지 사용자가 챙겨야 한다.

토스는 파일과 대화 상태를 다르게 다뤘다.

- 작업 파일은 같은 에이전트의 대화들이 함께 쓴다. 지난달 대화에서 만든 compare.py를 새 대화에서 바로 읽고 돌릴 수 있다. 한 대화에서 고치면 다른 대화에서도 고친 파일을 쓴다.
- 대화 상태는 세션마다 따로 둔다. 기존 대화를 이어 가면 저장된 상태를 쓴다. 새 대화에는 지난 대화에서 정한 분석 조건이 저절로 넘어가지 않으니 조건이나 작업 요약을 알려 줘야 한다.

지난 대화를 열어도 파일이 그때 버전으로 돌아가지는 않는다. 여러 대화에서 같은 파일을 동시에 고치면 충돌할 수 있다.

## 도구는 부르되 키는 넘기지 않는다

분석에는 Workspace 파일만이 아니라 업무 시스템의 데이터도 필요하다. 하니스를 업무 도구에 잇되 필요한 서비스에만 닿게 했다.

갇힌 하니스의 HTTP(S) 요청은 전용 유닉스 도메인 소켓(Unix domain socket)을 지나 Runtime HTTP 프록시로 간다. 유닉스 도메인 소켓은 IP 네트워크를 거치지 않고 같은 호스트의 프로세스끼리 잇는 통로다. 하니스에게 Pod 네트워크를 열어 주지 않고도 정해진 프록시로만 요청을 보낼 수 있다. 하니스가 프록시 환경변수를 무시해도 소용없다. 하니스의 네트워크가 애초에 Pod와 떨어져 있어 직접 나갈 길이 없다.

통신은 두 단계로 거른다.

1. Runtime HTTP 프록시가 목적지를 보고 Pod 자기 주소처럼 하니스가 닿아서는 안 되는 곳을 막는다.
2. OpenSandbox의 egress 정책이 업무 서비스 쪽으로 나가는 요청 가운데 허용할 목적지를 정한다.

허용할 업무 서비스는 환경마다 다르니 egress 정책도 환경에 맞춰 따로 잡아야 한다. 모델은 GenAI Gateway를, 업무 도구는 MCP(Model Context Protocol) Gateway를 거쳐 부른다. MCP는 에이전트가 외부 도구를 부를 때 쓰는 인터페이스다. 도구가 무엇을 할 수 있는지 확인하고 부르는 방식을 정해 둔다.

키는 어떻게 다룰까? 실제 API 키를 하니스 환경변수에 넣으면 하니스가 돌린 코드도 그 값을 읽는다. 디버깅하려고 환경변수를 찍었다가 로그나 결과 파일에 키가 섞일 수도 있다. 서비스를 부르려면 키가 필요하지만 하니스가 그 값을 알 필요는 없다. 토스는 여기에 OpenSandbox 인증 프록시를 썼다.

1. 하니스는 요청 헤더에 진짜 키 대신 대체값을 넣는다.
2. Runtime HTTP 프록시가 목적지를 검사하고 요청을 넘긴다.
3. OpenSandbox 인증 프록시가 미리 정한 목적지로 보낼 때 그 헤더의 대체값을 진짜 인증정보로 바꾼다.

하니스는 키를 한 번도 받지 않고 서비스를 부른다. 이 방식은 OpenSandbox 인증 프록시가 지원하는 HTTP(S) 연동에만 쓴다. 모든 CLI나 개인 구독 인증정보를 같은 식으로 다루는 건 아니다.

키를 숨겼다고 쓸 권한까지 줄지는 않는다. 하니스는 프록시를 통해 그 키로 허용된 기능을 그대로 쓸 수 있다. 그래서 Gateway는 모델과 도구 사용 권한을, 업무 서비스는 그 계정의 데이터 접근 권한을 따로 확인해야 한다. 문서 검색 서비스를 쓸 권한이 있어도 그 안의 문서 하나를 읽을 권한은 따로다. 에이전트가 읽은 데이터를 접속이 허용된 서비스로 내보내는 일도 이 구조만으로는 다 막지 못한다. 무엇을 읽을 수 있는지, 어디에 닿을 수 있는지, 거기서 무엇을 할 수 있는지를 함께 정해야 한다.

## Pod가 바뀌어도 이어 가려면

샌드박스 실행 환경은 배포나 장애로 언제든 바뀐다. Pod가 사라져도 작업 파일과 대화 상태는 남아야 한다. 둘은 영속 볼륨(Persistent Volume, PV)에 둔다. PV는 Pod와 따로 살아 있는 저장소다. 새 Pod가 뜨면 이 볼륨을 다시 붙여 기존 파일과 상태를 쓴다. 다만 파일로 저장한 결과는 돌아와도 끝난 프로세스의 메모리는 돌아오지 않는다. 메모리에만 있던 중간 계산은 다시 해야 한다.

그럼 대화 상태에는 무엇을 남겨야 할까? 화면에 보이는 질문과 최종 답만으로는 모자란다. 모델이 조회 도구를 여러 번 불렀다면 어느 결과가 어느 호출에서 나왔는지도 알아야 다음 요청을 처리한다. 긴 대화를 압축한 요약처럼 하니스가 안에서 관리하는 정보도 필요하다.

처음엔 플랫폼에 저장한 대화 기록을 하니스 형식으로 바꿔 세션을 되살렸다. 플랫폼 기록만으로 상태를 다시 만들 수 있다는 장점이 있었다. 반면 변환 코드는 하니스의 저장 형식과 처리 규칙을 따라가야 했다. 하니스가 도구 호출과 결과를 잇는 방식을 바꾸면 변환 코드도 함께 고쳐야 했다.

그래서 방향을 틀었다. 같은 하니스로 대화를 이어 갈 때는 그 하니스가 저장한 상태와 세션 ID를 그대로 다시 쓴다. 플랫폼은 상태가 저장된 경로만 기록해 뒀다가 다음 실행에 붙여 준다. 내부 상태를 플랫폼이 재구성하지 않고 하니스가 자기 상태를 직접 읽게 한 것이다. 저장된 상태를 못 찾으면 오류를 낸다. 이전 상태를 못 읽었는데 대화를 이어 가면 사용자는 앞서 정한 분석 조건이 반영됐다고 오해할 수 있다.

호환성 문제가 사라지진 않는다. 하니스 버전이 바뀌면 옛 상태를 읽을 수 있는지 확인해야 한다. 그래도 하니스 내부 형식을 플랫폼이 흉내 내고 관리하는 부담은 줄었다.

원문이 말하는 '이어 간다'에는 범위가 있다. 저장된 파일과 대화 상태를 바탕으로 다음 요청을 처리한다는 뜻일 뿐이다. 실패한 작업을 멈춘 지점부터 다시 돌리거나, 고친 파일을 옛 버전으로 되돌리거나, 외부 서비스에서 이미 처리한 일을 되돌리지는 않는다. 데이터 백업과 외부 작업의 중복 실행 방지는 따로 다뤄야 한다.

## 기록을 둘로 나눈 이유

대화를 이어 갈 때는 하니스 상태를 쓴다. 그런데 지난 대화를 화면에 보여 줄 때는 이 상태 파일을 읽지 않는다. 하니스마다 저장 형식이 달라서 조회 기능이 형식 변화를 일일이 쫓아가야 하기 때문이다.

하니스가 도는 동안에는 사용자 입력, 도구 호출, 실행 결과를 공통 형식으로도 남긴다. 이것이 공통 실행 기록이다. 메시지와 도구 호출 결과는 OpenResponses[^openresponses] 형식으로 저장하고 하니스가 남긴 원본 이벤트도 같이 둔다. 지난 대화를 볼 때는 이 기록만 읽으면 되니 하니스를 다시 띄울 필요가 없다.

| 하려는 일 | 쓰는 기록 | 처리 방식 |
|---|---|---|
| 같은 하니스로 대화 이어 가기 | 하니스 고유 상태와 세션 ID | 하니스가 저장된 상태를 읽어 다음 요청 처리 |
| 화면에서 지난 대화 보기 | 공통 실행 기록 | 하니스 실행 없이 메시지와 도구 결과 조회 |
| 다른 하니스로 작업 넘기기 | 공통 실행 기록과 허용된 작업 파일 | 인계를 요청하면 요약을 만들어 새 세션에서 시작 |

다른 하니스로 넘길 때는 옛 상태 파일을 쓸 수 없다. 인계를 요청하면 공통 실행 기록을 요약해 새 세션에 건넨다. 옛 세션을 되살리지 않고 요약을 참고해 새 대화를 연다. 예를 들어 지난 분석의 집계 조건과 결과 파일 위치를 넘기면 새 하니스는 그 설명과 허용된 작업 파일을 보고 일을 시작한다. 요약에서 빠진 내용을 확인할 수 있게 원문 기록도 남겨 둔다. 기록을 못 읽으면 요약을 만들지 않고 오류를 낸다.

세션 복원에 실패했다고 이 방식으로 슬쩍 넘어가지도 않는다. 저장된 상태로 이어 갈지, 요약을 들고 새로 시작할지는 요청할 때 사용자가 고른다. 기록을 두 벌 관리하는 수고는 생긴다. 대신 대화 조회와 요약 기능을 하니스마다 다른 형식에 맞춰 만들지 않아도 된다.

## 맺으며

처음 요청으로 돌아가 보자. "지난달과 같은 기준으로 이번 달 데이터도 비교해줘." 이걸 처리하려면 지난번 코드와 결과 파일, 그리고 어떤 기준으로 분석했는지가 남아 있어야 한다. 동시에 그 과정에서 필요한 것보다 많은 파일과 시스템을 열어 주면 안 된다. 토스의 답은 세 줄로 줄어든다.

- 접근 제한: 하니스가 돌리는 코드까지 파일과 네트워크 제한을 받는다.
- 작업 유지: Pod가 바뀌어도 같은 하니스로 대화를 이어 가도록 작업 파일과 대화 상태를 보관한다.
- 공통 기록: 하니스와 상관없이 이력을 보고, 다른 하니스로 넘길 때는 요약을 든 새 세션에서 시작한다.

원문은 곳곳에 선을 그어 둔다. 접근을 막는 것과 결과를 검증하는 것은 다르다. 키를 숨긴다고 권한이 줄지는 않는다. 대화를 이어 간다고 작업까지 되돌리지는 못한다. 울타리를 세운 팀이 그 울타리가 무엇을 못 막는지까지 적어 둔 글이다. 에이전트에게 사내 데이터를 맡기려는 팀이라면 이 목록부터 자기 환경에 맞춰 써 볼 만하다.

토스는 지금 사용자가 에이전트와 같은 작업 공간에서 직접 파일을 고치고 팀원들과 에이전트를 함께 쓰는 기능을 넓히고 있다고 한다. 다음 편은 대화창 밖, 터미널과 팀 업무 도구에서 에이전트를 쓰는 이야기다.
