> 아래는 원문의 절 순서를 따라 요지를 정리하고 해설을 붙인 노트다. 요지 정리와 해설은 옮긴 이의 것이고 전문은 위 링크에서 읽을 수 있다. 저자는 Flask를 만든 사람이고, 지금은 에이전트 하니스(harness) Pi를 만들고 있다.

## 한눈에 보기

저자는 1년 넘게 "커스텀 도구나 MCP 서버를 컨텍스트 창에 잔뜩 싣지 말고 스크립트와 CLI를 쓰라"고 해 왔다. 그런데 Pi 1.0은 MCP를 지원한다. 모순처럼 보이지만, 지원 방식이 Codemode다. 도구를 모델에게 하나씩 보여 주는 게 아니라, 모델이 쓴 코드가 하니스 안에서 도구들을 엮어 부른다.

| | 보통의 도구 호출 | Codemode |
|---|---|---|
| 모델이 보는 것 | 도구 정의 전체(토큰으로 변환되어 컨텍스트를 차지) | 코드를 실행하는 도구 하나 + 코드 안에서 쓸 수 있는 API |
| 큰 출력 | 컨텍스트에 들어오며 잘린다(Pi는 마지막 2,000줄) | 코드가 구조화된 값으로 받아 처리한다 |
| 여러 번 호출 | 한 번에 하나, 매번 왕복 | `Promise.all`로 병렬, 루프로 워크플로 |
| MCP 서버 | 도구 목록이 통째로 노출 | 코드가 필요할 때 찾아 쓴다(점진적 발견) |
| 실행 위치 | 실행 환경(손) | 하니스(뇌) 안의 격리된 런타임 |

## 도구란 무엇인가 (What Are Tools)

하니스는 모델에게 도구 정의를 건네고, 서버는 그것을 토큰 구조로 바꾼다. 모델이 어떤 도구를 언제 부르는지는 강화학습(reinforcement learning)으로 훈련된 결과다. 저자가 CLI와 bash를 선호하는 이유는 둘이다. 프로그램끼리 쉽게 조합되고, 모델이 훈련 과정에서 파일시스템이 어떻게 동작하는지를 이미 배웠기 때문이다.

다만 bash가 조합할 수 있는 것은 실행 가능한 프로그램뿐이다. 이미지를 읽거나 하위 에이전트(sub-agent)를 띄우는 일처럼 하니스가 모델 프로토콜에 직접 무언가를 넣어야 하는 능력은 하니스의 네이티브 도구여야 한다.

## 뇌와 손 (Brains vs Hands)

저자는 하니스를 뇌, 도구가 실제로 실행되는 환경을 손이라고 부른다. 둘은 같은 기계에 있을 수도 있지만 파일시스템과 신뢰 수준이 다르다. 뇌는 신뢰하는 쪽이고, 손은 격리할 수 있는 쪽이다. Gondolin 같은 샌드박스는 bash를 가둘 수 있지만 하니스 자체를 가두지는 않는다.

> 해설 — 이 구분이 글 전체의 전제다. Codemode가 "하니스 쪽에서 코드를 돌린다"고 할 때 그 코드는 손이 아니라 뇌 안에서 도는 것이고, 그래서 뒤에 나오는 강한 격리(네트워크·파일시스템·타이머 없음)가 필요해진다.

## 하니스를 코드로 지휘하기 (Orchestrating The Harness)

Codemode는 모델이 복잡한 작업을 코드로 표현하면 그 코드를 하니스 쪽에서 실행하는 방식이다. Pi에서는 WASM 런타임 안의 QuickJS로 JavaScript를 돌린다. 네트워크도, 파일시스템도, 타이머도 없고 메모리도 제한된다. 바깥으로 나가는 유일한 길은 다른 도구를 부르는 것뿐이다.

저자가 드는 이점은 네 가지다.

- 큰 도구 출력이 컨텍스트에서 잘리지 않고 코드에 구조화된 값으로 들어온다.
- 동시 실행과 간단한 워크플로가 가능하다. 몇 개만 먼저 찔러 보고 나머지를 한꺼번에 처리하는 식이다.
- `store()` 함수로 상태를 트랜스크립트에 남겨 다음 호출에서 쓸 수 있다.
- 이미지 생성이나 일회성 분류처럼 일반 도구로 노출하면 어색한 API를 컨텍스트 낭비 없이 쓸 수 있다.

이름은 Cloudflare가 먼저 쓴 것을 가져왔다고 밝힌다.

> 해설 — 핵심은 "토큰을 아끼자"가 아니라 "컨텍스트를 거치지 않아도 되는 데이터는 거치지 말자"에 가깝다. 100개의 결과를 모델이 읽고 하나씩 판단하는 대신, 코드가 결과를 받아 집계하고 모델에게는 요약만 돌려준다. 모델은 계획을 세우고 코드는 노동을 한다.

## 실제 모습 (What It Looks Like)

예시는 모두 실제 Pi 세션에서 나온 것이고, 코드는 사람이 한 줄도 쓰지 않았다고 한다. Codemode는 MCP를 켜지 않으면 기본으로 꺼져 있고, `defaultTools` 설정으로 켤 수 있다.

### 이미지 생성

쓸 수 있는 이미지 모델을 찾아 텍스트 프롬프트로 이미지를 만들고, 이미지나 텍스트를 돌려주는 스크립트다. 생성된 이미지는 모델에게도 전달되고 디스크에도 임시 산출물로 남는다.

### 분류하기

Jev 분류기로 열린 GitHub 이슈 100개의 감정, 좌절 점수, 이슈 종류를 분석해 저장하고, 가장 좌절한 이슈 12개를 돌려준다. `Promise.all`로 한꺼번에 던져도 안전한 이유는 Pi가 동시 도구 실행을 4개로 제한하고 나머지를 줄 세우기 때문이다.

두 번째 예시는 같은 분류기로 탱크 게임을 30단계 루프로 조종한다. 매 단계 게임 상태를 분류기에 넣고 공격·접근·회피·파워업 중 하나를 고르게 한다. 게임 상태와 분류기 판단 사이를 오가는 루프 패턴을 보여 준다.

### MCP 서버 부르기

MCP 도구는 모델에게 직접 노출되지 않는다. 에이전트는 Codemode API를 통해 도구를 찾아내며, 그래서 점진적 발견(progressive discovery)이 된다. 예시는 Sentry의 조직 목록을 받아 조직마다 프로젝트를 병렬로 조회하는 코드다. 저자는 모델이 Sentry 도구의 모양을 훈련 데이터와 시스템 프롬프트로 이미 알고 있는 듯하다고 본다.

> 해설 — 이슈 100개 예시가 이 글에서 가장 설득력 있다. 보통의 도구 호출이면 100번의 왕복과 100개의 결과가 컨텍스트에 쌓인다. Codemode에서는 한 번의 코드 실행 안에서 병렬로 돌고, 모델이 받는 것은 상위 12개뿐이다.

## 요즘 MCP는 싸움이다 (Modern MCP Is A Fight)

MCP 서버 대부분은 Codemode가 없는 하니스를 겨냥해 만들어졌다. 그래서 Cloudflare를 비롯한 일부 서버는 자기 안에 Codemode를 품고 있다. Pi의 Codemode 안에서 그런 서버를 부르면 "Codemode 안의 Codemode"가 된다. JSON이 두 번 이스케이프되고, 작은 모델은 헷갈리며, 안쪽 코드는 바깥 도구를 부를 수 없다. 저자는 이를 최선은 아니지만 이해할 만한 일이라고 본다.

## MCP에 바라는 것 (MCP Desires)

Codemode와 잘 맞으려면 MCP 서버가 갖춰야 할 것으로 네 가지를 든다.

- 구조화된 JSON 출력. `outputSchema`로 선언하면 가장 좋다.
- 일관된 결과 형태. 배치 크기에 따라 출력 모양이 달라지는 서버는 작은 탐색은 통과하고 본 실행에서 깨진다.
- 큰 바이너리 데이터 지원. 지금은 미리 서명된 URL 같은 우회가 어색하다.
- 여러 MCP 서버를 가로지르는 조합 가능한 도구 검색. 지금은 우연히 되는 수준이고 서버가 늘면 버티지 못한다.

## Codemode의 앞날 (Future of Codemode)

저자는 이것이 예전 CLI 권고를 뒤집는 게 아니라고 말한다. MCP가 자신이 권했던 코드 기반 접근 쪽으로 움직였고, Codemode는 그것을 하니스 안으로 확장한 것이라는 입장이다. 남은 문제도 솔직하게 적는다.

- 내구성(durability): 호출을 스냅샷해 이어 가려면 내구성 워크플로 엔진의 아이디어가 필요할 수 있다.
- 언어 선택: 결정적(deterministic)인 조합 언어로는 JavaScript보다 Starlark가 나을지 모른다.
- 바이너리 데이터와 이미지, 그리고 작은 모델에서 이 패턴이 약하다는 점.

결론은 아직 완성된 답이 아니지만 앞으로 더 쓰게 될 패턴이라는 것이다.

## 읽으며 짚어 둘 점

- 글은 Pi라는 저자 자신의 하니스를 기준으로 쓰였다. 다른 하니스가 같은 격리(QuickJS in WASM, 동시 실행 4개 제한)를 제공하는지는 별개 문제다.
- "Codemode 안의 Codemode" 문제는 MCP 생태계가 아직 이 패턴을 전제하지 않는다는 뜻이다. 지금 당장은 서버마다 궁합이 다를 수 있다.
- 저자가 말하는 이점 가운데 수치로 뒷받침된 것은 없다. 경험에서 나온 설계 주장으로 읽는 게 맞다.

## 남는 생각

CLI를 쓰라는 예전 조언과 Codemode는 같은 생각의 두 모습이다. 모델에게 선택지를 많이 보여 주는 대신 조합의 힘을 주라는 것. 차이는 조합이 일어나는 자리다. CLI는 손(실행 환경)에서, Codemode는 뇌(하니스) 안의 격리된 방에서 조합한다. 이 글이 짚는 대로, 그 방에서 무엇을 어디까지 할 수 있게 할지가 다음 설계 과제다.
