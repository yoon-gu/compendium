## 한눈에 보기

에이전트를 만들면 보통 이렇게 시험한다. 모델을 붙이고 도구 몇 개를 달고 프롬프트 몇 개를 돌려 본 뒤 답을 눈으로 훑는다. 저자들은 이것을 '바이브 체크(vibe check)'라 부른다. 처음에는 이걸로 충분하다. 그러다 한 워크플로의 프롬프트를 고쳤는데 다른 워크플로의 도구 호출이 조용히 망가지는 날이 온다.

| 항목 | 내용 |
|---|---|
| 문제 | 최종 답만 보면 루프, 잘못된 도구 인자, 토큰 낭비, 중복 실행 같은 실패가 안 보인다 |
| 성공 정의 | 핵심 사용자 여정(CUJ)의 조항 하나하나를 평가 지점으로 삼는다 |
| 시나리오 | 사용자 시뮬레이터로 시작해 점점 실제 트래픽으로 바꾼다 |
| 채점 | 1-5점 대신 예/아니요 질문. 품질과 함께 지연·토큰·비용·도구 호출 수를 잰다 |
| Day 0 | 트레이스 5-20개를 사람이 빨간 펜으로 읽는다 |
| Day 1 | 같은 시험을 매번 돌리고, 판정 LLM을 사람 채점에 맞춘다. 손잡이를 하나씩 50-60번 돌린다 |
| Day 2 | PR 병합 관문(성공률 95% 이상, 회귀 0)과 공유 대시보드 |
| 도구 | 오픈소스 agent-eval[^agent-eval], 트레이스는 OpenTelemetry[^otel] + OpenInference[^openinference] |

## 먼저, 에이전트 평가란 무엇인가

참고: [Google ADK 사용자 시뮬레이션 문서](https://adk.dev/evaluate/user-sim/), [agent-eval 저장소](https://github.com/GoogleCloudPlatform/professional-services/tree/main/tools/agent-eval)

챗봇은 질문 하나에 답 하나를 낸다. 평가도 그 답이 맞는지만 보면 된다. 에이전트는 다르다. 답을 내기까지 여러 단계를 거친다. 무엇을 할지 생각한 뒤 도구를 고르고 인자를 채워 부른다. 결과를 읽고 나면 다시 고른다. 이 과정 전체를 기록한 것이 트레이스(trace)다. 같은 최종 답이라도 도구를 두 번 불러 3초 만에 낸 것과 열두 번 불러 40초 만에 낸 것은 전혀 다른 에이전트다.

그래서 에이전트 평가는 세 가지를 함께 본다. 첫째는 답이 맞는지, 둘째는 과정이 옳았는지(올바른 도구를 올바른 순서로, 올바른 인자로 불렀는지), 셋째는 그 과정이 얼마나 비쌌는지다.

| | 바이브 체크 | 체계적인 평가 |
|---|---|---|
| 입력 | 그때그때 떠오른 프롬프트 몇 개 | 고정된 골든 데이터셋(golden dataset)과 시뮬레이션 시나리오 |
| 보는 것 | 최종 답 | 트레이스 전체(추론, 도구 인자, 중간 결과) |
| 채점 | "괜찮아 보이네" | 예/아니요 루브릭, 결정론적 지표, 비용·지연 |
| 비교 | 기억에 의존 | 기준선(baseline)과 수치로 비교 |
| 바뀐 뒤 | 다시 몇 개 돌려 봄 | 같은 시험 묶음을 전부 다시 돌림 |

아래는 두 방식을 파이썬으로 옮겨 본 예시다. 원문에는 코드가 없다. 원문의 사례(거래 불일치 이메일을 처리하는 에이전트)를 옮긴 이가 코드로 꾸몄다. `agent.run`, `judge` 같은 함수는 가상의 것이다.

```python
# 바이브 체크: 최종 답 문자열만 사람 눈에 들어온다. 실행은 1번, 기록은 없다.
reply = agent.run("브로커 메일: 거래 T-8812 가격이 장부와 다릅니다")
print(reply)  # "확인해 보니 ... 회신 초안입니다" → 그럴듯하면 통과
```

```python
# 체계적인 평가: 고정 데이터셋 전체를 돌리고 트레이스를 기준으로 채점한다.
results = []
for case in load_jsonl("golden.jsonl"):             # 튜닝 중에는 이 파일을 건드리지 않는다
    trace = agent.run(case["prompt"], record_trace=True)
    calls = [s for s in trace.steps if s.type == "tool_call"]
    results.append({
        # 결정론적 검사: 코드로 판단할 수 있는 건 코드로
        "found_txn": trace.final.txn_id == case["expected_txn_id"],
        "ledger_before_draft": first_index(calls, "ledger_lookup") < first_index(calls, "draft_reply"),
        # 판정 LLM: 1-5점이 아니라 예/아니요 질문 하나
        "ids_mapped": judge("내부 거래 ID를 브로커 표기로 바꿔 적었는가?", trace) == "YES",
        # 운영 비용: 품질과 같은 줄에 기록한다
        "latency_ok": trace.latency_s <= 30,
        "tool_calls": len(calls),
        "cost_usd": trace.cost_usd,
    })
report(results, baseline="runs/last_green.json")  # 지난 기준선과 지표별로 비교
```

판정 LLM을 쓰는 방식을 'LLM-as-a-judge'라고 한다. 사람 대신 다른 LLM에게 채점 기준을 주어 판정하게 한다. 이 판정자에게는 점수 대신 예/아니요를 물어야 한다. 이 글의 요점 가운데 하나다.

## 출발점: 세 가지 기본 블록

### 1. 핵심 사용자 여정으로 성공을 정의한다

시험은 핵심 사용자 여정(critical user journey, CUJ)에 묶어 둔다. CUJ는 페르소나, 목표, 제약, 검증 조건으로 짠다. 그러면 CUJ의 조항 하나하나가 그대로 평가 지점이 된다.

예로 든 페르소나는 운영 분석가다. 거래 상대방이 보낸 불일치 이메일이 오면 에이전트가 문제의 거래를 찾아 내부 장부와 거래 조건을 대조한 뒤 회신 초안을 쓴다. 회신에는 내부 거래 ID를 브로커 쪽 표기로 바꿔 적어야 한다. 30초 안에, 사람 개입 없이 끝내야 한다는 제약도 붙는다. 검증 지점은 이렇게 나온다. 올바른 거래 ID를 찾았나? 초안을 쓰기 전에 장부를 확인했나? ID를 제대로 바꿨나?

### 2. 시뮬레이션 사용자로 시작해 실제 트래픽으로 옮긴다

CUJ를 정상 경로(happy path) 시나리오와 예외 상황(edge case) 시나리오로 나눈다. 이것을 사용자 역할을 하는 LLM에 넣어 돌린다. Google ADK[^adk]의 사용자 시뮬레이션이 이런 일을 한다. 시나리오에는 첫 메시지(`starting_prompt`)와 사용자가 이뤄야 할 목표(`conversation_plan`), 필요하면 페르소나를 적는다. 그러면 시뮬레이터가 대화 흐름에 맞춰 다음 사용자 발화를 만든다. 에이전트가 정보를 한 번에 묻지 않고 하나씩 물어도 대화가 이어진다. 시간이 지나면 이 합성 시나리오를 실제 운영 트레이스로 바꿔 간다.

### 3. 여러 층에서 잰다

검사는 네 층으로 쌓는다. 단위 테스트, 결정론적 지표, LLM 판정 루브릭, 통합 테스트다. 원문은 이 네 층을 그림으로만 보여 준다. 본문에서 드는 예로 보면 결정론적 지표는 도구 인자나 기준값을 코드로 대조하는 계산 지표다. 판정 루브릭은 "환불 도구를 부르기 전에 계정 ID를 확인했나?" 같은 예/아니요 질문이다. 지연과 토큰 예산은 트레이스에 단언(assertion)을 걸어 검사한다.

## 피해야 할 함정 네 가지

함정 1은 시험을 버려서 기준선을 깨는 일이다. 실행 사이에 시험을 지우거나 바꾸면 결과가 나아졌을 때 에이전트가 좋아진 건지 시험이 쉬워진 건지 알 수 없다. 원문 그림의 표현대로 시험을 지우면 움직이는 건 에이전트가 아니라 기준선이다. 튜닝하는 동안에는 골든 데이터셋을 얼려 두고 한 번에 변수 하나만 바꾼다. 시험은 요구사항이 바뀔 때만 뺀다.

1-5점 판정은 흐릿하다. LLM이 매기는 점수는 실행할 때마다 흔들린다. 이런 판정에 기대면 함정 2에 빠진다. "이 답은 얼마나 도움이 됐나, 1-5점"을 "환불 도구를 부르기 전에 계정 ID를 확인했나, 예/아니요"로 바꾼다. 원문은 도구로 Google의 Adaptive Rubrics를 권한다.

함정 3은 글솜씨만 보고 운영 청구서를 무시할 때 생긴다. 답이 모든 품질 검사를 통과해도 한 번에 40초가 걸리고 쓸데없는 도구 호출을 열두 번 하며 질의 하나에 60센트가 든다면 운영에서는 실패다. 지연, 토큰(프롬프트·추론·완성), API 비용, 도구 호출 횟수를 품질 지표와 나란히 기록한다.

함정 4는 프레임워크마다 평가 파이프라인을 따로 만드는 데서 온다. 트레이스를 OpenTelemetry로 남기고 OpenInference 규약에 맞추면 평가가 특정 오케스트레이션 프레임워크에 묶이지 않는다. LangGraph[^langgraph]로 짰든 ADK로 짰든 직접 만든 런타임이든 파이프라인 하나로 평가할 수 있다.

## Day 0부터 Day 2까지 실제로 들이는 법

오픈소스 도구를 쓰면 설치는 두어 시간이면 끝난다. 정작 시간은 좋은 평가 전략을 세우는 데 든다.

### Day 0: 시나리오, 시뮬레이션, 그리고 '빨간 펜'

주요 CUJ마다 시나리오 초안을 쓰고 시뮬레이션을 돌린다. 이때는 집계 점수 대신 트레이스를 처음부터 끝까지 읽는다. 프롬프트, 추론 단계, 도구 인자, 출력을 다 본다. 에이전트가 머뭇거린 곳, 인자를 지어낸 곳, 도구를 잘못 고른 곳, 말이 길어진 곳에 빨간 펜으로 표시한다. 저자들 말로는 트레이스 20개쯤을 손으로 읽으면 실패 유형을 추측하며 보낼 며칠을 아낀다.

### Day 1: 주기, 신호, 시험 틀

이제 자동화한다. agent-eval이 뼈대를 만들고 여러 턴짜리 대화를 돌린다(HTTP로 `--base-url`을 주거나 오프라인으로). 트레이스를 모으고 Google의 Agent Evaluation 서비스와도 이어 준다. 원문 설명으로는 ADK, LangGraph, 직접 만든 런타임의 트레이스를 모두 받는다.

규칙은 단순하다. 프롬프트든 모델이든 도구 독스트링이든 무엇을 바꾸든 같은 시험 묶음을 다시 돌리고 기준선과 비교한다. 판정 LLM도 검증한다. Day 0에 사람이 채점한 트레이스를 판정자에게 다시 채점시켜 본 뒤 엔지니어의 판단과 맞을 때까지 채점 프롬프트를 다듬는다.

### 튜닝 루프: 다시 쓰기가 아니라 손잡이 돌리기 50-60번

이 단계에서는 작고 잴 수 있는 변경을 되풀이한다. 도구 인자 설명을 분명히 하거나 "이건 하지 마라" 같은 부정 제약을 하나 넣거나 JSON 출력 스키마를 고친다. 한 번에 하나씩이다. agent-eval의 HTML 보고서에는 통과/실패 지표 옆에 지연, 토큰 사용량, API 비용, 캐시 활용, 도구 호출 경로가 함께 나온다. 실패한 턴에는 Gemini[^gemini]가 쓴 원인 분석이 붙는다.

이 단계의 쓸모를 보여 주는 사례가 원문에 있다. 어떤 프롬프트 변경은 몇 개를 찍어 봤을 때 더 똑똑해 보였다. 그런데 시험 묶음을 돌리자 지연이 두 배가 됐고 도구 호출에서 지어낸 인자가 15% 늘었다. 작고 잴 수 있는 변경이 크게 갈아엎기보다 낫다.

### Day 2: 병합 관문과 공유 대시보드

PR 병합 관문은 agent-eval을 Cloud Build나 GitHub Actions에서 자동으로 돌려 만든다. 전체 예/아니요 성공률이 threshold(원문의 예는 **95%**)를 넘어야 한다. 전에 통과하던 핵심 지표는 하나라도 떨어지면 안 된다.

공유 대시보드용으로 트레이스 원본(JSONL), 프롬프트 해시, 모델 버전, 지연 분포, 점수표를 BigQuery나 Cloud Storage로 내보낸다. 그러면 팀 전체가 같은 숫자를 본다.

출시한 뒤에는 실제 트래픽을 출시 전 기준선과 비교한다. 운영에서 실패한 트레이스는 진단하고 좋은 실제 트레이스는 골든 데이터셋으로 올린다. 원문은 후속 글 [The Outer Loop](https://developers.googleblog.com/the-outer-loop-insights-first-an-ambient-quality-agent-that-diagnoses-your-production-agent/)도 함께 소개한다. 운영 트레이스를 자동으로 진단하는 '앰비언트 품질 에이전트'를 다룬 글이다.

## 자주 묻는 질문

원문 끝의 질문 다섯 개를 줄여 옮긴다.

- 바이브 체크의 문제는? 최종 답만 보이고 루프, 잘못된 도구 인자, 토큰 낭비, 중복 실행이 안 보인다.
- 처음부터 어떻게 시작하나? Day 0에는 트레이스 5-20개를 빨간 펜으로 읽는다. Day 1에 자동 검사를 붙이고 Day 2에 CI/CD 관문을 세운다.
- 왜 1-5점이 아니라 예/아니요인가? 판정자가 점수에서는 일관성이 없다. 예/아니요 질문에 계산 지표와 트레이스 단언(지연·토큰 예산)을 함께 쓴다.
- 파이프라인 하나로 여러 프레임워크를 평가할 수 있나? OpenTelemetry와 OpenInference로 맞추면 된다.
- 배포 뒤에는? 실제 트래픽을 기준선과 비교한다. 실패 트레이스는 진단하고 실제 트레이스는 골든 데이터셋으로 올린다.

## 정리

이 글의 처방은 새로운 발명보다 소프트웨어 테스트의 상식을 에이전트에 옮긴 쪽에 가깝다. 고정된 시험 묶음, 한 번에 변수 하나, 회귀를 막는 병합 관문 모두 그렇다. 에이전트라서 달라지는 점은 두 가지다. 우선 답 대신 트레이스를 봐야 한다. 또 판정자도 LLM이니 판정자 자신을 사람 채점에 맞춰 검증해야 한다. Day 0에 사람이 직접 트레이스를 읽으라는 조언이 가장 값싸고 가장 쓸모 있어 보인다.

> 해설 — 걸러 볼 점이 두 가지 있다. 첫째, Google 엔지니어가 쓴 글이라 도구 권장이 Google 제품(ADK, Agent Evaluation 서비스, Gemini, BigQuery)에 기울어 있다. 원리는 다른 도구로도 그대로 옮길 수 있다. 둘째, 원문은 agent-eval이 LangGraph와 직접 만든 런타임의 트레이스도 받는다고 쓴다. 그런데 2026년 10월 현재 저장소 README는 기본 지원 프레임워크를 ADK 하나로 적고 있다. 다른 프레임워크라면 OpenInference 트레이스를 직접 넘기는 설정이 필요할 수 있다.

[^agent-eval]: agent-eval — Google Cloud의 professional-services 저장소에 있는 오픈소스 CLI. `setup`·`init`·`run` 세 명령으로 데이터셋 뼈대를 만들고 트레이스를 모아 채점한 뒤 HTML 보고서를 연다. 이 글이 권하는 평가 도구다.
[^otel]: OpenTelemetry — 분산 시스템의 트레이스·지표·로그를 남기는 개방 표준. 이 글에서는 에이전트 트레이스를 프레임워크와 상관없이 같은 형식으로 남기는 바탕이다.
[^openinference]: OpenInference — Arize가 만든, OpenTelemetry 위에서 LLM·에이전트 호출을 기록하는 의미 규약. 이 글에서는 프레임워크별 파이프라인을 하나로 합치는 열쇠다.
[^adk]: Google ADK(Agent Development Kit) — Google의 오픈소스 에이전트 개발 프레임워크. 이 글에서는 사용자 시뮬레이션 기능으로 시나리오를 돌리는 데 쓰인다.
[^langgraph]: LangGraph — LangChain 팀이 만든 에이전트 오케스트레이션 프레임워크. 원문의 동반 영상은 LangGraph 에이전트에 평가 파이프라인을 붙인다.
[^gemini]: Gemini — Google의 LLM. 이 글에서는 agent-eval 보고서에서 실패한 턴의 원인을 분석해 적는다.
