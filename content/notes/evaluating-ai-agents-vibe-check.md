## 한눈에 보기

에이전트를 처음 만들면 어떻게 시험하는가? 모델을 붙이고 도구 몇 개를 단다. 프롬프트 몇 개를 돌려 본다. 답을 눈으로 훑고 그럴듯하면 넘어간다. 저자들은 이것을 '바이브 체크(vibe check)'라 부른다. 감으로 하는 점검이다. 처음에는 이걸로 된다. 그다음이 문제다. 한 워크플로의 프롬프트를 고쳤더니 다른 워크플로의 도구 호출이 조용히 망가진다. 아무도 모른다. 사용자가 먼저 안다. 이 글은 그날이 오기 전에 무엇을 갖춰 둘지 다룬다.

| 항목 | 내용 |
|---|---|
| 문제 | 최종 답만 보면 루프, 잘못된 도구 인자, 토큰 낭비, 중복 실행 같은 실패가 안 보인다 |
| 성공 정의 | 핵심 사용자 여정(CUJ)의 조항 하나하나를 평가 지점으로 삼는다 |
| 시나리오 | 사용자 시뮬레이터로 시작해 점점 실제 트래픽으로 바꾼다 |
| 채점 | 1-5점 대신 예/아니요 질문. 품질과 함께 지연·토큰·비용·도구 호출 수를 잰다 |
| Day 0 | 트레이스 5-20개를 사람이 빨간 펜으로 읽는다 |
| Day 1 | 같은 시험을 매번 돌리고, 판정 LLM을 사람 채점에 맞춘다. 손잡이를 하나씩 50-60번 돌린다 |
| Day 2 | PR 병합 관문(성공률 95% 이상, 회귀 0)과 공유 대시보드 |
| 도구 | 오픈소스 agent-eval[^agent-eval], 트레이스는 OpenTelemetry[^otel] + OpenInference[^openinference] |

## 먼저, 에이전트 평가란 무엇인가

참고: [Google ADK 사용자 시뮬레이션 문서](https://adk.dev/evaluate/user-sim/), [agent-eval 저장소](https://github.com/GoogleCloudPlatform/professional-services/tree/main/tools/agent-eval)

챗봇은 질문 하나에 답 하나를 낸다. 그러니 답만 맞으면 된다. 에이전트는 사정이 다르다. 답에 이르기까지 여러 걸음을 걷는다. 무엇을 할지 궁리한다. 도구를 고른다. 인자를 채워 부른다. 결과를 읽고 다시 고른다. 이 걸음을 전부 적어 둔 기록이 트레이스(trace)다.

왜 트레이스까지 봐야 하나? 답이 같아도 에이전트는 같지 않기 때문이다. 도구를 두 번 불러 3초 만에 답한 에이전트가 있다. 열두 번 불러 40초 만에 같은 답을 낸 에이전트도 있다. 답안지만 보면 둘 다 만점이다. 풀이를 보면 하나는 낙제다.

그래서 에이전트 평가는 세 가지를 본다. 답이 맞았나? 풀이가 옳았나? 올바른 도구를 올바른 순서로, 올바른 인자로 불렀는지를 묻는다. 그 풀이에 얼마가 들었나?

| | 바이브 체크 | 체계적인 평가 |
|---|---|---|
| 입력 | 그때그때 떠오른 프롬프트 몇 개 | 고정된 골든 데이터셋(golden dataset)과 시뮬레이션 시나리오 |
| 보는 것 | 최종 답 | 트레이스 전체(추론, 도구 인자, 중간 결과) |
| 채점 | "괜찮아 보이네" | 예/아니요 루브릭, 결정론적 지표, 비용·지연 |
| 비교 | 기억에 의존 | 기준선(baseline)과 수치로 비교 |
| 바뀐 뒤 | 다시 몇 개 돌려 봄 | 같은 시험 묶음을 전부 다시 돌림 |

아래는 두 방식을 파이썬으로 옮겨 본 예시다. 원문에는 코드가 없다. 원문의 사례(거래 불일치 이메일을 처리하는 에이전트)를 옮긴 이가 코드로 꾸몄다. `agent.run`, `judge` 같은 함수는 가상의 것이다.

```python
# 바이브 체크: 최종 답 문자열만 사람 눈에 들어온다. 실행은 1번, 기록은 없다.
reply = agent.run("브로커 메일: 거래 T-8812 가격이 장부와 다릅니다")
print(reply)  # "확인해 보니 ... 회신 초안입니다" → 그럴듯하면 통과
```

```python
# 체계적인 평가: 고정 데이터셋 전체를 돌리고 트레이스를 기준으로 채점한다.
results = []
for case in load_jsonl("golden.jsonl"):             # 튜닝 중에는 이 파일을 건드리지 않는다
    trace = agent.run(case["prompt"], record_trace=True)
    calls = [s for s in trace.steps if s.type == "tool_call"]
    results.append({
        # 결정론적 검사: 코드로 판단할 수 있는 건 코드로
        "found_txn": trace.final.txn_id == case["expected_txn_id"],
        "ledger_before_draft": first_index(calls, "ledger_lookup") < first_index(calls, "draft_reply"),
        # 판정 LLM: 1-5점이 아니라 예/아니요 질문 하나
        "ids_mapped": judge("내부 거래 ID를 브로커 표기로 바꿔 적었는가?", trace) == "YES",
        # 운영 비용: 품질과 같은 줄에 기록한다
        "latency_ok": trace.latency_s <= 30,
        "tool_calls": len(calls),
        "cost_usd": trace.cost_usd,
    })
report(results, baseline="runs/last_green.json")  # 지난 기준선과 지표별로 비교
```

두 번째 코드에 나오는 `judge`는 채점을 맡은 LLM이다. 사람 대신 다른 LLM에게 기준을 주고 판정을 맡긴다. 이 방식을 'LLM-as-a-judge'라고 한다. 그런데 이 채점관에게 무엇을 물어야 하나? 점수 대신 예/아니요를 물으라. 이 글의 요점 가운데 하나다.

## 출발점: 세 가지 기본 블록

### 1. 핵심 사용자 여정으로 성공을 정의한다

잘 됐다는 건 무엇을 두고 하는 말인가? 이걸 먼저 정해야 한다. 저자들은 핵심 사용자 여정(critical user journey, CUJ)에서 출발하라고 한다. 누가(페르소나), 무엇을 하려고(목표), 어떤 조건에서(제약), 무엇을 보면 됐다고 할지(검증 조건) 적는다. 그렇게 적은 조항이 하나하나 평가 지점이 된다.

원문의 예를 보자. 주인공은 운영 분석가다. 거래 상대방에게서 불일치를 따지는 이메일이 온다. 에이전트는 문제의 거래를 찾는다. 내부 장부와 거래 조건을 대조한다. 회신 초안을 쓴다. 회신에는 내부 거래 ID를 브로커 쪽 표기로 바꿔 적어야 한다. 제약도 있다. 30초 안에, 사람 손을 빌리지 않고 끝내야 한다. 그러면 검증할 것이 저절로 나온다. 올바른 거래 ID를 찾았나? 초안을 쓰기 전에 장부를 확인했나? ID를 제대로 바꿨나?

### 2. 시뮬레이션 사용자로 시작해 실제 트래픽으로 옮긴다

시험 문제는 어디서 구하나? 처음에는 지어낸다. CUJ를 순탄하게 흘러가는 정상 경로(happy path)와 꼬이는 예외 상황(edge case)으로 나눠 시나리오를 쓴다. 그 시나리오를 사용자 역할을 맡은 LLM에게 준다. Google ADK[^adk]의 사용자 시뮬레이션이 이 일을 한다.

시나리오에는 첫 메시지(`starting_prompt`)와 사용자가 이뤄야 할 목표(`conversation_plan`)를 적는다. 필요하면 페르소나도 붙인다. 나머지는 시뮬레이터가 대화 흐름을 보고 알아서 말한다. 에이전트가 정보를 한꺼번에 묻지 않고 하나씩 물어도 대화가 끊기지 않는다. 대본을 외운 배우보다 즉흥 연기를 하는 배우에 가깝다. 지어낸 문제는 언제까지 쓰나? 실제 사용자가 생길 때까지다. 그 뒤로는 운영 트레이스로 차츰 바꿔 간다.

### 3. 여러 층에서 잰다

검사는 한 가지로 끝나지 않는다. 단위 테스트, 결정론적 지표, LLM 판정 루브릭, 통합 테스트를 층층이 쌓는다. 원문은 이 네 층을 그림으로만 보여 주고 따로 풀지는 않는다. 본문에 나오는 예로 짐작하면 이렇다. 결정론적 지표는 도구 인자나 기준값을 코드로 맞춰 보는 계산 지표다. 판정 루브릭은 "환불 도구를 부르기 전에 계정 ID를 확인했나?" 같은 예/아니요 질문이다. 지연과 토큰 예산은 트레이스에 단언(assertion)을 걸어 검사한다. 코드로 잴 수 있는 것은 코드로 잰다. 사람의 판단이 필요한 것만 판정 LLM에게 넘긴다.

## 피해야 할 함정 네 가지

첫째 함정. 시험지를 바꾼다. 지난주보다 점수가 올랐다고 하자. 에이전트가 좋아졌나, 시험이 쉬워졌나? 그사이 시험 몇 개를 지우거나 바꿨다면 알 길이 없다. 원문 그림의 말을 빌리면 시험을 지울 때 움직이는 것은 에이전트가 아니라 기준선이다. 그러니 튜닝하는 동안에는 골든 데이터셋을 얼려 둔다. 한 번에 변수 하나만 바꾼다. 시험을 빼는 건 요구사항이 바뀌었을 때뿐이다.

둘째 함정. 1-5점 채점이다. LLM에게 "이 답은 얼마나 도움이 됐나, 1-5점"이라고 물으면 어떻게 되나? 같은 답에 어제는 4점, 오늘은 3점을 준다. 이런 점수로는 나아졌는지 나빠졌는지 가릴 수 없다. 질문을 바꾸면 된다. "환불 도구를 부르기 전에 계정 ID를 확인했나, 예/아니요." 이렇게 물으면 판정이 흔들릴 틈이 좁아진다. 원문은 도구로 Google의 Adaptive Rubrics를 권한다.

셋째 함정. 답의 품질만 보고 청구서는 안 본다. 모든 품질 검사를 통과한 답이 있다고 하자. 그런데 한 번에 40초가 걸린다. 쓸데없는 도구 호출을 열두 번 한다. 질의 하나에 60센트가 든다. 이 답은 합격인가? 운영에서는 불합격이다. 지연, 토큰(프롬프트·추론·완성), API 비용, 도구 호출 횟수를 품질 지표와 한 줄에 나란히 적는다.

넷째 함정은 프레임워크마다 따로 만든 평가 파이프라인이다. 어떤 팀은 LangGraph[^langgraph]로, 어떤 팀은 ADK로, 또 어떤 팀은 직접 만든 런타임으로 에이전트를 짠다. 평가 도구까지 셋을 만들 필요는 없다. 트레이스를 OpenTelemetry로 남기고 OpenInference 규약에 맞추면 된다. 기록 형식이 같으면 파이프라인 하나로 다 잰다.

## Day 0부터 Day 2까지 실제로 들이는 법

그러면 실제로는 어떻게 시작하나? 오픈소스 도구를 쓰면 설치는 두어 시간이면 끝난다. 시간은 무엇을 잴지 정하는 데 든다. 저자들은 이 일을 Day 0, Day 1, Day 2 세 단계로 나눠 보여 준다.

### Day 0: 시나리오, 시뮬레이션, 그리고 '빨간 펜'

Day 0에 할 일은 의외로 수작업이다. 주요 CUJ마다 시나리오 초안을 쓰고 시뮬레이션을 돌린다. 점수판은 덮어 둔다. 대신 트레이스를 처음부터 끝까지 읽는다. 프롬프트, 추론 단계, 도구 인자, 출력을 다 본다. 학생 답안지를 채점하는 선생님처럼 빨간 펜을 든다. 에이전트가 머뭇거린 곳, 인자를 지어낸 곳, 도구를 잘못 고른 곳, 말이 길어진 곳에 표시한다.

왜 자동화부터 하지 않나? 무엇이 틀리는지 모르면 무엇을 잴지도 모르기 때문이다. 저자들은 트레이스 20개쯤만 손으로 읽어도 실패 유형을 짐작하느라 보낼 며칠을 아낀다고 말한다.

### Day 1: 주기, 신호, 시험 틀

Day 1에 와서야 자동화한다. agent-eval이 뼈대를 만들고 여러 턴짜리 대화를 돌린다. HTTP로 `--base-url`을 주어 돌릴 수도 있고 오프라인으로 돌릴 수도 있다. 트레이스를 모으고 Google의 Agent Evaluation 서비스와도 이어 준다. 원문 설명으로는 ADK, LangGraph, 직접 만든 런타임의 트레이스를 모두 받는다.

무엇을 바꾸든 같은 시험 묶음을 다시 돌린다. 프롬프트를 바꿔도, 모델을 바꿔도, 도구 독스트링 한 줄을 바꿔도 그렇다. 돌린 결과는 기준선과 비교한다.

채점관은 누가 채점하나? 이것도 빠뜨리면 안 된다. 판정 LLM이 틀리게 채점하면 시험 전체가 헛일이 된다. Day 0에 사람이 빨간 펜으로 채점한 트레이스를 판정 LLM에게 다시 채점시킨다. 엔지니어의 판단과 맞을 때까지 채점 프롬프트를 다듬는다.

### 튜닝 루프: 다시 쓰기가 아니라 손잡이 돌리기 50-60번

그다음은 튜닝이다. 프롬프트를 통째로 갈아엎지 않는다. 손잡이를 하나씩 돌린다. 도구 인자 설명을 분명히 한다. "이건 하지 마라" 같은 부정 제약을 하나 넣는다. JSON 출력 스키마를 고친다. 한 번에 하나만 바꾸고 잰다. 저자들은 이런 손질을 50-60번 한다고 말한다.

잰 결과는 agent-eval의 HTML 보고서로 본다. 통과/실패 지표 옆에 지연, 토큰 사용량, API 비용, 캐시 활용, 도구 호출 경로가 함께 나온다. 실패한 턴에는 Gemini[^gemini]가 쓴 원인 분석이 붙는다.

이렇게까지 해야 하나? 원문의 사례가 답한다. 어떤 프롬프트 변경이 있었다. 몇 개 찍어 보니 에이전트가 더 똑똑해 보였다. 그런데 시험 묶음을 다 돌리자 다른 그림이 나왔다. 지연은 두 배가 됐다. 도구 호출에서 지어낸 인자가 15% 늘었다. 감으로는 나아졌는데 숫자로는 나빠졌다. 이러니 작게 바꾸고 재는 편이 크게 갈아엎는 것보다 낫다.

### Day 2: 병합 관문과 공유 대시보드

Day 2에는 이 시험을 팀의 규칙으로 만든다. 먼저 PR 병합 관문이다. agent-eval을 Cloud Build나 GitHub Actions에서 사람 손 없이 돌린다. 병합되려면 전체 예/아니요 성공률이 threshold(원문의 예는 **95%**)를 넘어야 한다. 전에 통과하던 핵심 지표는 하나라도 떨어지면 안 된다. 누가 프롬프트를 고쳐 다른 워크플로를 망가뜨리면 병합 단계에서 걸린다. 처음에 말한 그 사고를 여기서 막는다.

다음은 공유 대시보드다. 트레이스 원본(JSONL), 프롬프트 해시, 모델 버전, 지연 분포, 점수표를 BigQuery나 Cloud Storage로 내보낸다. 팀 전체가 같은 숫자를 보고 이야기하게 된다.

출시하면 끝인가? 아니다. 실제 트래픽을 출시 전 기준선과 비교한다. 운영에서 실패한 트레이스는 진단한다. 좋은 실제 트레이스는 골든 데이터셋으로 올린다. 시험지가 점점 현실을 닮아 간다. 원문은 후속 글 [The Outer Loop](https://developers.googleblog.com/the-outer-loop-insights-first-an-ambient-quality-agent-that-diagnoses-your-production-agent/)도 함께 소개한다. 운영 트레이스를 자동으로 진단하는 '앰비언트 품질 에이전트'를 다룬 글이다.

## 자주 묻는 질문

원문 끝의 질문 다섯 개를 줄여 옮긴다.

- 바이브 체크의 문제는? 최종 답만 보이고 루프, 잘못된 도구 인자, 토큰 낭비, 중복 실행이 안 보인다.
- 처음부터 어떻게 시작하나? Day 0에는 트레이스 5-20개를 빨간 펜으로 읽는다. Day 1에 자동 검사를 붙이고 Day 2에 CI/CD 관문을 세운다.
- 왜 1-5점이 아니라 예/아니요인가? 판정자가 점수에서는 일관성이 없다. 예/아니요 질문에 계산 지표와 트레이스 단언(지연·토큰 예산)을 함께 쓴다.
- 파이프라인 하나로 여러 프레임워크를 평가할 수 있나? OpenTelemetry와 OpenInference로 맞추면 된다.
- 배포 뒤에는? 실제 트래픽을 기준선과 비교한다. 실패 트레이스는 진단하고 실제 트레이스는 골든 데이터셋으로 올린다.

## 정리

나는 이 글의 처방이 새롭지 않다고 본다. 고정된 시험 묶음, 한 번에 변수 하나, 회귀를 막는 병합 관문. 소프트웨어 테스트에서 오래 써 온 상식이다. 이 글은 그 상식을 에이전트에 옮겼다.

그래도 에이전트라서 달라지는 점이 두 가지 있다. 하나는 답이 아니라 풀이를 채점해야 한다는 것이다. 트레이스를 봐야 한다. 또 하나, 채점관도 LLM이다. 채점관이 믿을 만한지부터 사람 채점에 맞춰 확인해야 한다.

가장 값싸고 가장 쓸모 있는 조언은 무엇일까? 나는 Day 0의 빨간 펜이라고 본다. 도구도 돈도 들지 않는다. 트레이스 20개를 직접 읽으면 된다. 감으로 하는 점검을 벗어나는 첫걸음도 사람이 직접 읽는 일이다.

> 해설 — 읽을 때 걸러 볼 점이 두 가지 있다. 첫째, Google 엔지니어가 쓴 글이다. 그래서 권하는 도구가 Google 제품(ADK, Agent Evaluation 서비스, Gemini, BigQuery)에 기울어 있다. 원리는 다른 도구로도 그대로 옮길 수 있다. 둘째, 원문은 agent-eval이 LangGraph와 직접 만든 런타임의 트레이스도 받는다고 쓴다. 그런데 2026년 10월 현재 저장소 README는 기본 지원 프레임워크를 ADK 하나로 적고 있다. 다른 프레임워크를 쓴다면 OpenInference 트레이스를 직접 넘기는 설정이 필요할 수 있다.

[^agent-eval]: agent-eval — Google Cloud의 professional-services 저장소에 있는 오픈소스 CLI. `setup`·`init`·`run` 세 명령으로 데이터셋 뼈대를 만들고 트레이스를 모아 채점한 뒤 HTML 보고서를 연다. 이 글이 권하는 평가 도구다.
[^otel]: OpenTelemetry — 분산 시스템의 트레이스·지표·로그를 남기는 개방 표준. 이 글에서는 에이전트 트레이스를 프레임워크와 상관없이 같은 형식으로 남기는 바탕이다.
[^openinference]: OpenInference — Arize가 만든, OpenTelemetry 위에서 LLM·에이전트 호출을 기록하는 의미 규약. 이 글에서는 프레임워크별 파이프라인을 하나로 합치는 열쇠다.
[^adk]: Google ADK(Agent Development Kit) — Google의 오픈소스 에이전트 개발 프레임워크. 이 글에서는 사용자 시뮬레이션 기능으로 시나리오를 돌리는 데 쓰인다.
[^langgraph]: LangGraph — LangChain 팀이 만든 에이전트 오케스트레이션 프레임워크. 원문의 동반 영상은 LangGraph 에이전트에 평가 파이프라인을 붙인다.
[^gemini]: Gemini — Google의 LLM. 이 글에서는 agent-eval 보고서에서 실패한 턴의 원인을 분석해 적는다.
