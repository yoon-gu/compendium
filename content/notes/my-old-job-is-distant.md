## 한눈에 보기

AI가 개발자의 일을 어떻게 바꿨을까? 거창한 전망 말고 한 사람의 하루는 어떻게 달라졌을까? 이 글은 그 물음에 한 개발자가 자기 경험으로 답한 회고다. 처음 ChatGPT를 언제 썼는지도 기억나지 않는다는 데서 시작한다. 끝은 에이전트가 몇 시간 만에 만든 iPhone 앱을 폰에 깔아 보는 장면이다.

| 단계 | 쓰는 법 | 개발자의 자리 |
|---|---|---|
| ChatGPT[^chatgpt] | 더 나은 검색창 | 내가 짜고, 모르는 것만 묻는다 |
| 복사·붙여넣기 | 예시를 붙이고 원하는 동작을 설명 | 싫은 언어(Ruby) 공부를 피하는 비상구 |
| 탭 완성 | Cursor[^cursor]가 내가 쓰던 패턴을 이어 쓴다 | 거의 그대로 내가 짠다 |
| 에이전트 코딩 | Claude[^claude]에게 말로 시킨다 | 한 줄 한 줄 다 검토하고 어려운 곳은 직접 |
| Opus 4.5-4.6 | 단계별 지시가 크게 줄어든다 | 생산성 약 3배, 병목은 리뷰 |
| Opus 5.5 | 서브에이전트, 도구, 대시보드 | 코드보다 QA·설계·도구 |

## 먼저, 탭 완성과 에이전트 코딩은 무엇이 다른가

참고: [Claude Code 개요](https://docs.claude.com/en/docs/claude-code/overview), [Cursor 탭 완성 문서](https://docs.cursor.com/tab/overview)

이 글은 두 가지 일하는 방식을 안다고 전제한다. 탭 완성은 편집기가 다음 몇 줄을 회색 글씨로 미리 보여 주고 개발자가 탭 키를 누르면 받아들이는 방식이다. 주도권은 개발자에게 있다. 한 줄씩, 내가 쓰던 흐름을 따라간다. 에이전트 코딩은 다르다. 할 일을 말로 맡기면 에이전트가 파일을 읽고 여러 파일을 고치고 테스트를 돌리고 결과를 보고한다. 개발자는 쓰는 사람에서 맡기고 검토하는 사람이 된다.

| | 탭 완성 | 에이전트 코딩 |
|---|---|---|
| 단위 | 다음 한두 줄 | 기능 하나, 파일 여러 개 |
| 누가 쓰나 | 내가 쓰고 도구가 거든다 | 에이전트가 쓰고 내가 검토한다 |
| 병목 | 타자 속도, 문법 기억 | 리뷰, 무엇을 맡길지 정하는 일 |
| 실수가 드러나는 곳 | 바로 눈앞 | 나중에, 리뷰나 QA에서 |

에이전트가 코드를 빨리 쓰면 무엇이 막히나? 저자의 답은 리뷰다. 모든 줄을 똑같이 꼼꼼히 볼 수는 없으니 어디를 깊이 볼지 고르게 된다. 아래 파이썬 예시는 그 기준을 옮긴 이가 코드로 꾸민 것이다. 원문에는 코드가 없다. 표준 라이브러리와 익숙한 패턴은 훑어보되 비즈니스 로직, 고객 데이터, 되돌리기 어려운 변경은 꼼꼼히 본다는 원칙만 나온다.

```python
# 보통의 방식: 에이전트가 바꾼 파일을 처음부터 끝까지 똑같은 깊이로 읽는다
for f in changed_files(pr):
    read_every_line(f)                         # 변경이 세 배로 늘면 리뷰 시간도 세 배
```

```python
# 저자의 방식: 위험한 곳만 사람이 정독하고 나머지는 훑는다
DEEP = ("migrations/", "crypto/", "billing/", "customers/")   # 되돌리기 어렵거나 고객 데이터에 닿는 곳
for f in changed_files(pr):
    if f.path.startswith(DEEP) or touches_business_rules(f):
        read_every_line(f)                     # 비즈니스 로직·고객 데이터·DB 변경·암호화
    else:
        skim(f)                                # 표준 라이브러리·컴포넌트·익숙한 패턴은 피해가 작다
```

## 검색창에서 비상구로

처음 ChatGPT는 더 나은 구글이었다. 예전에 Stack Overflow[^so]가 코딩 검색을 바꿨던 것처럼 말이다. 동료 브라이언이 문제만 생기면 ChatGPT에 물어봤냐고 해서 짜증이 났는데 어느새 저자도 거기서부터 시작하게 됐다.

다음은 복사·붙여넣기다. 예시 코드를 붙이고 원하는 동작을 설명하면 코드가 나왔다. 주로 Ruby 테스트 코드였다. 저자는 Ruby 쓰기를 싫어했다. 타입이 있는 언어에서 익숙했던 자동완성이 편집기에서 잘 안 됐기 때문이다. ChatGPT는 Ruby를 제대로 배우지 않고 넘어가는 비상구가 됐다. Cursor의 탭 완성도 자연스러웠지만 대부분 이미 쓴 패턴을 되풀이할 뿐이라 크게 기대지는 않았다.

## 가장 좋았던 시절

저자가 가장 좋아했다는 때는 컴퓨터 비전 프로젝트를 잠시 맡았던 무렵이다. 처음 보는 물체의 경계와 정렬을 찾아내는 일이었다. 파이썬 컴퓨터 비전을 몰라서 ChatGPT에게 물어 가며 배우면서 만들었다. Jupyter[^jupyter] 노트북에서 코드를 돌렸다. 모델이 엉뚱한 소리를 하면 그걸 모델의 지식이 끝나는 경계로 읽었다. 저자에게 이 시기는 검색 엔진 최적화로 오염된 검색 결과와 부실한 문서를 건너뛰게 해 준 때였다. 통제권을 내준 때는 아니었다.

## 에이전트에게 말로 시키다

탭 완성 다음은 Claude에게 말로 시키는 에이전트 코딩이었다. 처음에는 'AGI를 들이마신다'는 식의 열광적인 글이나 카르파티[^karpathy]의 유명한 발언들이 잘 와닿지 않았다고 한다. 남들이 쓰는 긴 소원 목록 같은 프롬프트도 이상해 보였다. 그러다 모델이 어디까지 하고 어디서 무너지는지 차츰 익혔다. 결국 말로 시키는 게 주된 일하는 방식이 됐다. 그때만 해도 모든 줄을 검토했고 까다로운 부분은 직접 짰다.

## Opus 4.5와 4.6: 병목이 리뷰로 옮겨 가다

새 모델들은 단계별로 일일이 짚어 주지 않아도 됐다. 몇 달 동안 합쳐진 PR을 기준으로 저자는 생산성이 세 배쯤 올랐다고 어림한다. 그러자 리뷰가 병목이 됐다. 앞에서 본 대로, 무엇을 깊이 읽고 무엇을 훑을지 고르는 법을 익혔다. 코드베이스 전체는 여전히 머릿속에 있었다고 한다.

## Opus 5: 비용과 수다

모델은 버전마다 나아졌다. 고칠 일이 줄었고 가끔은 스스로 잘못을 바로잡았다. 대신 비용이 올라가고 말이 많아졌다. 저자는 한동안 ChatGPT로 옮겼다. 코딩 실력은 거의 비슷했고 더 쌌고 덜 장황했다. 그래도 돌아왔다. OpenAI를 믿지 못한다는 개인적 편향을 그는 숨기지 않는다. Anthropic 모델이 다시 비슷하거나 더 나아지자 돌아갔다. 장황함도 고쳐질 거라 믿었다고 한다.

## Opus 5.5: 한 단계 위에서 일하기

에이전트 코딩은 다시 한 번 바뀌었다. 저자는 이제 한 단계 위에서 일해야 한다고 느낀다. 지금 일하는 방식은 이렇다.

- 코드 리뷰보다 QA를 중심으로 계획을 짜고 아키텍처 결정도 되돌릴 수 있는 것으로 다룬다.
- 화면을 만들 때 여러 안을 한꺼번에 뽑아 보고 시험용 결과물을 잔뜩 만든다.
- 계획과 진행 상황, 메모는 모델이 저자의 노트 앱에 직접 남기게 한다.
- 자기와 모델 둘 다를 위한 도구를 만든다. 번다운 차트, 취약점 추적, 활동 피드, 성능 모니터링 같은 것들이다.
- 일을 여러 서브에이전트에게 나눠 주고 감독 에이전트를 둔다. 모델끼리 서로의 설계를 시험하고 단단하게 만들게 하는 것도 궁리 중이다.
- 쓸모없는 실험 결과물도 평소보다 훨씬 많이 만든다. 대부분 횡설수설 같지만 아이디어를 모으는 일 자체가 즐겁다고 한다.

## 몇 시간 만의 iPhone 앱

가장 놀란 건 노트 앱 일이었다. 저자는 Electron[^electron]으로 만든 자기 노트 앱을 iPhone으로 옮길 수 있을지 알아보라고 시키고 자리를 떴다. 몇 시간 뒤 돌아와 보니 Swift[^swift]로 짠 기본 네이티브 앱이 폰에 설치돼 있었다. 모델은 QA를 해 달라고 기다리고 있었다. 노트를 전부 가져와 보니 꽤 쓸 만했다. 기능이 다 갖춰지진 않았지만 작동했다. 든 비용은 월 20달러 구독의 5시간 사용 한도 가운데 40%쯤이었다.

한번은 이미지 처리가 150ms 안에 끝나야 한다고 쓰려다 15ms라고 잘못 적었다. 저자는 고치지 않고 모델이 어디까지 하나 보기로 했다. 결과가 어땠는지는 글에 나오지 않는다. 다만 이 일로 무엇이 가능한지에 대한 기준을 다시 생각하게 됐다고 한다.

## 아득해지는 예전의 일

저자는 변화의 속도가 신나면서도 불안하다고 쓴다. 지금 그가 붙잡는 것은 시스템에서 가장 중요한 부분이다. 설계, 제약 조건, 그리고 빠르게 바뀌는 코드를 이해하게 해 주는 도구. 앞으로도 계속 적응해야 할 거라고 본다. 예전 방식에서 그리운 것도 많고 그립지 않은 것도 많다. 기계적이고 지루한 일이 사라진 건 분명 반갑다. 그래도 예전의 일하는 방식은 점점 멀어져 간다.

## 정리

이 글은 주장이 아니라 기록이다. 그래서 오히려 믿을 만하다. 한 사람이 몇 년에 걸쳐 같은 질문에 다르게 답해 온 흔적이 그대로 보인다. AI를 어디까지 믿을 것인가? 처음엔 검색 결과만큼이었다. 그다음 Ruby 테스트, PR 하나를 거쳐 지금은 앱 하나만큼이다.

나는 이 글에서 리뷰가 병목이 됐다는 대목이 가장 실용적이라고 본다. 생산성이 세 배가 되면 읽어야 할 코드도 세 배가 된다. 저자는 모든 줄을 똑같이 보지 않고 위험한 곳을 골라 깊이 보게 됐다. 되돌리기 어려운 것, 고객 데이터에 닿는 것, 회사만의 규칙이 그 기준이다. 그다음 단계에서는 리뷰조차 QA와 도구로 넘어간다. 사람이 코드를 읽는 대신 코드가 제대로 도는지 확인하는 장치를 짓는다.

> 해설 — 걸러 볼 점이 몇 가지 있다. 생산성 세 배는 합쳐진 PR 수로 어림한 개인의 감이다. 품질이나 버그는 따로 재지 않았다. iPhone 앱은 기능이 다 갖춰지지 않은 시제품이다. 15ms 일화의 결과는 글에 나오지 않는다. 모델 이름(Opus 4.5, 4.6, 5, 5.5)과 구독 한도 같은 사정은 2026년 가을 한 사람의 경험이라 시기와 요금제에 따라 달라질 수 있다. 무엇보다 이 글은 한 개인의 회고다. 팀이나 조직 단위에서 같은 변화가 일어난다는 근거는 아니다.
