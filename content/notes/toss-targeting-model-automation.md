## 한눈에 보기

2년 전만 해도 토스에서 모델 하나를 만들려면 내부망에서 Jupyter 노트북을 켜고, 쿼리를 짜고, 함수를 수없이 직접 만들어야 했다. 팀은 생각했다. ML 엔지니어(MLE)는 반복 작업보다 성과를 더 낼 거리를 찾는 데 시간을 써야 한다. 그래서 고객 타겟팅 모델 프레임워크 TASTE를 다듬었고 모델 학습 시간은 2주에서 1일로 줄었다.

그런데 하나가 남았다. "이 모델을 써도 되나?" 모델을 쓰는 쪽도 묻고 만든 MLE도 스스로 묻는다. 여기에 답하려면 비교하고 평가하고 지켜봐야 하는데 이 일은 여전히 손으로 했다. 원문은 모델 하나를 쓰기까지 거치는 비교 네 가지를 차례로 따라가며 각각을 어떻게 자동화했는지 보여 준다.

| 질문 | 무엇끼리 비교하나 | 예전 | 지금 |
|---|---|---|---|
| ① 피쳐를 몇 개 쓸까 | 피쳐 수 K끼리 | MLE가 경험으로 비율을 정함 | auto_k가 K별 성능을 재서 고름 |
| ② 어떤 구조를 쓸까 | 트리와 딥러닝 | 단계별 트리 여러 개를 곱한 조합을 손으로 비교 | 같은 평가셋으로 나란히 재서 고름 |
| ③ 기존 모델보다 나은가 | 새 모델과 기존 모델 | 점수와 정답을 손으로 조인 | 학습이 끝나면 평가 보고서가 나옴 (30분 → 1분) |
| ④ 입력을 믿어도 되나 | 날짜끼리 (학습 때와 오늘, 평가일 사이) | 확인하지 않음 | 결손이 한도를 넘으면 적재 중단, 평가는 여러 날짜에서 |

## 먼저, 타겟팅 모델과 TASTE란 무엇인가

참고: [TASTE 소개 글](https://toss.tech/article/taste), 원문의 표와 보고서 예시

타겟팅 모델은 고객마다 점수를 매긴다. 이 고객이 이 상품을 신청할 확률 같은 점수다. 마케터는 점수 순으로 줄 세운 명단에서 위쪽 일부, 예를 들어 상위 5%에게만 메시지를 보낸다. 그래서 이 글의 지표는 대부분 '위쪽이 얼마나 정확한가'를 잰다.

- 회수율(타겟 커버리지, recall@N%): 전체 양성(실제로 전환한 고객) 가운데 상위 N%가 잡아낸 비율
- 실행률(precision@N%): 상위 N% 안에서 실제 양성의 비율
- PR-AUC: 정밀도-재현율 곡선 아래 넓이. 양성이 드물 때 AUROC보다 차이가 잘 드러난다
- KS: 양성과 음성의 점수 분포가 얼마나 벌어졌는지

TASTE는 이런 모델을 만드는 토스의 프레임워크다. 설정 파일 하나로 후보 피쳐 수집 → 피쳐 선정 → 학습 → 추론·적재 → 평가가 한 파이프라인으로 돈다. 이 파이프라인이 내놓은 모델을 "써도 되나" 판단하려면 계산이 더 필요하다. 이번 글은 그 계산을 파이프라인 안으로 옮긴 이야기다.

원문에는 코드가 없다. 첫 번째 비교(피쳐를 몇 개 쓸까)의 차이를 독자에게 익숙한 파이썬으로 옮겨 적으면 이렇다. 예전 방식은 비율로 자른다.

```python
# 중요도 순으로 세운 뒤 정해 둔 비율만큼 남긴다
model = Tree().fit(X_train, y_train)
order = argsort(model.feature_importances_)[::-1]     # 중요도 높은 순
k = int(len(order) * 0.2)                              # 상위 20%, MLE 가 경험으로 정한 값
features = order[:k]
final = Tree().fit(X_train[:, features], y_train)
# 데이터가 크든 작든, 무엇을 예측하든 같은 비율
# 20% 가 너무 적은지 많은지는 재 보지 않으면 모른다
```

auto_k는 개수를 성능으로 정한다.

```python
# 같은 순서에서 K 를 늘려 가며 성능을 직접 잰다
model = Tree().fit(X_train, y_train)
order = argsort(model.feature_importances_)[::-1]     # 순서는 중요도로
scores = {}
for k in [10, 20, 30, 50, 75, 100, 150, len(order)]:
    m = Tree().fit(X_sample[:, order[:k]], y_sample)
    scores[k] = pr_auc_with_ci(m, X_recent[:, order[:k]], y_recent)  # 최근 기간 평가셋
best = max(scores.values(), key=lambda s: s.mean)
tied = [k for k, s in scores.items() if not significantly_lower(s, best)]
k = min(tied) if tied else ratio_k(order)              # 근거가 없으면 예전 비율로
# 개수는 성능으로: '최고점과 구별되지 않는 가장 작은 K'
```

## ① 피쳐를 몇 개 쓸까: auto_k

이 기능은 팀 채팅 스레드에서 시작했다.

그동안 피쳐 수는 MLE가 정한 비율로 골랐다. 후보 피쳐를 중요도 순으로 세운 뒤 상위 몇 %만 남겼다. 데이터 크기나 예측 대상이 달라도 늘 같은 비율을 썼다. 그러면 학습 효율도 성능도 떨어질 수 있다. 도메인·데이터·모델마다 알맞은 비율이 다르니 경험만으로 '상위 몇 %'를 자신 있게 정하기도 어렵다.

처음 떠올린 대안은 중요도가 급격히 떨어지는 지점, 엘보(elbow)에서 자르는 방법이었다. 해 보니 잘 안 맞았다. 엘보에서 20개쯤으로 자른 모델보다 75개를 쓴 모델이 성능이 훨씬 높은 일이 잦았다. 중요도가 몇몇 피쳐에 몰려 있어서다. 그러면 곡선이 꺾이는 점이 구조적으로 앞쪽에 잡힌다. 그 뒤에도 성능에 보탬이 되는 피쳐가 아직 남아 있는데 말이다.

팀은 한 모델의 후보 피쳐 458개를 중요도 순으로 줄여 가며 성능을 쟀다. 값은 458개 모델을 100%로 둔 상대값이다.

| 피쳐 수 K | AUROC | PR-AUC | 458개와 PR-AUC 차이 | 상위 5% 회수율 |
|---|---|---|---|---|
| 20 | 99.1% | 77.4% | 유의하게 낮음 | 91.5% |
| 30 | 99.5% | 74.2% | 유의하게 낮음 | 93.5% |
| 50 | 100.0% | 88.7% | 유의하게 낮음 | 99.4% |
| 75 | 100.1% | 98.4% | 구별 안 됨 | 100.8% |
| 100 | 100.2% | 100.0% | 구별 안 됨 | 101.2% |
| 458 | 100% | 100% | 기준 | 100% |

458개와 통계적으로 구별되지 않는 가장 작은 개수는 75개였다. 피쳐를 84% 줄여도 성능은 그대로이고 학습 시간과 메모리는 아낀다. 눈여겨볼 대목은 AUROC다. 20개일 때도 99.1%라 거의 차이가 없어 보인다. 그런데 PR-AUC는 77.4%로 뚝 떨어진다. 위쪽이 중요한 타겟팅에서는 어느 지표로 재느냐가 결론을 바꾼다.

결국 곡선 모양만 보고 자르는 건 맞지 않았다. 알아야 할 것은 '성능이 어디서 더 안 오르는가'였고 그건 직접 재 봐야 안다. 순서는 중요도로, 개수는 성능으로 정했다. 이 검증 절차를 그대로 자동화한 것이 auto_k다(팀이 만든 이름이다).

1. 후보 피쳐 전체로 트리를 한 번 학습해 중요도 순위를 매긴다.
2. 샘플 데이터에서 K = 10, 20, 30, 50, 75, 100, 150 … 마다 상위 K개로 다시 학습하고 가장 최근 기간 평가셋에서 PR-AUC를 잰다.
3. 최고점과 통계적으로 구별되지 않는 K 가운데 가장 작은 값을 고른다. 앞 표라면 75다.

어떤 K도 최고점과 구별되지 않으면 판단할 근거가 없다고 보고 예전 비율 방식을 그대로 쓴다.

성과도 있었다. 한 상품의 구매 전환을 예측하는 모델은 구조를 딥러닝에서 트리로 바꾸고 auto_k로 피쳐를 골랐다. 피쳐를 절반 넘게 줄였는데 상위 5% 회수율은 고관여 세그먼트보다 약 1.7배 높았다. 실제 메시지 발송에서도 이어졌다. 다른 상품 모델도 auto_k로 피쳐를 골랐다. 이 모델 점수 상위 1% 고객은 기존 규칙 기반 세그먼트보다 클릭률이 약 5배, 신청 전환율이 약 2.6배 높았다. 연령 구성을 맞춰 비교해도 클릭률은 3배 이상, 신청 전환율은 2배 이상이었다.

## ② 어떤 구조를 쓸까: 트리와 딥러닝을 나란히 잰다

노출 → 진입 → 클릭 → 신청처럼 단계가 이어지는 퍼널 모델은 그동안 단계마다 트리 모델을 따로 학습했다. 진입할 확률, 진입한 고객이 누를 확률, 누른 고객이 신청할 확률을 각각 배운 뒤 추론이 끝나면 곱했다.

최종 점수 = P(진입) × P(클릭) × P(신청)

운영도 해석도 쉽다. 하지만 단계끼리 남남이다. 진입 모델이 배운 신호가 클릭·신청 모델로 넘어가지 않는다. 데이터가 가장 적은 마지막 단계(신청)일수록 앞 단계 신호가 절실한데 쓰지 못한다.

손도 많이 갔다. 3단계 퍼널 하나에 모델을 최대 다섯 개 학습하고 점수를 곱하는 조합 열한 가지를 직접 비교했다. 채널(푸시·홈 화면·메시지)이 바뀌면 통째로 다시 했다. 퍼널이 수십 개라 운영하는 트리 모델도 수십 개로 불었다.

그래서 퍼널 전체를 한 모델로 배우는 딥러닝 모델 AITM[^aitm](Adaptive Information Transfer Multi-task, KDD 2021)을 TASTE 설정에서 고를 수 있게 했다. 원문은 이 모델이 최선이라고 믿는 건 아니라고 못 박는다. 프레임워크가 유연하니 다른 구조도 계속 더할 수 있다는 것이다.

AITM은 두 장치로 '추론한 뒤 곱하기'와 갈라진다.

- 정보 전달(Adaptive Information Transfer): 앞 단계에서 배운 표현을 변환한 뒤 현재 단계 표현과 어텐션(attention)으로 합친다. 앞 단계 정보를 얼마나 참고할지를 고객마다 가중치로 정하는 셈이다.
- 단조성 제약(Label Constraint): 뒤 단계 확률이 앞 단계 확률보다 커지면 넘친 만큼 손실에 벌점을 더한다. 클릭도 안 할 사람이 신청할 확률이 더 높게 나오는 모순을 막는다.

쓰는 법은 간단하다. 파이프라인을 새로 짜지 않고 TASTE 설정에서 퍼널 모델을 고른 뒤 단계별 정답을 한 테이블에 나란히 담으면 된다. 2단계면 label_a, label_b, 3단계면 label_c까지다. 파이프라인이 라벨 컬럼을 읽어 몇 단계인지 스스로 판별하고 학습 스키마를 만든다. 운영에는 마지막 단계 점수를 쓴다. 고객이 앞 단계를 다 거쳐 최종 전환까지 갈 확률이다.

라벨은 이렇게 정한다.

- 모집단은 퍼널 첫 단계에 참여할 기회가 있었던 고객으로 한정한다. 노출조차 안 된 고객이 섞이면 '관심이 없어서 안 한 사람'과 '기회가 없어서 못 한 사람'이 구분되지 않는다.
- 앞 단계는 안 거쳤는데 뒤 단계는 한 것으로 찍힌 행은 학습에서 빼고 그 비율을 기록한다. 퍼널 정의가 어긋났다는 신호다.
- 타겟팅에는 마지막 단계 예측값을 쓴다.

결과는 갈렸다. 운영 중인 비즈니스 퍼널 두 곳에서는 AITM 하나가 기존 트리 조합보다 나았다. AUROC가 2단계 퍼널에서 약 1.4%, 3단계 퍼널에서 약 0.6% 높았다. 모델 수를 줄이고도 성능을 지켰다. 반면 평가셋에 양성이 적은 다른 도메인의 퍼널에서는 트리가 앞섰다.

| 모델 | "클릭 또는 신청" AUROC (딥러닝 대비) |
|---|---|
| 트리 (CatBoost · XGBoost) | +7.5% · +7.2% |
| 트리 (XGBoost), 딥러닝과 같은 학습 조건 | +2.9% |
| 딥러닝 (AITM) | 기준 |

양성이 적으면 파라미터가 많은 모델을 안정적으로 학습하기 어렵다. 데이터가 적은 초기에는 트리와 auto_k로 시작한다. AITM으로 바꾸기 전에는 퍼널마다 성능을 비교해서 정한다.

## ③ 기존 모델보다 나은가: 학습이 끝나면 보고서가 나온다

예전엔 기존 모델과 비교하려면 점수 테이블과 정답 테이블을 손으로 조인해 지표를 다시 계산했다. 이제는 설정에 OOT(Out-of-Time, 학습 이후 기간) 정답 테이블만 적으면 된다. 추론이 끝나면 평가 태스크가 AUROC, KS, 상위 N% 구간별 성과를 로그에 남긴다. 비교할 기존 모델의 점수 테이블을 적으면 같은 고객·같은 정답으로 채점한 비교표도 함께 나온다. 모델 하나를 평가하는 시간이 30분에서 1분이 됐다.

보고서 숫자를 그대로 판단에 쓰려고 세 가지를 정했다.

- 상위 N%는 마케터가 쓰는 백분위 그대로 자른다. 보고서의 '상위 5%'가 실제 발송 대상 '상위 5%'와 같은 고객이다.
- 라벨이 있는 고객만 센다. 라벨을 모르는 고객을 비전환으로 세면 분모만 커져 실행률이 실제보다 낮게 나온다.
- KS는 부호를 유지한다. 절댓값으로 계산하면 순위가 거꾸로 뒤집힌 모델도 KS가 크게 나와 멀쩡해 보인다.

보고서에는 피쳐별 기여도 표도 들어간다. 예전엔 순열 중요도(permutation importance)를 그대로 보여 줬다. 피쳐 값을 섞었을 때 손실이 얼마나 나빠지는지 재는 값이다. 표로 읽기엔 두 가지가 걸렸다. 양수와 음수가 섞여 있어 0에 가까운 음수가 '기여 없음'인지 '거꾸로 쓰임'인지 알 수 없었다. 방향도 말하지 못했다. 선형 모델로 풀어 보면 이 값은 계수의 제곱에 비례해서 계산하는 순간 부호가 사라진다. '이 피쳐가 높을수록 전환 확률이 오르는가'에는 답이 없다.

크기와 방향을 나눴다.

크기는 1위를 1.000으로 두는 0-1 값으로 바꿨다. 최솟값-최댓값 정규화는 쓰지 않았다. 그러면 가장 큰 음수가 0에 놓이고 진짜 0(영향 없음)이 눈금 중간으로 밀려난다. 대신 반복 측정 평균에 표준오차의 2배를 더해도 0보다 작은 음수에는 !를 붙였다. 노이즈로 설명되지 않는 음수, 곧 모델이 거꾸로 쓰는 피쳐다. 이 피쳐가 안 쓰는 피쳐와 같은 0.000으로 묻히지 않는다.

방향은 확률 변화로 잰다. 다른 피쳐는 그대로 두고 피쳐 하나만 하위 10% 지점 값과 상위 10% 지점 값으로 바꾼 뒤 고객마다 예측 확률이 얼마나 달라지는지 본다.

```
d_i = p(x_i, x_j := q90) − p(x_i, x_j := q10)     # i 는 고객, j 는 값을 바꾸는 피쳐
방향   = mean_i(d_i)                              # 부호가 곧 방향
일관성 = d_i 가 양수인 고객의 비율                    # 50% 에서 멀수록 일관된 방향
```

최솟값·최댓값 대신 10%·90% 지점을 쓰면 이상치 한 명이 기준값을 정해 버리지 않는다. 일관성을 함께 보이는 건 신경망 때문이다. 신경망은 고객마다 방향이 뒤집힐 수 있다. 평균만 보면 절반은 오르고 절반은 내리는 피쳐가 '영향 없음'으로 읽힌다. 보고서에는 크기(importance)와 방향(d_proba), 괄호 안에 일관성이 한 줄로 나온다. 예를 들어 `+0.01057 (85%)`는 값이 높을수록 확률이 오르고 고객의 85%에서 같은 방향이었다는 뜻이다. 범주형 피쳐는 10% 지점을 정할 수 없어 방향을 n/a로 둔다.

## ④ 입력을 믿어도 되나: 날짜를 바꿔 가며 비교한다

이 절의 이야기는 모두 하나를 묻는다. 모델이 받는 입력이 우리가 생각한 그 값인가?

첫째, 모델은 고정한다. 처음엔 매일 재학습해 최신 데이터를 쓰면 좋을 줄 알았다. 매일 재학습하는 모델과 고정한 모델을 나란히 돌려 보니 회수율은 같았다. 그런데 점수 상위 10% 고객이 이틀 연속 겹치는 비율이 달랐다. 매일 재학습하는 쪽은 71%, 고정한 쪽은 95%였다. 회수율이 같아도 명단이 매일 이만큼 바뀌면 마케터가 쓰기 어렵다. 그래서 모델을 고정(pinned)했다. 고정하는 건 모델 파일이 아니라 피쳐 목록이다. 학습에 쓴 피쳐 목록과 해시값을 함께 저장하고 추론은 같은 목록일 때만 돈다.

둘째, 입력이 비면 점수를 내보내지 않는다. 모델은 멈춰 있어도 원천 테이블은 움직인다. 한 모델이 쓰던 원천 테이블 중 4분의 1가량이 몇 달 사이에 생산을 멈췄다. 피쳐 조인은 그날 파티션이 없으면 에러 없이 NULL을 채운다. 그대로 뒀다면 피쳐의 13-21%가 빈 채로 점수가 경고 하나 없이 나갔을 것이다. 이제는 추론할 때마다 피쳐별 결손을 센다. 결손 피쳐가 10%를 넘으면 배치를 실패시키고 그날 점수는 적재하지 않는다. 팀은 망가진 점수가 조용히 나가는 것보다 알람이 울리는 게 낫다고 봤다. 결손 비율의 추이는 재학습 시점을 정하는 신호로도 쓴다. 운영 중인 모델 세 개는 이 비율이 몇 달 사이 0%에서 6-8%까지 올랐다.

셋째, 평가는 여러 날짜에서 한다. 새 모델을 세 평가일에서 기존 모델과 비교한 적이 있다. 두 날은 기존 모델보다 조금 낮았고 마지막 하루만 크게 앞섰다. 나중 날짜에서만 갑자기 좋아지는 일은 드물어서 원인을 찾았다.

먼저 피쳐 단독 AUROC를 날짜별로 쟀다. 피쳐 하나만 예측 점수처럼 놓고 AUROC를 재는 방법이다. 다른 피쳐는 거의 그대로였는데 두 피쳐만 월중 기준일인 평가일 C에서 평가일 A보다 17% 올랐다. 두 피쳐는 월 단위로 집계하는데 달이 끝날 때까지 매일 다시 계산되고 있었다. 지난 월중 날짜를 기준으로 피쳐를 꺼내면 그 날짜 이후의 행동까지 들어 있었다. 모델이 맞혀야 할 정답 기간의 행동, 곧 미래 정보다.

원문은 SHAP[^shap]으로 봤다면 찾기 어려웠을 거라고 말한다. SHAP은 피쳐 값과 모델 점수의 관계만 본다. 고객이 실제로 전환했는지는 보지 않는다. 단독 AUROC는 피쳐와 정답의 관계를 바로 잰다. SQL로 계산할 수 있어 날짜 하나에 전체 고객을 몇 분이면 본다.

원인을 찾은 뒤 이렇게 바꿨다.

- 문제가 된 두 피쳐는 빼고 지난달까지의 데이터만 담은 테이블을 넣었다.
- 평가는 월말과 월중처럼 성격이 다른 날짜를 섞어서 한다. 한 날짜에서만 앞서면 채택 전에 피쳐를 날짜별로 다시 확인한다.
- 새 데이터 원천은 그 값이 기준일에 이미 확정돼 있었는지부터 확인하고 쓴다.

## 맺으며

원문은 세 가지로 마무리한다.

- 데이터에 기반한 결정. 피쳐 수든 모델 구조든 복잡도는 경험이나 유행에 기대지 않고 데이터 규모에 맞춰 실험으로 정한다. 피쳐를 84% 줄여도 성능이 같았고 더 복잡한 딥러닝 퍼널 모델이 늘 낫다고 가정하지 않았다.
- 엔지니어링으로 줄인 손일. 조합 열한 가지를 비교하던 일은 라벨 테이블 하나로, 30분 걸리던 평가는 1분으로 줄었다.
- 합리적 의심과 꾸준한 개선. 명단이 흔들려서 모델을 고정했고, 입력이 비면 점수를 멈췄고, 한 날짜에서만 튄 성능을 끝까지 쫓아 미래 정보를 찾아냈다.

제목의 '판단에만 집중하세요'는 사람이 할 일을 줄이자는 말이 아니다. 어떤 고객의 어떤 행동을 예측할지 정하는 일, 결과가 실제 쓰임에 충분한지 살피는 일, 이 모델을 채택할지 결정하는 일은 여전히 사람이 한다. 팀은 MLE가 그 판단에 시간을 쓰도록 비교를 자동화했다. 그리고 그 판단은 숫자를 믿을 수 있을 때만 의미가 있다. 원문에서 가장 오래 남는 장면도 그래서 마지막 비교다. 성능이 좋게 나왔을 때 기뻐하는 대신 "왜 하필 이 날만?"을 물은 대목이다.
