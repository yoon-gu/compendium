# 하니스 엔지니어링 101 핸즈온 — 2편 오래 달리는 에이전트 (시나리오)

원문 6-9장(컨텍스트 예산, 서브에이전트, 조종, 백그라운드 작업). 목차는 [outline.md](outline.md) 2편 그대로.
1편에서 굳힌 형식을 따른다: 가로판, 합쇼체 강사, 실제 실행 녹화, 터미널 아래 '지금 실행 중인 코드 줄', 코드는 타이핑 클립 + 설명 중인 줄 네모,
실행 화면마다 "여기까지 확인", 처음 나오는 용어는 화면 아래 한 줄 풀이, 모델 답이 다 뜬 뒤에 설명(LEAD 1.5초). 목소리 소희(Qwen3-TTS), 길이 20분 안팎.

이 문서는 화면 순서와 실험 설계다. 나레이션 문장은 녹화로 실제 숫자가 나온 뒤 대본(script-2.md)으로 쓴다. 아래의 `{…}` 자리는 녹화 값이 들어갈 곳.

## 이 편의 질문 하나

1편의 에이전트는 짧은 일에서는 잘 돌았다. 오래, 크게 시키면 무엇이 먼저 무너질까? 답은 네 가지이고, 수업 하나가 하나씩 막는다.

| 수업 | 무너지는 것 | 막는 법 | 체크포인트 |
|---|---|---|---|
| 7 | 배열이 차서 호출이 거절된다 | 도구 결과를 잘라 내고, 잘랐다고 말한다 | 도구 결과가 예산을 가장 많이 먹는다 |
| 8 | 한 번 쓰고 말 탐색이 배열에 영원히 남는다 | 빈 배열로 도는 같은 루프에 맡긴다 | 부모 배열은 깨끗하게 남는다 |
| 9 | 모델이 바뀐 세상과 자기 계획을 놓친다 | 몸이 배열 맨 아래에 알림을 붙인다 | 몸의 사건이 배열의 문장이 된다 |
| 10 | 느린 명령 앞에서 루프가 멈춘다 | 일을 뒤로 돌리고, 끝나면 몸이 뇌를 깨운다 | 기다리는 일은 몸이 한다 |

## 화면 순서

`[코드]` 타이핑 클립, `[실행]` 터미널 + 실행 줄, `[그림]` 정지 다이어그램, `[모션]` 애니메이션, `[JSON]` 실제 배열 일부를 보여 주는 화면.

### 장 1 · 들어가며

1. 표지 — "오래 달리면 **무엇이** 무너지나". 2편 · 오래 달리는 에이전트
   - 1편을 안 본 분을 위해 세 줄 복습: 배열 하나, while 루프 하나, 도구 이름으로 함수를 고르는 표 하나.
2. [모션] 지난 편의 루프가 바퀴를 돌 때마다 배열이 길어지는 그림(1편 array-grow를 이어 받아, 이번엔 도구 결과 덩어리가 쌓인다).
   - "오늘은 이 루프를 오래, 크게 돌려 보고 무너지는 곳 네 군데를 하나씩 고칩니다."
3. [그림] 오늘의 지도 — 위 표 네 줄. 수업 틀(같이 쓰기 → 실행 → 방금 일어난 일 → 자주 막히는 곳 → 체크포인트)은 1편과 같다고 한 줄.
4. 준비물 — 1편 `lab/` 그대로 + 새 파일 넷. 명령 한 줄로 받기. "1편 코드가 돌던 분은 추가 설치가 없습니다."

### 장 2 · 수업 7 · 컨텍스트 예산

5. [그림] 윈도우와 예산은 다르다 — 컨텍스트 윈도우(모델이 한 번에 받을 수 있는 최대 길이)와, 실제로 집중해서 읽어 주는 범위. 배열이 가득 차기 전에 이미 앞쪽 지시를 덜 따르기 시작한다(컨텍스트 열화, context rot).
   - 비유 한 장: 회의록이 100쪽을 넘으면 첫 쪽의 결정을 다들 잊는다.
6. [실행] 큰 로그 통째로 읽기 — "logs/build.log를 읽고 빌드가 왜 깨졌는지 알려 줘."
   - 기대: 모델이 `read_file`로 통째로 읽음 → 다음 호출에서 HTTP 400(입력이 너무 김) 또는 입력 토큰 `{N}`만큼 폭증. 실제로 나온 쪽을 쓴다.
   - 여기까지 확인: 여러분 화면에도 `[usage] in=` 숫자가 한 번에 크게 뛰거나 400이 나오면 맞게 오셨습니다.
7. [JSON] 배열 안을 들여다보기 — 실패 직전 배열의 크기를 덩어리별 막대로: 시스템 프롬프트·도구 정의 `{a}`, 대화 `{b}`, 도구 결과 `{c}`. 거의 다 도구 결과.
   - 체크포인트 미리: 예산을 먹는 건 말이 아니라 도구 결과입니다.
8. [코드] `truncate()` 같이 쓰기 — 길면 머리와 꼬리만 남기고, 가운데에 "몇 글자를 잘랐다, 전체는 이 파일에 있다"를 적는다. `read_file`에는 `offset`·`limit`(몇째 줄부터 몇 줄).
   - 왜 "잘랐다고 말하기"가 중요한지는 다음 실행에서 바로 보인다.
9. [실행] 같은 질문, 자르는 판 — 머리·꼬리에는 원인이 없다(일부러 가운데에 묻어 둠). 모델이 잘렸다는 표시를 보고 저장된 파일을 `grep`이나 범위 읽기로 다시 찾아 원인 줄을 짚는다.
   - 숫자: 입력 토큰 `{N1}` → `{N2}`.
   - 여기까지 확인: `[truncated …]` 표시가 보이고, 모델이 다시 찾아 들어가면 성공입니다.
10. 자주 막히는 곳: 말없이 자르기 — 저자가 처음엔 잘랐다는 말을 안 붙였다가 모델이 잘린 파일을 온전한 줄 알고 헤맸다는 이야기(우리 말로 요약). 화면은 "말없이 자른 판" 한 줄 결과와 비교 표.
    - 녹화 여유가 되면 실제로 말없이 자른 판도 한 번 돌려 넣는다(선택).
11. [그림] 더 알아 두기 두 가지 — 압축(오래된 대화를 요약 한 덩어리로 바꾸고 최근 몇 바퀴만 그대로 둠, Claude Code의 `/compact`)과 메모리 파일(세션이 바뀌어도 남겨야 할 것을 디스크에, 배열은 RAM·파일은 디스크).
    - 압축은 캐시를 한 번 깨지만 드물어서 괜찮다고 1편 수업 6과 이어 준다. 오늘은 만들지 않고 숙제로.
12. 체크포인트 — 도구 결과가 예산을 가장 많이 먹는다. 자를 땐 잘랐다고 말한다. 필요한 만큼만 모델이 가져가게 한다.

### 장 3 · 수업 8 · 서브에이전트

13. [모션] 서브에이전트란 무엇인가 — 부모 배열 옆에 빈 배열이 하나 생기고, 그 안에서 도구 호출이 수십 번 쌓였다가, 맨 끝 답 한 문단만 부모 쪽으로 넘어오고 자식 배열은 사라진다.
    - 정의 한 줄: 빈 배열로 1편의 루프를 한 번 더 돌리고, 마지막 답만 도구 결과로 돌려받는 것.
    - 팀·조직도처럼 설명하는 글이 많지만, 이유는 하나: 부모의 배열(작업 기억)을 지키려고.
14. [코드] `agent` 도구 같이 쓰기 — 도구 설명("자식은 이 대화를 전혀 모르니 배경을 다 적어라"), `run_subagent()` 다섯 줄, 디스패치 표에 한 줄. 자식에게는 `agent` 도구를 주지 않는다(손자는 없다).
15. [실행] 서브에이전트 없이 — `minishop/`에서 "재시도 로직이 어디 있고 몇 번까지 다시 시도하는지 찾아 줘." 파일을 `{k}`개 읽고 답. 부모 배열 `{P0}` 바이트.
16. [실행] 서브에이전트로 — 같은 질문. 부모는 `agent` 한 번 부르고 답을 받는다. 자식 쪽 호출 `{k2}`번은 회색 들여쓰기로 보인다. 부모 배열 `{P1}` 바이트, 자식 배열은 끝나고 버려짐.
    - 여기까지 확인: `[sub]` 줄들이 지나간 뒤 부모의 `[array]` 숫자가 작게 남으면 성공입니다.
17. [그림] 무엇을 아끼고 무엇을 쓰나 — 막대 둘: 총 토큰(부모+자식)은 비슷하거나 더 많다 `{T0}` vs `{T1}`. 줄어드는 건 부모 배열 `{P0}` → `{P1}`. 돈은 그대로, 아끼는 건 주의력.
18. [JSON] 부모가 자식에게 쓴 일감 — 실제로 모델이 만든 `task` 문자열을 화면에. 자주 막히는 곳: 자식은 아무것도 모른다. 좋은 일감 네 가지(무엇을, 어디서, 끝의 모양, 돌려줄 형식)를 문자열 위에 표시.
    - 저자 경험 요약: 탐색만 맡겼는데 쓰기 도구가 있어 파일을 고쳐 버렸다 → 탐색용 자식에게는 쓰기 도구를 빼고 "고치지 말 것"을 적는다.
19. 맡길 일, 맡기지 말 일 — 표 하나. 맡길 일: 찾기, 테스트 돌리고 요약, 문서 읽기, 서로 독립인 여러 조각. 맡기지 말 일: 세션의 판단이 필요한 일, 한 번 검색이면 끝날 일, 줄줄이 이어지는 수정.
20. 체크포인트 — 부모 배열은 깨끗하게 남는다. 일감은 슬랙도 못 보는 외주 업체에 주는 티켓처럼.

### 장 4 · 수업 9 · 리마인더 큐와 할 일 목록

21. [그림] 루프 도중에 모델에게 말 걸기 — 모델은 배열에 있는 것만 안다. 일하는 도중 사람이 파일을 고치면? 80,000 토큰 전에 한 "커밋 전에 물어봐"는? 열두 단계 중 일곱째에서 길을 잃으면?
    - 몸이 배열 맨 아래 사용자 쪽 메시지에 `<system-reminder>` 꼬리표를 단 글을 붙인다. 왜 시스템 프롬프트가 아니라 맨 아래인가: 1편 수업 6의 캐시(위를 고치면 아래 전부 제값), 최근 글에 주의가 잘 간다, 사건은 바퀴 사이에 생긴다.
22. [코드] 큐 같이 쓰기 — `REMINDERS = []`, `remind(text)`, 다음 사용자 쪽 메시지에 쏟아 붓는 `drain()`. 파일 감시: 모델이 읽은 파일의 수정 시각을 적어 두고, 바뀌면 `remind("…가 바뀌었다, 다시 읽어라")`.
    - 흩어진 곳에서 문자열을 바로 끼워 넣지 말고 큐 하나로 — 나중에 "모델이 무엇을 봤나"를 설명할 수 있게.
23. [실행] 알림 없이 — 일: "pager.py의 page_count에 docstring을 달아 줘." 모델이 파일을 읽은 직후, 실습 스크립트가 사람인 척 같은 파일의 다른 함수를 고친다(화면 아래 `[사람이 pager.py를 고침]` 줄). 모델은 예전 내용 그대로 덮어써서 사람의 수정이 사라진다. `diff`로 확인.
24. [실행] 알림 있게 — 같은 일. 이번엔 다음 바퀴에 `<system-reminder> pager.py가 바뀌었다` 가 붙고, 모델이 다시 읽고 고친다. 사람의 수정이 살아 있다.
    - 여기까지 확인: 두 번째 판의 `diff`에 사람이 고친 줄과 docstring이 둘 다 있으면 성공입니다.
25. [JSON] 배열 끝을 열어 보기 — 실제 세션 파일에서 `tool_result` 바로 뒤에 붙은 `<system-reminder>` 텍스트 블록. 1편 수업 2의 세션 파일 화면과 같은 꼴.
26. [실행] 할 일 목록 — `todo_write` 도구. 일: "README 오타 두 개 고치고, page_count 고치고, 테스트 돌려 줘." 모델이 목록을 쓰면 몸이 그 목록을 다음 메시지 맨 아래에 다시 붙인다. 터미널에 `[todo]` 체크 상자가 바퀴마다 하나씩 채워진다.
    - 모델이 자기 계획을 다시 보는 이유: 50,000 토큰 전에 쓴 계획은 다른 글처럼 흐려진다. 목록을 모델 밖에 두면 매번 새 글로 맨 아래에 온다. 화이트보드를 눈앞에 세워 두는 것.
27. 자주 막히는 곳: 너무 자주 조종하기 — 매 바퀴 "조심해"를 넣으면 모델이 배경 소음으로 듣는다. 규칙 둘: 시계가 아니라 사건으로 알린다. 늘 필요한 말이면 시스템 프롬프트나 도구 설명으로 옮긴다. 저자 경험 요약: 방금 직접 만든 파일까지 "읽고 나서 고쳐라" 규칙을 걸었더니 모델이 자기가 쓴 걸 다시 읽는 헛걸음을 반복했다.
28. 체크포인트 — 몸의 사건이 배열의 문장이 된다. 드물게, 구체적으로, 사실만.

### 장 5 · 수업 10 · 백그라운드 작업

29. [그림] 동기 루프의 한계 — 25초 걸리는 테스트 앞에서 할 수 있는 세 가지: 통째로 기다린다(아무것도 못 함), 시간 제한으로 끊는다(모델은 "여기선 테스트가 실패한다"고 배움), 모델이 `sleep 5` 하고 확인, 또 확인(비싼 뇌가 주방 타이머 노릇).
30. [코드] 작업 표 같이 쓰기 — `TASKS = {}`, `run_command`에 `background` 플래그 → `Popen`으로 띄우고 바로 "작업 b1 시작"을 돌려줌. 출력을 모으는 스레드가 끝나면 `remind("b1 끝남, exit 1")` — 수업 9의 큐를 그대로 씀. `task_output` 도구.
31. [실행] 테스트를 뒤로 돌리고 그동안 다른 일 — "slow_test.py를 돌려 결과를 알려 주고, 기다리는 동안 README 오타를 고쳐 줘." `[tool] run_command(background)` → `started b1` → README 고침 → 다음 바퀴에 `<system-reminder> b1 끝남` → `task_output` → 결과 보고. 바퀴 시각을 화면에 찍어 기다리는 동안 다른 일이 진행됐음을 보인다.
    - 여기까지 확인: `started b1` 다음에 테스트 결과가 오기 전에 다른 `[tool]` 줄이 끼어 있으면 성공입니다.
32. [실행] 차례가 끝난 뒤 몸이 뇌를 깨운다 — 모델이 "끝나면 알려 드릴게요" 하고 `you>` 프롬프트로 돌아온 뒤, 사람은 아무것도 안 치는데 몇 초 뒤 `[harness] b1 끝남 → 모델을 부릅니다` 줄과 함께 assistant가 이어서 말한다. 아래 코드 줄은 입력 대기 대신 알림 쪽 분기가 켜진다.
    - 키보드만 차례를 여는 게 아니다. 작업 완료도 하나의 사건이다.
33. 자주 막히는 곳: 앞자리 sleep — 모델이 `sleep`으로 기다리려 하면 몸이 막고 "백그라운드로 돌리면 알려 준다"고 돌려준다. 모델이 그렇게 하는 건 학습 자료가 그래서이고, 좋은 길을 쉬운 길로 만드는 건 몸의 몫. (녹화에서 모델이 실제로 sleep을 시도하면 그 장면을, 아니면 가드 코드와 직접 넣은 예로.)
34. [모션] 사건이 차례를 연다 — 키보드, 작업 완료, 파일 변경, 타이머가 모두 같은 입구(배열 맨 아래에 붙이고 모델 부르기)로 들어간다. 감시(조건이 맞으면), 예약(시각이 되면), 스스로 알람(모델이 "10분 뒤 깨워 줘"). 규칙 넷: 깨울 때마다 돈이 든다, 알림은 사실이어야 한다, 사람이 다 보고 멈출 수 있어야 한다, 약속은 디스크에.
35. 체크포인트 — 기다리는 일은 몸이 한다.
